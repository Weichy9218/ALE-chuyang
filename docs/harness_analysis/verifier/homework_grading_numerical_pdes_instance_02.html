同样是六条检查全部通过、零条失败，agent 在收到报告后主动放宽了两名学生的给分。这次改动贡献了一半增益。另一半来自初稿里一个与 verifier 无关的写法差异。

一、这道题怎么评分

按给定的评分标准批改五份数值 PDE 作业，交五个文件：grades.csv、error_tags.csv、per_student_feedback.json、common_mistakes_summary.md、grader_manifest.json。

评分是五项的算术平均：分数逐格比对（五名学生乘五个字段共 25 格）、错误标签的集合相似度、逐生反馈对隐藏短语的覆盖率、总结对隐藏短语的覆盖率、清单键齐全。三项里有两项对着隐藏短语打分，这意味着措辞对不上就丢分，而措辞要求从公开材料看不到。

这题的 base 抖动很大：11 次运行的分数跨度是 0.140，所以单轮的正负要放在这个幅度里读。

二、verifier 冻结了什么

六条可执行检查，全是结构契约：文件集合、表头与学生编号、标签词表、每条反馈不超过 70 词、总结非空、清单三个键。

另有三条被列为不可验证，理由写得很清楚：

The public rubric gives maximum points and correctness descriptions but no deterministic partial-credit or deduction schedule for answers that satisfy only some elements. A frozen checker cannot prove exact numerical scores without inventing unstated grading rules.
— verifier_suite.json，contract.grades_csv.rubric_aligned_partial_credit_correctness

也就是说，占分最重的「给分是否合理」这一维，verifier 明确声明测不了。

五、这道题说明什么

又一次「全绿之后才发生的改动」。和 FluSight 一样，触发行为改变的不是失败项，是报告本身。而且这次改动落在 verifier 明确声明测不了的那一维上。

增益的一半根本不属于 verifier。反馈用 ASCII 还是 Unicode 写公式，是初稿阶段的写法偏好，与 verifier 没有关系，却贡献了 +0.043。这类差异在单次运行的对比里无法与组件效应分开，这也是为什么单题单次的 delta 不能直接当成组件的效果。

换行符这种小事会吃掉真实的分。第 31 步那次编辑失败无声无息，verifier 的六条检查不覆盖标签完整性，自查也没发现。机械检查只在它被写出来的地方起作用。
