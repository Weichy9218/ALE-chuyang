# 代码安全与程序分析 面试复习笔记

这一节的目标是把程序分析的核心技术讲清楚，并且能把它们和两件事挂上钩。一是大模型做代码安全任务（审计、漏洞挖掘、逆向）时，这些技术怎么当工具。二是用 cyber/CTF 这类任务训练评估模型时，怎么用程序分析给出的可验证结果当奖励信号。（在这次资格考核里，这块是次要材料，够你在话题转到 ALE 安全题时接住即可。）

## 一、静态分析

静态分析指不运行程序，只看源码或二进制，推断它可能的行为。核心优势是覆盖所有代码路径，不依赖具体输入。核心代价是它推断的是"可能"，因此会有误报（报了但实际不会发生）和漏报（真有问题但没报出来）。

### AST（抽象语法树）

编译器前端把源码解析成的树状结构，每个节点是一个语法构造，比如函数定义、赋值、函数调用。它去掉了括号、分号这些纯语法噪声，保留结构。几乎所有源码级分析都从 AST 起步，因为在树上匹配模式比在文本上用正则可靠得多。Semgrep 的规则本质就是在 AST 上做结构匹配。

### 控制流图 CFG

把函数拆成基本块（一段没有分支、顺序执行的指令），块之间用边表示跳转（条件分支、循环、函数返回）。CFG 回答的是"执行可以按什么顺序走"。它是数据流分析、路径分析的基础。逆向工具里看到的函数流程图就是 CFG 的可视化。

### 数据流分析

在 CFG 上追踪某个值或某个属性怎么随执行传播。经典问题包括：某个变量在某点是否已定义、某个值可能来自哪些地方（到达定值）、某个变量之后还会不会被用到（活跃变量）。它是很多检查的底层机制，比如"用了未初始化的变量""这个指针可能为空"。

### 污点分析

数据流分析的一个专门化，用来找注入类漏洞。三个概念：

- source，不可信数据的入口，比如 HTTP 参数、命令行输入、文件内容。
- sink，危险操作的落点，比如 SQL 拼接、`system()` 执行、文件路径拼接。
- sanitizer，能把不可信数据变安全的处理，比如参数化查询、转义、白名单校验。

规则是：如果存在一条从 source 到 sink 的数据流，中间没有经过合适的 sanitizer，就报一个漏洞。SQL 注入、命令注入、路径穿越、XSS 都可以用这个框架描述。难点在于 sanitizer 识别得准不准，以及跨函数、跨文件的数据流能不能追全。追不全就漏报，把无害流当成有害就误报。

### 符号执行与 concolic

符号执行不用具体输入跑程序，而是把输入当成符号变量，沿着路径收集约束条件（比如走进这个 if 需要 x 大于 10 且 x 小于 100）。到达某个目标点时，把这条路径的约束交给约束求解器（SMT solver，如 Z3），求出一组能真正触发这条路径的具体输入。它能自动构造走到某段代码或触发某个 bug 的输入，这对漏洞挖掘和 CTF 解题很有用。

核心问题是路径爆炸。程序里每个分支都让路径数翻倍，循环和递归让路径数量指数甚至无限增长，符号执行很快就跑不动。concolic（concrete + symbolic，混合执行）是常见缓解手段：用一个具体输入实际跑一遍确定主路径，同时在旁边收集符号约束，然后有选择地翻转某个分支条件去探索新路径，而不是盲目展开所有路径。

angr 是最常用的开源二进制分析框架（Python），能做符号执行、CFG 恢复、concolic。CTF 里典型用法是给它一个二进制，设定"到达打印 flag 的地址"为目标、"到达失败分支"为规避，让它求解出通过校验的输入。局限还是路径爆炸，以及遇到复杂加密、哈希这类求解器啃不动的约束时会卡住。

### SAST 工具：CodeQL 与 Semgrep

SAST（静态应用安全测试）工具的核心思路是把漏洞模式写成可查询的形式，在代码的结构化表示上匹配。

- CodeQL 把整个代码库建成一个数据库（含 AST、CFG、数据流信息），你用一种类 SQL 的查询语言 QL 去写"找出从 source 到 sink 且无 sanitizer 的路径"这种查询。它支持跨过程的污点追踪，表达能力强，适合深度分析，代价是建库和查询较重。GitHub 用它做代码扫描。
- Semgrep 更轻，规则写起来接近"带语义的 grep"，在 AST 上做模式匹配，支持一定的数据流但不如 CodeQL 深。它快、易上手，适合在 CI 里跑规则集，代价是复杂的跨函数漏洞它抓不到。

两者共同的局限是静态分析固有的误报漏报权衡。规则收紧则漏报多，放松则误报多，误报多了开发者就不看了。

面试官可能怎么问 / 怎么答：

- 问：污点分析怎么找 SQL 注入？答：把请求参数标为 source，把执行 SQL 的 API 标为 sink，把参数化查询和转义标为 sanitizer，检查是否存在从 source 到 sink 且不过 sanitizer 的数据流。关键难点是跨函数追踪数据流和准确识别 sanitizer。
- 问：符号执行的最大问题是什么，怎么缓解？答：路径爆炸，分支导致路径指数增长。缓解手段有 concolic 混合执行、路径剪枝、状态合并、设定探索目标只求解相关路径。
- 问：CodeQL 和 Semgrep 怎么选？答：要深度跨过程污点分析、能接受较重的建库，用 CodeQL。要在 CI 里快速跑规则、覆盖常见模式，用 Semgrep。

## 二、动态分析

动态分析指实际运行程序，观察真实行为。优势是它报的问题基本是真的（低误报），因为是实打实触发的。代价是只能覆盖实际跑到的路径，没跑到的地方发现不了（会漏报）。

### fuzzing（模糊测试）

自动生成大量输入喂给程序，看它是否崩溃或触发异常状态。现代 fuzzer 的关键是覆盖率引导：不是纯随机撒输入，而是用插桩记录每个输入走过了哪些代码边，如果某个输入触发了新的覆盖，就保留它并在它基础上继续变异。这样 fuzzer 会自己"进化"出能钻进程序深处的输入。

- AFL / AFL++ 面向可编译或可插桩的目标程序，是覆盖率引导 fuzzing 的代表。
- libFuzzer 是进程内 fuzzer，你写一个接收字节数组的入口函数（fuzz target），它在同一进程里反复调用，适合对库函数做单元级 fuzzing，速度快。

几个配套概念：

- 语料（corpus）是初始种子输入集合。给好的种子能让 fuzzer 更快进入有意义的代码路径，比如给一个 PNG 解析器喂几张真实 PNG。
- 崩溃三角化（triage）指拿到大量崩溃后去重、定位根因、判断可利用性。很多崩溃是同一个 bug 的不同表现，需要归并；还要判断这个崩溃是能被攻击者控制的，还是无害的断言失败。

fuzzing 是现代漏洞挖掘主力的原因：它自动化程度高、几乎不需要理解程序语义、对解析器和处理不可信输入的代码特别有效，而且找到的问题自带能复现的输入（PoC）。工业界靠它持续在浏览器、内核、编解码库里挖出大量内存安全漏洞，Google 的 OSS-Fuzz 就是规模化例子。

### sanitizer（消毒器/检测器）

编译时插桩，让程序在运行中一旦出现某类未定义行为就立刻报错并给出精确位置，而不是默默继续或很久之后才崩。它们放大 bug 的可观测性，和 fuzzing 是天然搭档（fuzzer 造输入，sanitizer 抓问题）。

| 工具 | 检测什么 |
|---|---|
| ASan（AddressSanitizer） | 内存错误：堆栈缓冲区溢出、use-after-free、double free、内存泄漏 |
| UBSan（UndefinedBehaviorSanitizer） | 未定义行为：整数溢出、空指针解引用、错误的类型转换、越界移位 |
| MSan（MemorySanitizer） | 使用未初始化的内存 |
| TSan（ThreadSanitizer） | 数据竞争等并发问题 |

代价是运行变慢、内存占用增大，所以用在测试和 fuzzing 阶段，不用在生产。

### 动态污点分析与插桩

动态污点分析在运行时给不可信数据打标记，跟踪它在实际执行中流到哪里，比静态污点更准（是真实发生的流），但只覆盖跑到的路径，且开销大。插桩（instrumentation）是这些技术的共同底层，指在程序中插入额外代码来采集信息。编译期插桩（如 sanitizer、AFL 的编译模式）快但要能重编译；运行期插桩（如 Pin、DynamoRIO、Valgrind、QEMU 模式）不需要源码但慢，用于分析闭源二进制。

面试官可能怎么问 / 怎么答：

- 问：为什么 fuzzing 成了漏洞挖掘主力？答：自动化、不依赖理解代码语义、对处理不可信输入的代码命中率高、结果自带可复现 PoC，覆盖率引导让它能自主深入。配合 sanitizer 还能抓到不直接崩溃的内存错误。
- 问：ASan 和 UBSan 的区别？答：ASan 抓内存地址类错误（溢出、UAF、double free），UBSan 抓 C/C++ 语言层面的未定义行为（整数溢出、非法移位、空指针解引用）。两者互补，常一起开。
- 问：静态和动态分析怎么配合？答：静态覆盖全路径但误报多，动态低误报但覆盖受限于实际执行。实践上静态先定位可疑点，动态或 fuzzing 去确认能否真实触发。

## 三、二进制与逆向基础

### 编译链接

源码经过预处理、编译成汇编、汇编成目标文件（.o），再由链接器把多个目标文件和库合并成可执行文件，解析符号引用。动态链接下，对库函数的调用在运行时才绑定，靠 PLT/GOT 这类间接跳转表实现，这也是很多利用技术的作用点。

### ELF / PE 结构

ELF 是 Linux 的可执行和目标文件格式，PE 是 Windows 的。都由头部加若干段/节组成，常见的有代码段（.text）、已初始化数据（.data）、未初始化数据（.bss）、只读数据（.rodata）。逆向时先看这些结构确定入口点、导入导出函数、各段权限。

### 调用约定与栈帧

调用约定规定函数调用时参数怎么传、谁负责清栈、返回值放哪。比如 x86-64 System V（Linux）用寄存器 rdi、rsi、rdx、rcx、r8、r9 传前六个整型参数，返回值放 rax。栈帧是每次函数调用在栈上分配的一块空间，存放局部变量、保存的寄存器、返回地址。栈溢出利用的核心就是覆盖栈帧里的返回地址。

### 常见二进制保护

| 保护 | 作用 | 对抗的攻击 |
|---|---|---|
| NX / DEP | 数据页不可执行 | 阻止直接在栈/堆上执行注入的机器码，逼攻击者转向 ROP |
| ASLR | 随机化内存布局基址 | 让攻击者猜不到目标地址，需要先泄露地址 |
| Stack Canary | 在返回地址前放一个随机值，返回前校验 | 检测栈溢出，被改写则中止 |
| PIE | 让可执行文件本身也能被随机化加载 | 配合 ASLR 随机化代码段基址 |
| RELRO | 把 GOT 等重定位表设为只读 | 阻止改写 GOT 劫持函数调用 |

这些保护是叠加的。现代利用往往需要先绕过 ASLR（泄露地址）再配合 ROP 绕过 NX，逐层拆。

### 反汇编 vs 反编译

反汇编把机器码翻回汇编指令，是一对一的。反编译更进一步，试图把汇编还原成类 C 的伪代码，方便阅读，但因为编译丢失了变量名、类型、结构信息，还原是有损且可能出错的猜测。

Ghidra（NSA 开源）和 IDA Pro（商业，长期行业标准）是主流逆向平台，都提供反汇编、反编译（IDA 的 Hex-Rays、Ghidra 自带）、CFG 可视化、交叉引用、脚本扩展。角色是逆向工程的主工作台，动态调试则配合 GDB（加 pwndbg/GEF 插件）或 x64dbg。（你在 ALE 里就是用 Ghidra 那套思路，只不过在 Linux 上用 objdump、pefile、capstone 手工逆的。）

面试官可能怎么问 / 怎么答：

- 问：NX 和 ASLR 分别防什么，为什么要一起用？答：NX 让注入的数据不能当代码执行，ASLR 让攻击者猜不到地址。单独一个都能被绕（NX 用 ROP、ASLR 用地址泄露），叠加起来提高利用门槛。
- 问：反汇编和反编译区别？答：反汇编是机器码到汇编的一对一翻译，可靠；反编译是汇编到伪代码的有损还原，可读但可能不准，因为类型和变量名在编译时已丢失。
- 问：栈 canary 怎么被绕过？答：泄露出 canary 值再原样写回、利用不经过 canary 的溢出点（比如覆盖局部指针）、或针对 fork 出的子进程逐字节爆破（子进程 canary 与父进程相同）。

## 四、内存安全漏洞类

这些漏洞几乎都来自 C/C++ 让程序员手动管理内存和缺乏边界检查。

| 漏洞 | 一句话原理 | 为什么危险 | 缓解 |
|---|---|---|---|
| 栈溢出 | 向栈上缓冲区写入超过其大小的数据，覆盖相邻的返回地址等 | 可劫持控制流，改返回地址跳到攻击者代码或 ROP 链 | Canary、NX、ASLR、边界检查、用安全的字符串函数 |
| 堆溢出 | 堆上缓冲区越界写，破坏相邻堆块或堆管理元数据 | 可篡改堆结构或相邻对象，进而控制流劫持或任意写 | 堆隔离、ASan、加固的分配器 |
| UAF（use-after-free） | 释放后仍使用该指针，此时内存可能已被重新分配 | 攻击者可占位控制那块内存，读到或写入受控数据，常导致 RCE | 释放后指针置空、智能指针、隔离分配、ASan |
| double free | 同一块内存释放两次，破坏分配器空闲链表 | 可被操纵成任意地址分配，导致任意写 | 释放后置空、分配器检测、ASan |
| 类型混淆 | 把一个对象当成不匹配的类型来使用 | 按错误的内存布局解释数据，可越界或伪造指针 | 严格类型检查、运行时类型校验（RTTI）、语言层保证 |
| 整数溢出 | 计算超出整数范围回绕，常见于算长度或大小 | 回绕出的小值导致分配过小的缓冲区，后续写入溢出 | 检查溢出、用更宽类型、UBSan |
| 格式化字符串 | 把用户可控数据当作 printf 的格式串 | `%x` 泄露栈内存、`%n` 实现任意地址写 | 永远用固定格式串，把用户数据当参数传 |

内存安全语言为什么从根上消掉一大类：Rust 用所有权和借用检查在编译期保证没有悬垂指针、没有数据竞争，越界访问默认 panic 而不是越界读写，因此栈/堆溢出、UAF、double free 这些在安全代码里编译期或运行期就被挡住。代价是有学习曲线、和 unsafe 块、以及和 C 交互的边界仍需小心。Go、Java 等带 GC 的语言也消除了手动内存管理类的漏洞，但通常有运行时开销。据统计，微软和 Google 都报告过大型 C/C++ 代码库中约七成安全漏洞是内存安全问题，这是推动内存安全语言的主要动因。

面试官可能怎么问 / 怎么答：

- 问：UAF 为什么这么容易被利用？答：释放后那块内存可被重新分配给攻击者可控的对象，于是攻击者能用旧指针读写自己布置的数据，常能进一步伪造虚表指针或函数指针拿到执行权。
- 问：为什么说 Rust 从根上消掉一类漏洞？答：所有权和借用检查在编译期就排除了悬垂指针和释放后使用，边界检查把越界变成受控 panic，不再是可利用的越界读写，因此整类内存安全漏洞在安全代码里不存在。
- 问：格式化字符串怎么做到任意写？答：`%n` 会把"目前已输出的字符数"写到对应参数指向的地址，攻击者控制格式串就能控制写入的地址和数值。

## 五、供应链与依赖安全

现代项目大量依赖第三方包，攻击面从自己的代码扩展到整条依赖链和构建过程。

主要风险：

- 依赖投毒。攻击者发布恶意包，手段包括抢注相似名（typosquatting）、劫持已有维护者账号后发布带后门的新版本、或往一个被广泛依赖的包里植入恶意代码。
- 构建脚本风险。npm 包的 install 脚本、Python 的 setup.py 在安装时会执行任意代码，装一个包就可能在你机器上跑攻击者的命令。
- 传递依赖。你直接依赖的包又依赖别的包，实际引入的往往是几百上千个你没审过的包。

常见加固手段，你项目里的 pi harness 有一整套可以对应上：

| 手段 | 作用 |
|---|---|
| pin exact version（锁定精确版本） | 不用 `^`、`~` 这类范围，锁死到具体版本，避免自动拉到被投毒的新版本 |
| 锁文件 / shrinkwrap | 记录整棵依赖树的精确版本和哈希，保证每次安装装到的是同一份，可复现、可校验完整性 |
| min-release-age（最小发布时长） | 只装发布已超过一定时间的版本，给社区留出发现并下架恶意新版的窗口，躲开刚投毒就装进来的情况 |
| `--ignore-scripts` | 安装时不执行包的 install/postinstall 脚本，堵住装包即执行任意代码这条路 |
| npm audit | 对照已知漏洞数据库扫描依赖，报告有漏洞的包和可升级版本 |

这些措施的共同思路是减少自动化带来的不可控：不自动升级、不自动执行脚本、装什么有精确记录且可校验、给恶意版本留出被发现的时间差。

面试官可能怎么问 / 怎么答：

- 问：锁文件解决什么问题？答：把整棵依赖树钉到精确版本和哈希，保证构建可复现，并能校验下载内容没被篡改，避免同一份 manifest 在不同时间装出不同（可能被投毒的）依赖。
- 问：`--ignore-scripts` 为什么重要？答：npm 包的安装脚本会执行任意代码，是供应链攻击最直接的落地点，禁用它能让"装一个包"不再等于"在本机跑陌生代码"。
- 问：min-release-age 的道理？答：投毒的恶意版本通常发布后不久就被发现下架，只装足够旧的版本能避开这个窗口，用时间换安全。

## 六、从大模型视角

这一节把上面的技术和"用可验证的 cyber 任务训练评估模型的 agentic 代码安全能力"连起来。

### 模型做代码安全任务的现状与难点

- 代码审计和漏洞挖掘。模型能识别常见漏洞模式（注入、硬编码密钥、不安全反序列化），在小范围代码上表现不错。难点是跨文件、跨函数的长程数据流推理，以及区分真实可达的漏洞和理论上存在但实际触发不了的（误报问题模型同样有）。
- 逆向。模型能读懂反编译出的伪代码、解释函数意图、辅助命名，但对经过混淆、无符号信息的大型二进制，靠模型独立完成完整逆向仍然困难，长上下文和精确性都是瓶颈。
- 通用难点。安全任务往往需要多步工具交互和精确执行，一步算错地址或偏移就前功尽弃，这对模型的长程推理和不能出错的精度要求很高，正好是这类任务用来训练和区分模型能力的原因。

### 程序分析工具怎么给 agent 当 tool

把上面的技术包装成 agent 可调用的工具，让模型不靠脑补而靠实际反馈来工作：反汇编/反编译（Ghidra、IDA 脚本接口）给结构化视图，调试器（GDB）让模型下断点看内存验证假设，符号执行（angr）帮求解触发路径的输入，fuzzer 自动探索崩溃，SAST（CodeQL、Semgrep）给候选漏洞点，编译、跑测试、执行 PoC 提供客观成败信号。关键在于这些工具的输出是客观、可验证的，模型的判断能被实际执行结果检验，而不是停留在自然语言猜测。

### 用可验证结果当奖励

cyber/CTF 任务适合做训练评估，正因为成败可以程序化判定，不需要人打主观分。几种可验证的奖励信号：CTF 拿到 flag（二值判定，天然干净）、漏洞利用是否成功（PoC 是否真的触发崩溃或拿到 shell，可自动检测）、补丁质量（定义成"原 PoC 不再触发且原有测试全通过"，两条都能自动跑）、覆盖率或中间进展（用是否走到某段代码这类里程碑给更密的过程奖励，缓解稀疏）。这套思路的价值是奖励来自真实执行而非模型自评，不易被 reward hacking，且任务可按难度和工具依赖分层。

面试官可能怎么问 / 怎么答：

- 问：为什么 cyber/CTF 任务适合训练 agentic 能力？答：成败可程序化验证（flag、PoC 触发、测试通过），奖励客观且不易被刷；任务需要多步工具交互和长程精确推理，正好锻炼和区分这些能力。
- 问：怎么给"模型修漏洞"定义一个可验证奖励？答：合格补丁要同时满足原 PoC 不再触发漏洞、且原有测试全通过。两条都能自动执行判定，避免主观打分，也防止只堵 PoC 却引入回归的偷懒解。
- 问：程序分析工具在 agent 里起什么作用？答：把猜测变成可验证的操作。模型用反汇编看结构、用调试器验证内存状态、用符号执行求输入、用测试确认修复，工具的客观输出既指导推理也提供训练信号。
