# Agent Harness 与工具使用

这一块你有实操，缺的是把它组织成能讲清楚的语言。目标有两个：一是能把 agent harness 的工程讲透，二是把它和你简历里的 harness–model 协同进化对起来。你在 ALE 上跑过两套对照鲜明的 harness（薄的 pi、重的 ale_claw），这是很好的具体案例。

## 一、先分清两个词：harness 和 scaffold

面试里这两个词容易混，分清楚显专业。

harness 指承载模型跑起来的整套外壳：主循环、上下文管理、工具接入、会话存储、超时和预算控制。它是"运行时基础设施"。

scaffold 指注入给模型的引导结构：system prompt、工具描述、规划或反思的提示、干预策略。它是"喂给模型的引导"。

一套 agent 系统可以 harness 做得完整而 scaffold 做得极薄（pi 就是这样），也可以两者都厚（ale_claw）。区分它俩的意义在于：研究模型自身能力时，你希望 scaffold 尽量薄，这样跑出来的行为基本是模型自己的行为，不是框架替它定的。这正是薄 harness 适合当研究基座的原因，也和你要研究"去掉 harness 后模型还剩多少能力"直接相关。

## 二、一次 rollout 的全貌

一次 rollout 是 agent 在一个任务上从收到 prompt 到进程退出的完整过程。要能口头讲清这个循环：

1. 启动装配：读配置拿到 provider 和模型，构建 system prompt，注册工具，初始化上下文。
2. 进主循环：一个 while 循环，每轮流式取一条 assistant 响应；若带工具调用就执行，把结果推回上下文；发一个 turn 结束事件；再检查是否该停。
3. 每轮执行工具：工具调用打到环境（文件系统、shell、或远程桌面），结果作为观察进上下文。
4. 上下文接近上限时压缩（compaction）：自动摘要旧消息，腾出窗口。
5. 停止：模型不再发工具调用（自然停），或触发停止回调，或出错。

停止条件是个容易被追问的点。最薄的做法（pi）只有三个停止条件：这条消息不含工具调用、外部回调要求停、出错。它没有 max steps、没有 token 预算，何时停完全交给模型判断。对短任务没问题，对长任务模型会自我合理化地一直跑（我在 ALE 见过一个任务刷到 135 步、烧掉几百万 token），所以给长程任务加预算护栏是 harness 的必要工程。

## 三、pi 与 ale_claw：一薄一厚的对照（你的实操案例）

这个对照是你最好的谈资，因为它把 harness 设计的每个维度都摊开了。

| 维度 | pi（薄） | ale_claw（厚） |
|---|---|---|
| 谁跑主循环 | 外部 Node CLI 拥有整个循环 | 进程内 Python 手写 while 循环 |
| 运行基底 | Linux 容器本地文件系统，只有 bash 和文件工具 | 通过 Cua SDK 连远程桌面虚拟机，能做图形界面操作 |
| 工具集 | 七个：read/bash/edit/write/grep/find/ls | computer（GUI）、analyze_image（视觉）、多后端文件、exec、web_search/fetch、memory、子 agent 委派 |
| 停止条件 | 模型不发工具调用就停，无步数护栏 | 靠 DONE 信号加 max_steps 上限 |
| 上下文 | 有 compaction | 反应式加主动式压缩、消息规范化清洗层 |
| 记忆 | 无 | 磁盘持久化记忆库加刷写策略 |
| 多模型 | 单模型 | summary/gui/auxiliary 多模型分工，五处独立的思考档位 |
| scaffold | 极薄，system prompt 就一句角色加工具列表加两条准则 | 模块化 PromptBuilder，注入 AGENTS.md、记忆规则、DONE 约定 |

一句话总结这个对照：任务只要在 Linux 里读写文件跑命令，pi 这种薄壳接入成本低、行为干净；任务要图形界面、长时程、记忆、子 agent 协作，就需要 ale_claw 这种厚 harness。选哪个取决于任务需要多少外部支撑，以及你是想研究模型裸能力还是想把任务做成。

## 四、harness 的可改造面（这是协同进化的抓手）

薄 harness 的价值在于它把改造点暴露得很清楚。以 pi 为例，不用 fork 主循环，就有几个注入行为的位置，从轻到重：

- 循环内的三个钩子。轮末回调（判断是否该停，可以加预算止损、加客观完成判据）、工具执行前回调（可拦截一次调用，比如检测到改文件前没读过就拦下、检测到重复失败命令就提示换思路）、工具执行后回调（可把客观事实注入观察，比如把某个指标的当前值和目标值附回给模型，逼它面对差距）。这三个钩子正好覆盖三种介入时机：动作前拦截、动作后反射、轮末止损。
- extension 系统：注册新工具（补上内置工具没有的能力，比如一个通用 verifier 工具）、订阅事件采集轨迹特征。
- system prompt：注入通用程序性准则（改文件前先读、产出后先自检）。这是静态倾向，改不了运行中的相机决策，相机决策要靠钩子。
- 模型配置：换模型、开关 reasoning、调上下文窗口和采样。

为什么这一节对你重要：你简历里说 harness 引导模型 on-policy 产生可学习轨迹，再训练内化。上面这些钩子和注入点，就是 harness 引导的具体手段。你可以讲：我用轮末钩子给客观完成判据、用工具后钩子把事实反射给模型，引导它跑出既成功、又带可学习结构的轨迹，这些轨迹再拿去训练把能力内化进权重。这把抽象的协同进化落到了具体的工程接口上。

要能守住一条红线：这些注入必须是注入事实或控制，不能替模型生成动作，更不能泄露答案。否则跑出来的轨迹是 harness 的功劳不是模型的，训练内化就没有意义，评测也失真。这条"镜子不是地图"的约束，是做协同进化时最容易踩的坑，能主动讲出来显示你想得深。

## 五、一个真实的 debug 故事（你的加分素材）

在 ALE 上我遇到一个现象：同一个模型（gpt-5.6）在薄 harness（pi）里工具调用很积极、能解题，在厚 harness（ale_claw）里几乎不发工具调用，30 轮里只发 0 到 1 次，每轮先说要干什么然后道歉，六道题全 0 分。

排查过程：先排除外部因素，确认网关本身工具调用能通（curl 直接打通）、执行器能用（pi 用同一套能解题）、任务本身没问题（pi 能解）。在三种 ale_claw 配置下复现，确认是模型和 harness 的相互作用问题。最后 root cause 到模型循环路由：ale_claw 按模型名把模型分派到不同的处理循环，gpt-5.6 没匹配到任何专用循环，掉进了兜底的一个 Qwen 风格视觉循环，那个循环把工具当成 Qwen 的 XML 标签发、还强行注入截图，而 gpt-5.6 是原生 OpenAI 工具调用格式，看不懂 Qwen 的 XML，于是只输出纯文本、从不发工具调用。修复是一行路由正则的改动，把 gpt-5.6 也路由到原生工具调用的循环，改完那道冒烟题从 0 分变 1.0 分，五轮内正常用工具解出。

这个故事能讲出三个点：一是 harness 对模型行为的影响可以是决定性的，同一个模型换个 harness 就从能干活变成完全不干活；二是 debug agent 系统要分层隔离变量（网关、执行器、任务、harness 逐个排除）；三是模型和 harness 的接口协议（工具用原生 tools 数组还是 XML 标签）不匹配会静默地毁掉一切。对你研究协同进化，这正说明 harness 和模型不是独立的两块，它们的耦合要专门设计。

## 六、工具使用与 context engineering 要点

- 工具应是薄封装，把一个文件或 shell 操作包成模型可调用的接口，加截断、输出累积这类工程细节，不塞任务逻辑。工具越薄，模型行为越是它自己的。
- 结构化输出：让模型按 schema 产出，验证放在工具调用层，不匹配就让模型重试。这比事后解析自然语言稳。
- MCP（Model Context Protocol）：一套把工具、资源、提示标准化暴露给模型的协议，让 harness 能统一接入外部能力。你简历里提到熟悉 MCP，要能说清它解决的是工具接入的标准化和解耦。
- 渐进式披露（progressive disclosure）：你在预测未来智能体里用过，能力和知识按需暴露而不是一次塞满上下文。要能讲它解决什么：上下文预算有限、一次全给稀释注意力、也容易让模型过早锁定思路。
- 上下文压缩（compaction）：长任务窗口不够时摘要旧消息。坑是摘要会丢信息，关键事实要保住；且即便有压缩，无步数护栏时上下文照样滚很大。

## 七、预判的问答

问：厚 harness 和薄 harness 你怎么选？答：看目的。要把任务做成、要复杂能力（GUI、记忆、多 agent），厚的。要研究模型裸能力、要跑出的行为是模型自己的、要低成本快速迭代，薄的。做协同进化研究我倾向从薄的起步，因为它 scaffold 干净、改造点清晰，我能精确控制注入了什么，从而能区分哪些能力是模型的、哪些是 harness 撑的。

问：怎么让 harness 引导出的能力真的进了模型，而不是训练后一撤 harness 就没了？答：用对照评测。训练后在完全无 harness 引导的裸设定下评模型，和训练前比、和只有 harness 无内化的版本比，看内化的增量。协同进化的每一轮都应该能观察到裸模型能力在抬升，否则就是 harness 在替模型干活。

问：agent harness 里最难的工程问题是什么？答：我的体感是三个。一是何时停，无护栏会失控、护栏太紧会截断有效探索。二是上下文管理，长程任务信息又多又要保关键。三是模型和 harness 的接口匹配，我亲手踩过工具协议不匹配导致模型完全不干活的坑。这三个都是长程 agentic 任务放大出来的问题。

问：你说的 harness 引导 on-policy 轨迹，和直接 RL 采样有什么不同？答：直接采样是模型自己跑，冷启动时在稀疏长程任务上常跑不出正样本，没有可学的东西。harness 引导是用轮末判据、事实反射、前置守卫这些手段提高轨迹的成功率和可学习结构，但注入的是事实和控制不是答案，所以轨迹仍然是 on-policy 的、仍然反映模型的决策，只是被引导到了更有信息量的区域。这解决的是 RL 冷启动的探索问题。
