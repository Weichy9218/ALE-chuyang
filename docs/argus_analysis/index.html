2026-07-27 · gpt-5.6-sol · Boyue 端点 · 组会分享

Summary

我把 Argus（四角色自主系统）在 ALE 105 题上的运行结果拿来和我自己的单体 ale_claw 做了对比。核心发现：

  • 26 题同模型对照，Argus 高 0.046，去掉一道题只高 0.007。 统计上不显著。
  • Argus 赢在门槛题。 三道 base 拿 0 分、Argus 拿满分的题，失败原因都是同一个：单体自认完成但产物不达标，没有独立环节能发现。
  • 关键变量不是「多角色」或「Reviewer 能打回」。 是四个设计选择的组合：每轮全新会话让 Reviewer 物理上不受 Engineer 叙述影响、CHECKPOINT.md 双向可纠正让状态收敛、Manager 作为唯一连续记忆承载崩溃恢复、done 必须有独立正面证据而非流程性判定。
  • 可迁移的设计经验：有权力的复核需要三样配套——每轮新会话、推进必须有证据、终检再加一层。

下面所有分析的原始轨迹（run.json、argus_summary.json、events.jsonl、task_card.json）都在 docs/argus_analysis/ 的三个 case 子目录下，可以直接读 Reviewer 的判定原文和 Engineer 的每一步。

二、Argus 系统架构

四个模型角色在一份落盘的项目状态上轮流工作，彼此不共享对话上下文，只通过 CHECKPOINT.md 和结构化事件流交接。官方叫 dense intelligence——把决策、执行、验证绑在同一条长循环里，而不是一个 agent 一口气做完。

三平面与四角色。控制平面调度，执行平面产出并独立复核，记录平面只存事实不判定完成。右侧虚线是运行时自进化回路。
角色做什么权力边界
Manager接操作者意图，选生命周期和 vertical，推进或回退阶段唯一能改阶段的角色；在所有其他角色每轮失忆的系统里，它是连续性的唯一承载者
Planner把目标拆成 backlog，每个子任务带验收命令产出结构化任务，不能改阶段
Engineer在沙箱里执行一个有边界的回合产出交付物；自选 review=skip 或 required（低风险 bounded 工作可以跳过复核）
Reviewer独立检查产物和日志返回 done / continue / blocked，判定权威，系统不许其他角色覆盖

这四个角色本身不稀奇。真正不同的是下面四个设计选择。

设计选择一：每轮全新会话，CHECKPOINT.md 双向可纠正

每轮 Engineer 和 Reviewer 都开全新会话。Reviewer 物理上看不到 Engineer 上一轮的推理链，不是「不被说服」，是根本没有那个上下文。角色之间唯一的状态桥是 CHECKPOINT.md——Engineer 写它，Reviewer 在审查时发现不对可以直接改它。这意味着共享状态会朝正确方向收敛，即使单次写入有错。

设计选择二：Manager 是唯一有连续记忆的角色

在一个所有执行角色每轮都失忆的系统里，Manager 是唯一知道完整历史的。ct_geometry 第 1 轮 Engineer 后端崩了，是 Manager 判 continue 让系统换新会话接上第 2 轮。崩溃恢复不需要特殊逻辑——新会话读 CHECKPOINT.md 就知道该从哪继续，Manager 负责决定要不要继续。

设计选择三：done 必须有独立正面证据

系统不接受「Engineer 说完成了」或「流程走完了」作为完成的依据。done 需要 Reviewer 给出具体的正面证据（测了什么值、对比了什么文件、结果是什么）。收尾任务还有 Goal Gate 再加一层。这让轮数成为规则的自然结果而不是人为设定：没有证据就 continue，有证据就 done，不需要规定跑几轮。

设计选择四：Engineer 自选复核路由

不是所有工作都走 Reviewer。Engineer 完成一个回合后自选 review=skip 或 required。低风险 bounded 工作（比如装个包、跑个初始化脚本）可以跳过复核，只有关键产出才强制独立审查。这是成本控制：不是每一步都花 Reviewer 的 token。

ALE 专用的 vertical

Argus 有个 ale_last_exam vertical，把最常导致零分的失败写成八条硬门槛交给 Reviewer 逐条核：精确输出路径、交付包齐全、能被原生程序解析、长流程真跑完、值是实测不是猜、原生证据为真、跨产物一致、终检无遗漏。后面三道题里 Reviewer 的 stop_reason 就是在逐条对照这些。

base 失败原因

反复修改体素尺寸（0.833、1.0、0.765），LEAP 要求接近 0.8 每次都报错。MSE 在被错误破坏的网格上测的。优化器朝错方向漂（SAD 800→951，真值 786）。最终交的 JSON 是圆整数 784/1214/-2.0，和自己搜出来的都不一致。第 86 步自认完成，没有独立核验。

Argus 过程

角色事件取自 ct_geometry_case/argus/argus_summary.json。

七、经验总结

1. 独立验收的权力是必要条件，不是充分条件

我的 verifier 没有打回权力，也够不到真正的评分面。但光给 Reviewer 权力不够——它还必须物理上无法被 Engineer 的推理链带偏（全新会话），并且它的判定标准必须是具体的正面证据（测了什么值、对比了什么文件），而不是「看起来做完了」。

2. 有权力的复核需要三样配套

我之前给验证加过硬权力，当时判定为死路。Argus 撑住这个权力靠的是：每轮新会话防共识偏见、CHECKPOINT.md 双向可纠正让状态收敛、Goal Gate 在终检上再加一层防 Reviewer 自己判松。我缺的不是判断，是这套配套。

3. Manager 作为唯一连续记忆比想象中重要

在所有执行角色每轮失忆的系统里，得有一个角色知道完整历史、决定要不要重试。ct_geometry 崩溃后能接上，不是靠特殊的恢复逻辑，是 Manager 判 continue + 新会话读 CHECKPOINT.md 自然恢复。

4. 规划拆解对工具链任务有价值

abm_hangzhou 单体 18 步超时，Argus 27 分钟完成。Planner 不只是"拆成步骤"，而是每个子任务带验收命令——Engineer 知道什么算做完这一步。对需要多步配置才能跑起来的题，这比加 token 有用。

5. 多角色在 26 题上统计不显著

去掉 ct_geometry，Argus 只比 base 高 0.007。还输了 5 题。更硬的证据在 SWE-Bench Pro（731 题，78% vs 59%）。ALE 26 题的价值是把机制讲清楚，不是证明分数优势。

6. 代价真实

三道题分别 $16、$19、$10，输入 token 是单体数倍到二十倍。门槛题值得，高分再磨的题未必。

怎么看原始轨迹

每个 case 子目录结构一致：

  • task_card.json — ALE 的题目定义（prompt、评分规则、输入文件、VM 配置）
  • argus/run.json — 整次运行的元数据（模型、步数、token、耗时、得分）
  • argus/argus_summary.json — 每个 mission 的 Reviewer stop_reason 原文，这是最有信息量的文件
  • argus/events.jsonl — ALE harness 级别的事件流（部署、执行、评分）
  • argus/eval_result.json — 最终评分结果

要看 Argus 具体怎么做一道题，读 argus_summary.json 的 stop_reason 字段。它是 Reviewer 写给系统的判定原文，包含它核了什么、测了什么值、怎么得出结论。
