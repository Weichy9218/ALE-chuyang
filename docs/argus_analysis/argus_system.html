Argus 系统是怎么做的：细节、特色，以及它能在 ALE 上成功的关键

这页只讲一件事，Argus 作为一个 agent 系统在结构上做对了什么。它不是把一个模型调得更聪明，而是把决策、执行、验证拆成有明确权力边界的角色，跑在一份可持久、可审计的状态上。下面用几张图把这套结构讲清楚，最后对照我只做了 prep 和 verifier 两层的尝试，说明差在哪、能学什么。

一、三个平面加四个角色

Argus 官方把系统分成三个平面。控制平面管调度和意图，执行平面干活并做复核，记录平面只存事实、不判定工作算不算完成。四个模型角色分布在前两个平面上，各自有明确的权力边界。

图 1　三个平面与四个角色。控制平面调度，执行平面产出并复核，记录平面只存事实。右侧虚线是自进化回路，审查通过的结果会沉淀成下一次任务能用的持久状态。

关键在最后一句。记录平面存下所有事实，但它不决定工作算不算完成。完成与否只由执行平面里那个明确选定的判定路径决定，要么 Engineer 自审（仅限低风险有边界的活），要么独立的 Reviewer。控制平面负责调度和推进，但推进阶段要有证据。三件事分开，谁也不能既当运动员又当裁判。

二、reviewed mission loop：任务怎么跑完一轮

Argus 的长命对象是 campaign，不是一段对话。campaign 被切成一个个 mission，调度器一次只发一个 mission，跑完记录结果，在干净的边界上才推进。每个 mission 内部是 Engineer 和 Reviewer 的反复循环，下图是官方 Algorithm 1 的流程。

图 2　reviewed mission loop（官方 Algorithm 1）。Engineer 产出后，低风险有边界的活可以自审，否则走独立 Reviewer；收尾任务和 vertical 要求的复核不能跳过。continue 就返工，done 才收下。

这个循环里有三个容易被忽略但很关键的约定。

  • Engineer 和 Reviewer 的每一轮都用全新的模型会话。跨轮的连续性只靠 CHECKPOINT.md 这一份文件传递，里面是目标、当前状态、已验证完成、失败的死路、待解问题、下一步。这让 Reviewer 读到的是产物本身和这份状态，不是 Engineer 一路的叙述，不容易被带偏。
  • Engineer 写 checkpoint，独立复核被触发时 Reviewer 是这一轮 checkpoint 的最终编辑者，它会按产物纠正里面的话。
  • 完成的来源被显式记下来。完成永远不来自文件名、token 数量或措辞关键词，只来自 Engineer 自审或独立 Reviewer 这两条明确路径之一，而且收尾和 vertical 要求的复核不能被豁免。

三、Reviewer 是一条选择性纠错通道

把 Reviewer 单独拎出来说，因为它是这套系统相对单体 agent 最大的增量。单体的毛病是执行的人同时宣布完成，于是自认做完就等于交付。Argus 让一个独立的、读真实文件的 Reviewer 来判，而且它的判定权威，系统不许用关键词或标签去覆盖它。下面是官方在 SWE-Bench Pro 731 题上公开的数据。

图 3　Reviewer 的路由与挽救（SWE-Bench Pro 731 题，来自 Argus 技术报告）。复核集中在更难的那部分任务上，被要求返工的题里近八成最终通过。

值得学的一点是路由。Argus 不是每道题都上独立复核，而是把独立复核集中在高风险、收尾这类地方，低风险的活让 Engineer 自审。这样既保住了验收的把关，又不让每题都付双倍成本。

四、固定模型的运行时自进化

Argus 的模型参数是冻的，但每一次审过的 mission 都可能改变下次任务能用到的持久状态。它把这件事定义得很窄，只有走完「产出候选、按产物核查、授权方提交、后续任务复用」这四步、真被留下来复用的，才算数。没走完这条路的活动不计入。

图 4　固定模型的运行时自进化。留下来的不是模型权重，是审过的记忆、技能、流程、验证规则、路由和任务定义。

谁能改、谁能提交，是分开的，这是它设计里很讲究的地方。

持久状态谁产出候选谁提交

产出和提交分开，意思是没有哪个角色能自己扩自己的权。这跟前面 Reviewer 的设计是同一条原则，把关的权力和被把关的行为不放在同一个人手里。

五、可靠性与资源治理

长时间跑的系统就算单次模型调用很强，也会因为运行漂移而失败，比如一直原地打转、反复提交同一个失败任务、卡在一个阶段推不动。Argus 把这些当成一等公民来治理。

  • 回合级进度分类加边界重规划。 一轮里没有产生决定或产物变化的工作会被停下或重新表述，长跑的外部作业和模型推理分开跟踪。
  • 子任务连败熔断。 同一族任务连续失败若干次，就算模型每次换个说法重提，也会被自动跳过，不再送到 Engineer。
  • 无进展上报与探针。 连续几个 mission 没有前进就上报操作者；空闲若干轮就派一个探针任务，去验证「卡住」这个判断是不是已经过时。
  • 预算集中在调用边界核算。 开工前查预算、完工后对账，任何角色都不能自己扩自己的额度。

这些是让前面那套权力结构在长流程里不失控的兜底。Argus 自己也踩过坑，有过一个活锁 bug，Reviewer 每轮都认证了证据、Manager 却总回 hold，白烧了近 20 美元，之后才补上活锁检测。多角色带来了单体没有的新失败方式，需要专门的熔断去接住。

六、为 ALE 定制的 vertical

ALE 按隐藏参考给完成的交付物打分，agent 退出后才评。Argus 有一个专门的 ale_last_exam vertical，把最常导致直接零分的东西写成八条硬门槛，交给 Reviewer 逐条核。这解释了主页三道题里 Reviewer 到底在核什么。

contract-complete　题面每条要求逐项对到产物
bundle-present　完整交付包在精确路径上
artifacts-parse　能被原生程序或格式检查器解析
workflow-finished　长流程真跑完，不是中途
values-measured　报的值是实测算出，不是猜的
native-evidence-valid　原生程序状态和截图为真
cross-artifact-consistent　跨产物的标识、时间、维度、值一致
final-hard-gate-audit　终检没有缺失、畸形、全空、冲突

ct_geometry 里 Reviewer 从 sinogram 重跑重建核 SSIM，就是 values-measured 和 workflow-finished；wsi 里用 OpenSlide 重读坐标区域，是 native-evidence-valid；abm 里查值是仿真算的不是抄 AFC 标签，是 values-measured。八条门槛不是空话，是针对隐藏评测失分方式的具体清单。

七、对我的启发

我之前在 ale_claw 上只加了 prep 和 verifier 两层。对照 Argus 这套结构，差别不在于「我少加了几个角色」，而在于几条设计原则我没做到位。

1. 把关要有权力，而且要能触达真正的评分面

我的 verifier 是无权力的辅助，只推结果、不能打回，而且它只对公开材料做冻结的机械检查，够不到隐藏参考决定的评分面。Argus 的 Reviewer 判定权威、能强制返工，还能从原始数据重跑到被打分的那个量上。同样是「加验证」，有没有权力和能不能触达评分面，是两回事。

2. 权力要有配套才不失控

我试过给验证加硬权力，当时判定为死路就放弃了。现在看，Argus 让权力不失控靠的是三样配套，复核开全新会话保证独立、推进必须见到具体证据、加一圈熔断防止卡死。我当时缺的是这套配套，不是「要不要权力」的判断。

3. 产出和提交分开，是贯穿全系统的一条原则

不只是复核，连自进化里改记忆、改技能都是 Engineer 产出候选、Reviewer 提交。把关的权力和被把关的行为始终不在同一个角色手里。我的 prep 和 verifier 是挂在单体 writer 旁边的辅助，writer 仍然自己决定一切，这条原则没有落进结构。

4. 状态是持久、可审计的对象，不是一段对话

Argus 的长命对象是 campaign，不是 transcript，崩溃后从提交过的状态接着跑。我的 prep 侦察结果和 verifier 检查结果都是喂给 writer 的一次性文本，没有沉淀成可复用、可审计的持久状态。

5. 长流程要把运行漂移当成一等问题

我关注的是单轮的准备和验证质量，没有系统地处理原地打转、反复失败、卡阶段这些长流程特有的失败。Argus 有专门的熔断和上报。要做有体系的 agent，这一层绕不过去。
