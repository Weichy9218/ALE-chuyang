数字营销受众分群

taskId：business_finance/digital_marketing_audience_segmentation_1

从约一万条客户档案中筛出"近 90 天高频购买但近 30 天不开邮件"的再触达人群，套用治理规则做抑制、剥离 PII、算每人短信与推送资格，再与六个已有受众做重叠分析，交出三个文件，由本地脚本对照隐藏参考答案按加权分打分（0.0 到 1.0）。

题目做什么

角色设定是数字营销分析师，为一次再触达（re-engagement）活动做受众分群。整个流程是一条单阶段的数据处理链：从 parquet 档案里按条件筛人，套治理规则，算资格，做重叠分析，输出三个文件。下面按处理步骤拆开。

第 1 步：按目标条件筛出合格人群

目标人群定义在 segmentation_brief.md：近 90 天有 3 次及以上购买，且近 30 天没开过任何邮件。落到字段上是三个条件同时成立（AND）：

  • purchase_count_90d >= 3
  • email_opens_30d == 0
  • last_email_open_days_ago > 30

业务含义是"买得多但邮件够不着"，所以改用短信和推送去触达。

第 2 步：套治理规则做抑制

依据 governance_policies.yaml 的抑制列（Suppression List）：有活跃工单的客户从所有外发活动里抑制掉，条件是 support_tickets_90d > 0。这一步在第 1 步的合格集上再做一次剔除，得到最终受众。参考答案里最终受众规模是 449 人。

第 3 步：算每人的短信与推送资格

激活渠道来自 brief 和 governance 的 Opt-Out Compliance：

  • sms_eligible：sms_opt_in == 1 记 1，否则 0。
  • push_eligible：push_opt_in == 1 记 1，否则 0。
  • any_channel_eligible：短信或推送任一为 1 即记 1（逻辑或）。

这三列以 1/0 写进 roster 每一行。参考答案统计：短信资格 109 人、推送资格 104 人、任一渠道资格 196 人（109 与 104 有重叠，取并集是 196）。

邮件退订（email_opt_out = 1）只影响邮件渠道，本次活动用短信和推送，所以不缩减受众规模，只在 segment_definition.json 里以 opt_out_compliance: true 声明已遵守。

第 4 步：剥离 PII 列

为 PII 合规，输出 roster 必须去掉 age、gender、city、state 四列。注意 governance_policies.yaml 的受限字段只列了前三个（age、gender、city），但 brief 第 5 步和打分脚本都把 state 一并算作必须去掉的列，所以四列都不能留。

第 5 步：与六个已有受众做重叠分析

existing_audiences.csv 给了六个已有受众及其定义（如 state = 'CA' AND ltv > 5000）。对每个受众，需要在完整档案上求出其成员集合，再与本次合格受众的 customer_id 求交集：

  • overlap_count：交集人数。
  • overlap_pct = overlap_count / 合格受众规模 × 100，分母是本次受众的 449，不是已有受众自身的 size。
  • flag_high_overlap：高重叠标记（参考答案中六行都是 False，该列不参与打分）。

两处要小心：AUD-003 Email Engaged 定义是 email_opens_30d >= 3，与本次受众的 email_opens_30d == 0 天然互斥，重叠必为 0。AUD-005 Cart Abandoners 定义用到 has_cart_abandonment，这个列在数据字典和档案里都不存在，无法匹配到任何人，参考重叠也是 0。求重叠要在完整档案（含 state 等列）上算，不能用已剥离 PII 的 roster。

硬性要求

  • 合格人群判据严格按 brief：purchase_count_90d >= 3 且 email_opens_30d == 0 且 last_email_open_days_ago > 30，三条同时成立。
  • 必须做工单抑制：support_tickets_90d > 0 的客户从受众里移除。
  • 输出 roster 里绝不能出现 age、gender、city、state（大小写不敏感，出现即判 0）。
  • 受众规模不得低于治理下限 50（min_size）。参考受众 449 远超下限，若你的受众不足 50 会直接判 0。
  • 三个文件都要能被解析（JSON 合法、CSV/TSV 可读）并保存到 output/ 目录，缺一或读不出即判 0。
  • overlap_pct 的分母必须是本次合格受众规模，不是已有受众的 size。
  • 运行环境：机器上有 Python 3.12 和 uv；依赖清单在 input/runtime_env/pyproject.toml，用 cd input/runtime_env && uv sync 安装，用 uv run --project input/runtime_env python 脚本.py 运行。

用什么评测

评分链路是纯程序化的，没有 LLM 参与。main.py 的 evaluate() 用 session.read_bytes 依次读六个文件：三个 agent 输出（output/ 下三件）加三个隐藏参考（reference/ 下同名三件），任一读取抛异常就返回 [0.0]。读到后调用 evaluate_segmentation.py 的 score_segmentation(seg_out, roster_out, overlap_out, seg_ref, roster_ref, overlap_ref)，该函数返回 {"score": float, "details": dict}，harness 取 [result["score"]] 里的那个浮点数为最终分。

总分是六个组件的加权和，权重合计为 1.0：

组件权重（脚本常量）衡量什么
segment_definition 结构0.15（W_SEG_STRUCTURE）四项结构检查的通过比例
audience_stats0.10（W_AUDIENCE_STATS）四个统计量落在容差内的比例
roster customer_id0.35（W_ROSTER_IDS）合格客户集合与参考的 Jaccard 相似度
roster 资格列0.20（W_ROSTER_ELIG）交集客户三列资格的逐格准确率
overlap_count0.15（W_OVERLAP_COUNTS）六个受众重叠人数精确命中的比例
overlap_pct0.05（W_OVERLAP_PCT）六个受众重叠百分比落在容差内的比例

每个组件都是 0 到 1 的比例值，乘权重相加，最后 round(final, 4)。这意味着分数是连续的，可以拿部分分。roster 的 customer_id 集合权重最大（0.35），是本题分数的主要来源。

在计算这些组件之前，有若干硬门槛，一旦触发直接返回 0.0，不再进入加权计算。

怎么评测

硬门槛（命中即 0.0）

判据条件后果
文件可读六个文件（3 输出 + 3 参考）中任一 read_bytes 失败evaluate() 直接返回 [0.0]
JSON 可解析segment_definition.json（输出或参考）无法 json.loads返回 score=0.0

组件一：segment_definition 结构（权重 0.15）

四项检查，各占 1/4，通过数除以 4：

检查通过条件
filter_predicates 集合相等把每条谓词归一化为 (str(field), str(operator), str(value)) 三元组，输出集合与参考集合完全相等。参考三条：(purchase_count_90d, >=, 3)、(email_opens_30d, ==, 0)、(last_email_open_days_ago, >, 30)。
suppression_rules 集合相等同样按 (field, operator, value) 三元组比（reason 不参与），参考为 (support_tickets_90d, >, 0)。
activation_channels 键集合相等渠道名集合等于 {sms, push}。
pii_fields_removed 覆盖输出集合等于参考集合，或是其超集。参考为 {age, gender, city}，所以多列出 state 也算通过。

谓词比对是字符串精确比：value 会被 str() 转字符串，写 3 得 "3"、写 3.0 得 "3.0"（不匹配）。operator 必须与参考用一样的写法（>=、==、>），换成 gte、equals 之类会失配丢掉该项。

组件二：audience_stats（权重 0.10）

检查四个字段：total_qualifying、sms_eligible、push_eligible、any_channel_eligible（pct_of_total_profiles 不在其中）。逐字段判定，通过数除以 4：

  • 输出缺该字段（值为 None）：跳过，不计通过，但分母仍是 4，等于丢分。
  • 无法转 float：跳过（丢分）。
  • 参考值为 0 时，输出也为 0 才算通过。
  • 参考值非 0 时，相对误差 abs(out - ref) / abs(ref) <= 0.02（2%）算通过。

按参考值换算的允许绝对偏差：total_qualifying 449（±8.98）、sms_eligible 109（±2.18）、push_eligible 104（±2.08）、any_channel_eligible 196（±3.92）。

组件三：roster customer_id（权重 0.35）

取输出与参考各自的 customer_id 集合（去空白、去空串），算 Jaccard 相似度 |交集| / |并集|。完全一致得 1.0，多筛或漏筛的客户都会拉低这个值。这是权重最大的一项。

组件四：roster 资格列（权重 0.20）

对每个既出现在输出、又出现在参考里的 customer_id，逐个比较 sms_eligible、push_eligible、any_channel_eligible 三列，命中格数除以（交集行数 × 3）。比较前用 _normalize_bool 归一：1/true/yes → "1"，0/false/no/空 → "0"。只在参考里、不在输出里的客户不计入分母（那部分损失已经由组件三的 Jaccard 承担）。

组件五：overlap_count（权重 0.15）

按 existing_audience_id 对齐，对参考里的每个受众（共 6 个），若输出中该行存在且 int(overlap_count) 与参考完全相等则算命中，命中数除以 6。缺行或计数不等都丢该项。

组件六：overlap_pct（权重 0.05）

同样按 6 个受众对齐，abs(out_pct - ref_pct) <= 0.5（0.5 个百分点容差）算命中，命中数除以 6。

失分的典型形态

  • 直接判 0：三个文件之一没写到 output/ 或格式坏了；roster 里留了 age/gender/city/state 任一列；受众筛得不足 50 人（比如把 AND 写成 OR 或漏了某个条件导致集合塌缩）。
  • 丢组件三（0.35）：过滤条件理解偏差是最常见的。比如把"3 次以上"写成 > 3、漏掉 last_email_open_days_ago > 30、忘了做工单抑制，都会让 customer_id 集合偏离参考，Jaccard 掉分。
  • 丢组件五、六（0.15+0.05）：重叠算错。典型是 overlap_pct 用错分母（拿已有受众的 size 而非 449），或者对 has_cart_abandonment（不存在的列）处理不当而报错/给出非 0，或用剥离 PII 后的 roster 去算 state 相关的 AUD-001 导致算不出。
  • 丢组件一（0.15）：谓词写法与参考不一致。operator 用了非标准符号、value 写成浮点、activation_channels 键名不是 sms/push，都会让对应子项失配。
  • 丢组件二（0.10）：audience_stats 里某个计数偏差超过 2%，或字段名拼错/缺失导致取值为 None。
  • 丢组件四（0.20）：资格列算错，比如 any_channel_eligible 用了"与"而不是"或"，或把 email_opt_out 误当作短信/推送的排除条件。
