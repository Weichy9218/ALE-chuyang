题目做什么

业务背景：母婴类目 owner 在大促前突然离职，其执行 / 协调 / 关键决策 / KPI 兜底四项职责一并空缺。同时叠加三重扰动：能接标准化子任务的 Beauty 同级 owner 临时不在岗；监管方点名一个母婴品牌，触发紧急下架与品牌风险重评的合规子流程；senior lead 对统一决策只有 48 小时 SLA。要求在保留原流程锚点的前提下改写 BPMN，让它能在这四重叠加扰动下正确运转，并交出配套的合规凭证。

题目声明正确答案不唯一：允许三种参考方案指纹（A / B / C）之一，也允许满足全部硬约束的新颖设计。参考答案采用指纹 A（Peer-Owner-Led Committee）。下面按评测器的五个部分与设计维度拆开。

锚点与流程键（原始流程的保留部分）

原始流程 zMBCategoryGovernance_original 有 7 个 userTask，其中四个是 owner 独揽的节点（owner_review_and_approve、owner_coordinates_merchants、owner_handles_exception、owner_result_accountability），改写时拆解掉。必须原样保留、ID 不改的锚点：

  • team_drafts_initial_plan（起点侧锚，指派 mbTeamLead）
  • team_executes_plan（终点侧锚，指派 mbTeamLead）
  • lane logistics_lane 与其中的 logistics_capacity_confirmation（物流，仅通知、不进主决策流）

流程键必须改为 zMBCategoryGovernance_modified_L3（评测器也接受 _A / _B / _C 后缀变体）。原始定义要保持独立、不被覆盖。

18 项结构改造（modification_1..18）

题面把改造清单固定为 18 条，要在 structural_changes.json 里逐条声明。核心几条：职责三分（执行 / 协调 / 关键决策落在至少 3 个不同角色）；新增 team_joint_mature_plan_preparation 成熟计划准备任务替代原粗稿；≥4 因子的多因子判断网关；peer-owner 标准化任务泳道；协调泳道；temporary_unified_decision 统一决策任务；48 小时 timer boundary；有界 senior-lead 升级；上限 3 次的 joint-plan 有界重试；决策→执行→重规划闭环；合规危机子流程；peer 不在岗兜底网关；物流锚定仅通知；A/B 测试 / 免费试用 / 新商入驻子流保留；每个人工改判产 out_rationale；独立终止升级 end event escalation_final_end；每个新排他网关有默认流；并行评审网关。

34 条业务规则（rule_1..30 含子规则 6a/8a/14a/16a）

规则集在 business_rules_L3.md。rule_1..26 是显式规则；rule_27..30 是 context-bound 规则，规则文档只给编号和摘要，权威约束文本藏在四份 stakeholder_artifacts/ 里，必须读文档才能提取。要在 business_rules_compliance.json 的 rules 映射里全部覆盖，共 34 个键。规则间存在真实冲突（如 rule_11 senior 比例上限 与 rule_29 角色分离），必须用顶层 priority_chain 声明冲突解法。

rule_27..30：四份利益相关方文档里的隐藏约束

  • rule_27（regulator_email_thread.md）：合规危机分支上，brand_risk_reassessment_task 必须从 compliance_signal_check 可达，且必须在流程到达 temporary_unified_decision 之前同步完成，不能并行走捷径。
  • rule_28（product_compliance_slack.md）：在 team_drafts_initial_plan 上引入三个默认 true 的 in_* kill-switch 变量 abTestEnabled / freeTrialEnabled / newMerchantAdmissionEnabled，并在下游用排他网关按这三个变量守卫；不能删任务、不能永久置假。
  • rule_29（senior_leadership_memo.md）：temporary_unified_decision 与 senior_lead_expedited_decision 的 assignee 必须是不同角色，senior lead 不能同时当委员会主席和临界升级决策者。
  • rule_30（audit_post_mortem.md + regulator_email_thread.md）：合规子流程里至少一个任务写可写 formProperty complianceHandled（或等效 latch 名），合规危机网关条件引用该变量做再入闸（如 ${!complianceHandled}）。

L3 结构刚性（rule_23..26 与隐藏检查 a37–a51）

这是 L3 相对低层级的加固，用来堵各种“看起来对但运行时会死锁”的取巧。要点：peer 泳道任务名必须覆盖 5 个标准化评审话题（ad_ratio、ab_test、free_trial、new_merchant、review_based_promotion）；每个 peer-topic 任务 2 跳内回溯到并行网关且中间只经网关不经 userTask；gw_peer_available 的 true 分支直连并行 split；不许混合并行网关（既 ≥2 入又 ≥2 出）；并行 join 各入边追溯到同一个 split；split 出边数等于 join 入边数；排他网关默认流必须无条件且至少有另一条带条件的兄弟流；锚点链 draft→joint plan→unified decision→execute 静态逐步可达；senior 升级任务出发的每条路径都终止到 main_end 或 escalation_final_end；gw_decision_outcome 默认流 3 跳内回到重试网关或终止升级；不许有场景不认领的影子 userTask（a50）；每个可写 out_* 输出必须下游被引用（a51）。

三种方案指纹与 L3 层级关系

L3 是 Case 2 的“hardened”层级：相对 Case 1 的唯一解，L3 放开成三个可接受的设计家族，但把结构与合规约束加密到运行时不易蒙混的程度。三种指纹：

  • A：Peer-Owner-Led Committee：peer-owner 泳道承担标准化工作，三人委员会（senior-lead + peer-owner + team-lead）做统一决策，senior 升级只处理顶层问题。
  • B：Senior-Lead-Light Chair：senior lead 用 timer boundary 异步主持，跨类目运营池吸收标准化工作。
  • C：Team-Internal-Committee-Led：内部团队委员会（team lead + BA + merchant ops lead）起草成熟计划，peer owner 只做标准化委派。

参考答案是指纹 A。评测器不强制走指纹：只要 A+B+C+D 四部分都过，就构成 novel-qualifying 通过 Section E（详见评测一节）。

硬性要求

  • 只能用 userTask 承载新增人工工作，不许用自定义 Java delegate；新任务保持类型化 flowable:formProperty 数据流（in_* / out_*）。
  • 网关条件只用变量型 ${...} 表达式，禁止 ${true} / ${false} / ${1==1} 之类恒真恒假（反作弊 d09/d11）；每个引用的变量在网关求值时必须已存在（Flowable 6.5.0 对未定义变量严格报错，不回退）。
  • 每个新排他网关必须有 default 属性，指向唯一一条无条件出流；默认流不得带条件。
  • 每个新 userTask 必须有非空 <bpmn:documentation>。
  • 物流不许碰：不得从主流向 logistics_capacity_confirmation 引入任何 sequenceFlow，不得改其出边，它保持并行、仅通知（rule 8 / 8a）。
  • 成功的异常处理路径要重新汇入主流；最后兜底的升级要送到独立终止 end event escalation_final_end。
  • 不得修改 input/ 下的任何暂存文件；最终产物只写 output/。
  • JSON / md 凭证必须与真正产出的 BPMN 一致，评测器会交叉核对网关条件、因子数、timer 时长、数据流、assignee。
  • 运行时测试把角色 assignee 变量全设为 admin；Flowable REST 基址 http://localhost:8080/flowable-task/process-api/，凭据 admin / test。

用什么评测

评分链路：harness 调 main.py 的 evaluate() → 先确认 5 个必交文件都存在（缺一个直接返回 [0.0]）→ 把五份产物读进临时目录，连同评测方控制的 test_scenarios_L3.json → 调 score_output_bundle() → 取 result["score"] 作为该题分数。

score_output_bundle() 分两步：

  1. 契约预闸 _validate_test_results()：核对 test_results.json 与 manifest。场景 manifest 必须恰好 60 条；结果必须恰好 60 条、id 全在 manifest 内、无重复、category 与 manifest 逐条相符；passed_scenarios 必须等于结果里 pass=true 的计数、total_scenarios=60、pass_rate 与 passed/total 相差 ≤1e-6、anti_gaming 类恰好 5 条、若给了 scenarios_summary 须与逐条统计一致。任一不符直接返回 score=0.0（validation=test_results_contract），连 evaluate_L3 都不跑。
  2. 主评测：把 evaluate_L3 的 evaluate() 跑在结果目录里，返回报告。分数取 report.get("weighted_score", 1.0 if overall_pass else 0.0)。报告不含 weighted_score，所以就是 overall_pass → 1.0 或 否则 0.0。

evaluate_L3 是纯程序化的自包含评测器：用 lxml（缺失时退回 xml.etree）解析 BPMN，自建 BPMNGraph 抽象做拓扑分析，读三份 JSON 和 design_decisions.md 做规则比对。不调用 openai/anthropic/litellm，也不跑隐藏测试套件。overall_pass = all(A,B,C,D,E)，五个部分全过才算过。

run_tests.py 不在自动打分链上。它是给 agent 用来把 60 场景打真实 Flowable 实例、生成 test_results.json 的参考工具（自身用 90% 阈值决定退出码，anti_gaming 场景在其中恒判为 pass、注为“结构检查交给 evaluate_L3”）。真正决定分数的是 evaluate_L3 的 check_test_results，它按 95% 阈值重新判 Section B。两者不冲突：一个正确部署并跑通的 BPMN，60 场景一般能全过。

能力瓶颈：不是单点，是四件事叠在一起

1. 规模与耦合，撞上全有或全无

约 50 个精确、彼此耦合的硬检查，横跨图拓扑、命名、数据流、角色、5 个互相一致的文件；一个没过就是 0。pi_on 实际过了 B、E 两整段、A/C/D 也过了大半，只栽在约 6 个检查上，换算成加权分大概 44/50，却被记成 0。四条各自栽在不同子集，说明这不是“缺某一个能力”，而是模型没法把这么大一组约束同时兜住并一次产对。

2. 隐藏、且被题面自己带偏的约定

评测器在若干处 grep 精确字符串，而这些字符串题面没给全，有一处还自相矛盾。这是四条运行共同的墙：

c11 是最致命的一处，四条 18/18 段全挂，报的都是 no_chosen_approach。评测器要 prose：每段 ## Modification N，正文含 Chosen approach:（正则 chosen\s*approach，中间是空格）、Rejected alternatives:（≥2）、Rationale cites rules: rule_X（须字面有 cites/references rules）、Trade-off:。但题面把这些写成反引号里的下划线形式 chosen_approach。agent 照题面写了 chosen_approach:，正则里“chosen”后要空格、下划线不匹配，于是 18 段全挂。这一个格式坑单独就能把每条运行判 0。参考解用的正是 - **Chosen approach:** … / - **Rationale cites rules:** rule_2, rule_3 的 prose 形式。

同类还有 a23/a24：协调任务名要同时含 merchant+coordination、campaign+coordination（或用参考解确切 ID merchant_readiness_coordination / campaign_cadence_coordination），agent 起了别的名字就匹配不到。c07：每个 modification 要引用真实存在于 BPMN 里的 element ID，agent 在 modification_1（角色拆分）里引用的是角色名/lane 名。这些约定不在可见规格里，不看评测器源码猜不到。

3. 没有反馈闭环

agent 的强项是“改到检查器变绿”。这题把检查器藏了、把运行时也架空了（自报即可过 B），等于让它蒙着眼过 50 道暗门。四条运行没有一条能对着真实评测结果迭代，这是通过率上不去的结构性原因，不是努力能补的。

4. 也有真实的内容缺口

不全是格式坑。a36（合规子流程要在重规划环内且有 latch 可写变量）、a37/a42（并行拆合对称、每个拆分支要有 userTask、无混合网关）、d03（senior 介入 ≤30%）、e07（指纹要有具体那几条有向边）是真正的 BPMN 设计不变式，模型在同时应付其它约束时没兼顾到。它能画出一张看着合理的 BPMN，但兜不住这一整套防死锁的图拓扑。

这题是可解的。把 reference/ 的参考解喂进同一个评测器，五段全过、overall_pass=True（501 行 BPMN、约 34 个 userTask）。所以天花板真实存在，缺的是精确度和对约定的命中，不是这题做不了。

怎样才能做对

分两层：一层是现状下让 agent 尽量过；一层是要真正可解、且能测出模型真实水平，得改任务侧。

A. 对 agent（现状下最大化通过率）

  • 把评测器当规格逆向。题面给了三种参考指纹 A/B/C 和一批精确措辞（“Chosen approach”、“Rationale cites rules”、canonical ID），把这些当硬约定逐字照抄，别按自己的模板起名。
  • 用确切的 canonical ID（merchant_readiness_coordination、campaign_cadence_coordination、temporary_unified_decision…），直接命中 name-fragment / ID 检查。
  • design_decisions.md 用 prose 形式（## Modification N + **Chosen approach:** …），不要用题面那种 snake_case 键；structural_changes.json 每个 modification 至少引一个真实 element ID。这两条单独就能把 C 段从必挂变可过。
  • 增量构建 + 每步自查图不变式：把 13 条不变式（拆/合对称、无混合网关、锚点链连通、升级路径终止、senior 比例 ≤30%…）写成自己的检查脚本反复跑。
  • 但要认清上限：看不到评测器、也没有真运行时反馈的前提下，一道 50 条隐藏约定的全有或全无题，靠盲产加猜，稳定通过基本不可能。

B. 要让这类题真正可解、可测（任务侧，按杠杆从大到小）

  1. 给反馈闭环（最大杠杆）。把评测器（哪怕子集）或一个真正能跑的 Flowable 暴露给 agent，让它 fix-until-green。agent 迭代到检查器变绿的能力远强于一次盲产，这一条能把这类题从“几乎不可能”变成“多轮能收敛”。
  2. 让约定可发现、且和题面一致。chosen_approach vs Chosen approach 这种直接是题面与评测器不一致的 bug，先修掉；把 canonical ID、name-fragment、精确措辞写进规格；把 exact-string 换成语义匹配。
  3. 给部分分。50 条检查的全有或全无既几乎不可赢、也测不出信息——四条都记 0，但 pi_on 实际过了约 44/50。加权分能把“差一点”和“完全不会”区分开。
  4. 降耦合。把 BPMN 拓扑、合规文档、运行时测试拆成独立计分的子交付，避免一个格式错误连坐整题。
一句话。这道题现在测的不完全是“模型会不会设计这套治理流程”，很大一部分是“模型能不能蒙对一批没写在规格里的精确约定”。前者是能力，后者是评测设计。要测前者，得先把后者从盲测改成有反馈、有部分分、约定一致的测法。
