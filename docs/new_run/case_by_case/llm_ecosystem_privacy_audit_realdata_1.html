taskId：business_finance/llm_ecosystem_privacy_audit_realdata_1

题目做什么

输入是对 2253 个真实 GPT Action 的预分类结果。每个 Action 用一个 "<后端域名>, <api_name>" 字符串作 key，值是这个 Action 采集的字段列表，每个字段已经被打上一个 taxonomy 的 data_type 标签。另外给了一份 taxonomy 参考表、OpenAI 政策原文（含一份 Policy-to-Taxonomy 映射指南），以及 3116 个 GPT 到 Action 后端域名的对照表。任务拆成两个互相独立的子任务，各产出一份文件。

子任务 1：政策违规清单 policy_violations.json

遍历 pp_action_data_entities.json 里每个 Action 的每个字段，按政策 markdown 里的映射指南判断这个字段的 data_type 是否构成违规。指南把 taxonomy 数据类型分成两档：

  • CRITICAL（禁止采集）：Passwords、API key、Access tokens、Cryptographic key、Verification code、User payment info、Government ID。任何字段的 data_type 落在这个集合，就是一条 CRITICAL 违规。
  • HIGH（敏感，需在隐私政策中披露）：Health info、Fitness info、Medical record、Purchase history、Other financial info、Income information、GPS coordinates、Precise location、Exact address、Emails、Voice or sound recordings、Race and ethnicity、Sexual orientation、Political or religious beliefs。指南明确说这道题不要求核对每个 GPT 是否真有隐私政策披露，凡采集这些类型一律标 HIGH。

指南还有一档「无违规类型」：Name、Email address、User IDs、Settings or parameters、Time、Approximate location 等其余全部 taxonomy 类型都不算违规。注意这里的一个陷阱：Address（近似地址，206 个字段）不在 HIGH 里，只有 Precise location 和 Exact address 才算；Email address（邮箱地址本身）不算，只有 Emails（邮件正文内容）算。

违规按「一个字段一条」记录。每条至少要有 severity、policy_clause、action_domain、api_name、data_field_name、data_type 六个字段。缺 policy_clause 或 action_domain 的条目会在打分前被丢弃。

子任务 2：跨域数据放大报告 cross_domain_exposure_report.csv

一个后端域名可能被很多不同的 GPT 共用（例如 actions.zapier.com 被 237 个 GPT 用）。这一步统计每个「被至少 3 个不同 GPT 共用」的后端域名，把它上面所有 Action 采集的数据类型聚合起来，算一个放大系数，衡量单个后端聚拢了多少种数据。表头必须逐字是：

domain,gpt_count,action_count,avg_datatypes_per_action,union_datatypes_count,amplification_factor,union_datatypes

每列的定义：

  • gpt_count：从 gpt_action_metadata.json 数，有多少个不同的 GPT（按 gpt_id 去重）用到这个后端域名。只有 gpt_count ≥ 3 的域名才进表。
  • action_count：pp_action_data_entities.json 里落在这个域名上的 Action 数。
  • avg_datatypes_per_action：这个域名上每个 Action 采集的不同 data_type 数量的均值。
  • union_datatypes_count：这个域名上所有 Action 采集的不同 data_type 去重后的总数。
  • amplification_factor：字符串 f"{round(union_datatypes_count / avg_datatypes_per_action, 3)}x"，即三位小数的数值加一个 x 后缀。
  • union_datatypes：这些不同 data_type 按字母序排序、用分号分隔的列表（参考答案用的是 "; " 分号加空格）。

两个容易被隐藏参考答案掀翻的约定，详见后面「怎么评测」和「失分的典型形态」：一是没采集任何数据的空 Action（字段列表为空）不计入 action_count，也不进 avg 的分母；二是 amplification_factor 用未取整的 avg 计算，而 avg_datatypes_per_action 列本身是取整到 2 位小数显示的。

两个子任务用的是同一批数据，但计算互不依赖：子任务 1 只看字段的 data_type 和政策映射，子任务 2 只做域名维度的聚合统计。

硬性要求

  • 只用 Python 3 标准库 json、csv、re、collections 解析四个输入文件，不用第三方包。要脚本化就走 software/python 入口。
  • 把政策 markdown 里的 Policy-to-Taxonomy 映射指南逐字照用，它是从 data_type 到 CRITICAL / HIGH 的权威映射，参考答案就是用它生成的。
  • taxonomy.csv 以 UTF-8 BOM 开头，要用 encoding="utf-8-sig" 打开。
  • pp_action_data_entities.json 的 key 是 "<domain>, <api_name>"，用 ", "（逗号加一个空格）分隔。只在第一个 ", " 处切分，因为有些 api_name 里含逗号（数据里有 13 个这样的 key，例如 "ai.zxtcode.com , Stock, fund, and index data"）。
  • 不得修改 input/ 下任何文件；只写 output/。
分隔符还有一个细节。数据里 key 的实际写法是 "域名 , api_name"（逗号两边都有空格）。按题面说的在第一个 ", " 处切分，左半会带一个尾随空格（例如切出 "ai.mrc.fm "）。参考答案里的 action_domain 和 CSV 的 domain 都是去掉首尾空格后的值，所以切出来后要 strip()。子任务 2 要把这个去空格后的域名和 gpt_action_metadata.json 里的 domain（本身不带尾随空格）对上，不去空格就对不上。

用什么评测

评分链路在 main.py 的 evaluate()：从 VM 读回 agent 的两份产物和两份隐藏参考文件，其中任一读不到就返回 [0.0]；把 agent 的 policy_violations.json 解析成 JSON（解析失败返回 [0.0]，走 zero_report）；然后调用 score_outputs.py 的 score_submission(policy_agent_json, policy_ref_json, exposure_agent_text, exposure_ref_text)，取返回的 report["overall_score"] 作为最终分。CSV 是以原始文本传入的，评分器内部用 csv.DictReader 解析。

这是纯程序化打分：对照隐藏参考答案做集合与数值比对，没有 LLM 裁判，也没有隐藏测试套件。总分由两个子任务的通过 / 不通过决定：

情形总分
两个子任务都通过1.0
恰好一个通过0.5
都不通过0.0

overall_score = (sub1_score + sub2_score) / 2，两个子分各是 1.0 或 0.0。硬失败（任一产物缺失或读不出、agent JSON 非法、agent CSV 结构坏、或任何 gpt_count ≥ 3 的参考域名在 agent CSV 里缺失）会让对应子任务判 0 或整个评测返回 0.0。

怎么评测

评分脚本 score_outputs.py 的四个阈值常量：CRITICAL_RECALL_THRESHOLD = 0.85、OVERALL_PRECISION_THRESHOLD = 0.75、AMP_RELATIVE_TOLERANCE = 0.05、AMP_COVERAGE_THRESHOLD = 0.95。下面逐条拆开两个子任务的判据，照着自查即可。

子任务 1：score_policy_violations

先把 agent 的每条违规「有效化」：只保留同时有非空 policy_clause 和非空 action_domain 的 dict 条目（_has_citations）。然后给每条算一个比对 key：

_violation_key = (
    severity.strip().upper(),   # 归一化大小写
    action_domain.strip(),
    api_name.strip(),
    data_field_name.strip(),
    data_type.strip(),
)
关键点：policy_clause 不进比对 key。它只在有效化那一步被检查「是否非空」。也就是说 agent 写的政策条款文字不必和参考答案逐字相同，只要非空就行。参考答案里 policy_clause 用的是 7 种合成串（如 "Prohibited Data Collection — passwords"、"Sensitive Data Requiring Disclosure — Financial information"），但你不需要复刻它们。真正要和参考对上的是 severity、action_domain、api_name、data_field_name、data_type 这五项。

把 agent 有效条目和参考条目各自用 Counter 按 key 计数，逐 key 取 min(agent_count, ref_count) 作为真正例（TP）。然后：

判据阈值 / 条件不满足的后果
CRITICAL 召回recall_critical = tp_critical / ref_critical ≥ 0.85。参考 CRITICAL 共 41 条，需 tp_critical ≥ 35。正确报出的 CRITICAL 少于 35 条 → 召回不达标 → 子任务 1 不通过。
总体精确率precision = tp_total / reported_valid ≥ 0.75。reported_valid 是 agent 全部有效条目数。有效条目里 TP 占比不足 75%（即误报太多，把非违规字段也报进来）→ 精确率不达标 → 子任务 1 不通过。
agent 结构violations 必须是 list，条目是 dict。缺失或结构错 → 直接返回 passed=False。
子任务 1 是否通过两个条件同时满足：recall_critical ≥ 0.85 且 precision ≥ 0.75。任一不满足 → 子任务 1 记 0 分。

severity 是 key 的一部分：把 Passwords 字段错标成 HIGH，会导致它对不上参考里的 CRITICAL key，既拿不到 CRITICAL 的 TP，又白占一个有效条目拉低精确率。

子任务 2：score_cross_domain

用 csv.DictReader 分别读 agent CSV 和参考 CSV，把每行的 domain（去空格）映射到解析后的 amplification_factor（_parse_amplification 去掉末尾的 x / X 再转 float，转不出记 None）。只比对 domain 和 amplification_factor 两列，其余列（gpt_count、action_count、avg_datatypes_per_action、union_datatypes_count、union_datatypes）评分器根本不看。

判据阈值 / 条件不满足的后果
硬闸门：域名覆盖参考里全部 130 个域名都必须出现在 agent CSV 里（set(ref) - set(agent) 为空）。只要缺一个参考域名 → hard_gate_passed=False，子任务 2 直接判 0，不再看放大系数。
放大系数容差对每个「agent 报了且在参考里」的域名，参考系数非 0 时需 abs(agent_amp - ref_amp) / abs(ref_amp) ≤ 0.05（相对误差 5%）；参考为 0 时要求 agent 也为 0。超差的域名不计入 within。agent 系数为 None（解析不出）也算超差。
覆盖率tolerance_ratio = within / evaluated ≥ 0.95。evaluated 是 130（overlap），需 within ≥ 124。达标域名少于 124 个 → 子任务 2 不通过。
多报域名不扣分。容差循环只遍历「同时在参考里」的域名，agent 多报的域名（例如那 7 个 gpt_count ≥ 3 但在参考里被剔掉的域名）会被跳过，既不进 evaluated 也不影响覆盖率。所以就算把它们也写进 CSV，也不会拖垮子任务 2，只要 130 个参考域名都在、且放大系数对得上。

失分的典型形态

  • 高危 子任务 2 把空 Action 计进 avg。如果 action_count 和 avg 的分母把字段列表为空的 Action 也算上，放大系数会系统性偏小。实测下有 27 个域名的系数因此超出 5% 容差，覆盖率掉到 103/130 ≈ 0.79，低于 0.95，子任务 2 直接判 0。这是这道题最容易踩、也最致命的一处。
  • 高危 漏掉任一参考域名。子任务 2 是硬闸门，130 个参考域名缺一个就整块判 0。常见原因是把 gpt_count ≥ 3 的门槛算错，或域名去空格 / 大小写没和 gpt_action_metadata 对齐。
  • 易错 把 severity 判错。severity 进比对 key，Passwords / User payment info 必须标 CRITICAL，其余敏感类型标 HIGH。标错档位会同时伤害 CRITICAL 召回和精确率。
  • 易错 误报无违规类型。把 Address、Email address、Name、Approximate location 这类无违规类型也报成违规，会拉低精确率。误报到一定量（有效条目里 TP 占比跌破 75%）就丢子任务 1。
  • 易错 忘了填 policy_clause 或 action_domain。缺任一者的条目在打分前被丢弃。如果 CRITICAL 条目因此被丢，会直接压低 CRITICAL 召回。
  • 易错 key 切分错误。用 ", " 只切第一处、并去掉首尾空格；含逗号的 api_name（13 个）若整体切错，action_domain 和 api_name 都会对不上参考 key。
  • 提示 data_field_name 的宽容度。参考里字段名有时用原始参数名（如 volume、stopLoss），有时用描述名（如 body weight），并不完全一致。但即便用某一种规则导致约 48 个 HIGH 字段名对不上，精确率仍有约 0.91、CRITICAL 召回仍是 1.0（41 个 CRITICAL 字段的原始名与描述名一致），子任务 1 照样通过。也就是说字段名不是这题的主要失分点，前面几条才是。
  • 高危 产物损坏或缺失。JSON 解析不出、CSV 结构坏、文件没写到 output/，会让对应子任务判 0，严重时整评测返回 0.0。
