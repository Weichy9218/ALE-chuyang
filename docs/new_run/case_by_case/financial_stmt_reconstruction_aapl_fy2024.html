Apple FY2024 合并资产负债表重建

taskId：business_finance/financial_stmt_reconstruction_aapl_fy2024

从苹果公司 FY2024 的 Form 10-K 里抽出截至 2024 年 9 月 28 日的合并资产负债表，按给定 schema 写成 output/balance_sheet.json；打分脚本把 JSON 里 30 个数值字段逐一和隐藏参考答案做精确比对，得分是对的字段占比，元数据不对则直接 0 分。

题目做什么

只有一个变体，没有难度分层。agent 扮演财报抽取分析师，把苹果 FY2024（会计年度截至 2024 年 9 月 28 日）的合并资产负债表还原成结构化 JSON。整个工作可以拆成三步。

阶段一：定位 FY2024 合并资产负债表

输入里给了同一份 10-K 的两种形态：PDF（aapl-2024-10k.pdf）和 SEC EDGAR HTML（aapl-20240928.htm）。要在其中找到标题为 “CONSOLIDATED BALANCE SHEETS” 的那张表。这张表有两列，左列是本期 September 28, 2024，右列是上一年 September 30, 2023。task.json 明确目标列是 September 28, 2024，只取这一列。

可用的工具是 pdftotext 把 PDF 转文本，再用 grep 定位关键行；或直接解析 HTML。软件封装脚本只是把命令转发给系统里的 /usr/bin/python、/usr/bin/pdftotext、/usr/bin/grep。

阶段二：逐字段抽取数值

按 output_schema.json 的字段清单，从该表本期列抄出每一项，单位是 USD 百万（millions），照报表原样填，不四舍五入、不估算、不换算单位。字段分三大块：

  • 资产：流动资产 7 项（现金及等价物、短期有价证券、应收账款净额、非贸易应收款、存货、其他流动资产、流动资产合计），非流动资产 4 项（长期有价证券、不动产厂房设备净额、其他非流动资产、非流动资产合计），以及总资产。
  • 负债：流动负债 6 项（应付账款、其他流动负债、递延收入、商业票据、一年内到期的定期债务、流动负债合计），非流动负债 3 项（长期定期债务、其他非流动负债、非流动负债合计），以及总负债。
  • 股东权益：普通股与额外实收资本合计、每股面值、授权股数（千股）、已发行并流通股数（千股）、累计赤字、累计其他综合损失、股东权益合计，以及末尾的负债与股东权益总计。

注意几个容易抄错的点：每股面值是 0.00001 美元（报表写作 $0.00001），授权与流通股数在 schema 里以“千股”为单位（shares_authorized_thousands = 50,400,000，即 504 亿股；shares_issued_and_outstanding_thousands = 15,116,786）。累计赤字和累计其他综合损失是负数（分别为 -19,154 和 -7,172）。

阶段三：组装成 schema 规定的 JSON 并写出

顶层要有 metadata 和 consolidated_balance_sheet 两个对象，键名与嵌套层级必须和 schema 完全一致（打分靠点分路径匹配，键名错一位这条就算错）。写到 output/balance_sheet.json。所有中间产物和最终文件只能放在 output/ 下，不能改动 input/ 里的任何文件。

打分脚本也接受一种简化形态：顶层直接给 assets、liabilities、shareholders_equity 三个键（不套 consolidated_balance_sheet），脚本会自动包装。但简化形态下仍要显式给出 period（或 period_of_report）和 currency，否则元数据校验会失败。

硬性要求

  • 只交一个文件 output/balance_sheet.json。
  • 单位用报表原样的 USD 百万，不四舍五入、不估算、不换算单位。
  • 只取截至 2024 年 9 月 28 日这一列，不能用 2023 年那一列的数。
  • JSON 必须同时包含 metadata 对象和 consolidated_balance_sheet 对象，且包含 schema 里的每一个键。
  • 不得修改 input/ 下任何文件；草稿和最终输出只放在 output/ 下。
  • 允许使用的工具是基线 Linux 工具：Python、pdftotext、grep，不需要也不允许账号门控或付费软件。
  • 输出目录名受限：REMOTE_OUTPUT_DIR 必须是 output / output_test_pos / output_test_neg 之一，或以 output_admin_ 开头；默认是 output。

用什么评测

main.py 的 evaluate() 是打分入口，链路如下：

  1. 先确认参考文件 reference/aapl_fy2024_balance_sheet_reference.json 存在，不存在直接返回 [0.0]。
  2. 把 scripts/score_outputs.py 的内容写到 VM 的 /tmp/agenthle_eval/…/score_outputs.py，然后执行：
    python score_outputs.py --output <remote_output_dir> --reference <reference_dir>。
  3. 脚本把打分报告以 JSON 打到 stdout。若进程返回码非 0，evaluate() 返回 [0.0]。
  4. 否则解析 stdout，取 report["score"] 作为最终分：return [float(report.get("score", 0.0))]。

这是纯程序化打分，对照隐藏参考答案做数值精确比对，没有 LLM 裁判，也没有 pytest 式隐藏测试套件。

只有 score 进入最终分。脚本还算了 pass_fail（要求无错误、三个顶层合计都对、且字段准确率 ≥ 0.95），但 evaluate() 只取 score 字段，pass_fail 不影响 harness 得分，只是报告里的参考信息。

分值映射：得分 = 正确的数值字段数 ÷ 30（accuracy = correct / total），是 0.0 到 1.0 的连续值。但只要 errors 列表非空（元数据或结构任一项不合格），得分就被硬置为 0.0：score = float(accuracy) if not errors else 0.0。

怎么评测

score_outputs.py 的判据分“硬门槛”和“逐字段计分”两层。任一硬门槛不过，全局 0.0；过了硬门槛后按对的字段占比给分。

比对细节：

  • 路径匹配。numeric_leaves() 递归遍历 consolidated_balance_sheet，用点分路径（如 assets.current_assets.cash_and_cash_equivalents）作键。提交和参考用同一套遍历，所以键名或嵌套错一处，这条路径就对不上，算错。
  • 数值容差。没有容差，是 Decimal 精确相等。整数差 1、正负号错、单位错（比如把 152,987 写成 152987000000）都算错。
  • 格式宽容度。叶子值可以是数字或字符串；字符串先 .replace(",","").strip() 再转 Decimal，所以 "152,987" 和 152987 等价。布尔值被忽略（不计入叶子）。每股面值 0.00001 与 1e-05 在 Decimal 下相等。
  • 多余键不扣分。提交里比参考多出来的路径记入 extra_paths，不影响得分；只有参考里的 30 个路径参与计分。
  • 顶层合计单独跟踪。后缀为 total_assets / total_liabilities / total_shareholders_equity 的字段会汇入 top_level_totals_correct，它只影响 pass_fail，不改变 score。
  • 两种可接受形态。顶层带 consolidated_balance_sheet 的完整形态，或顶层直接给 assets/liabilities/shareholders_equity 的简化形态（脚本 normalize_submission 会补包一层元数据）。两者都不匹配时，submission_bs 为 None，判为结构错 → 0.0。

据此可自查：先保证 metadata 五项全对（否则一律 0），再核对 30 个数值。字段准确率 ≥ 0.95（即至少 29/30 对）且三个顶层合计都对时 pass_fail 为真，但 harness 分只看准确率本身。

失分的典型形态

  • 元数据一处错，全盘归零。company/ticker/period_of_report 写得和参考不一致（比如公司名写成 “Apple”、日期写成 “2024-9-28” 或 “September 28, 2024”），或 currency 不在 {USD, USD_millions}、unit 不在 {millions, USD_millions}，errors 非空后即使 30 个数全对也是 0.0。
  • 没写 metadata 或 consolidated_balance_sheet。缺 metadata 报“must be present”，缺 consolidated_balance_sheet（且未用简化三键形态）判结构错，都直接 0.0。
  • 键名或层级不对。把 property_plant_and_equipment_net 写成 ppe_net、把某项放错父节点，点分路径对不上，这些字段全记为错。
  • 取错列。抄了 2023 年 9 月 30 日那一列的数，几乎所有字段都对不上参考的 2024 值。
  • 单位或量纲错。把百万当成元展开（152,987 → 152,987,000,000），或股数没按“千股”填（把 50,400,000 千股写成 50,400,000,000 股），Decimal 精确比对下算错。
  • 正负号漏掉。accumulated_deficit 和 accumulated_other_comprehensive_loss 是负数，写成正数即错。
  • 每股面值写法。面值目标是 0.00001，写成 0（丢精度）或 0.0001 都算错；0.00001 与 1e-05 等价可以接受。
  • 把文件写错位置。输出不在允许的目录名下、文件名不是 balance_sheet.json，脚本找不到即“missing required output”，0.0。
  • 个别数字抄错。这类只按比例扣分，每错一个丢 1/30 ≈ 0.033，不会归零（前提是元数据和结构都过关）。
