题目做什么

原流程（original_process.bpmn20.xml）是 LY Juice 月度排产的五步线性流程：销售需求分解 → 生产排程 → SKU 排序 → 供应链 Lead 综合确认产能 → 月度计划确认后并行下发采购与工厂执行。它假设季度 S&OP 之后关键原料基本有保障，且到货即合格。本题设定这两个假设同时失效（原料短缺 + 来料质量暂扣），要求把流程改造成能处理这类复合中断的版本。改造由 L1、L2、L3 三层难度叠加，评测脚本也是三层叠加：L3 的检查建立在全部 L1 与 L2 检查之上。

层与层的关系

三个评测脚本不是三套独立评测，而是一条继承链，最终只跑 L3：

  • L1（evaluate.py）：定义 11 个原始锚点元素（startEvent、task_salesDemand、task_productionSchedule、task_skuSequencing、task_capacityConfirmation、task_monthlyPlanConfirmation、task_procurementExecution、task_factoryExecution、gw_parallel_split、gw_parallel_join、endEvent），用锚点加拓扑遍历识别新增节点，给出结构检查 1 到 14、反作弊 D1 到 D3、合规（9 项修改 + 10 条规则）、场景、数据流 E1 到 E4、角色耦合 F1 到 F5。
  • L2（evaluate_L2.py）：改用基于属性（assignee、candidateGroups、节点名）的发现函数 discover_L2_chain，重新识别 L1 与 L2 全部节点（因为插入质量门后 L1 的位置式 BFS 会错认），重跑结构检查 1 到 14 并追加 15 到 22（质量门），反作弊追加 D8 到 D10，合规扩到 15 项修改 + 16 条规则，数据流追加 E5 到 E7，角色追加 F6、F7。
  • L3（evaluate_L3.py）：结构追加 check_25/27/28/29/31，反作弊追加 D11 到 D16（含路径敏感性行为分析），合规扩到 18 项修改 + 22 条规则并加交叉校验 30/32/33，另有不计分的加分项 D17/D18/check_23。数据流 E 段与角色 F 段直接复用 L2 版本，L3 未再扩展。

因此 agent 的目标是一个能同时满足 L1、L2、L3 全部要求的 BPMN。下面按子任务拆开。

供应风险与替代寻源（L1 主链）

在 task_skuSequencing 之后插入采购可用性确认任务（Procurement Lead），产出 supplyRiskDetected。接一个供应风险排他网关：无风险直接回主链的产能确认；有风险走替代寻源任务（Procurement Lead），产出 sourcingSuccessful。寻源结果网关：寻源足够回主链，不足则进入产品组合调整路径。所有异常处理成功后必须重新汇入主流程（闭环），不能自己新开一个结尾。

质量检验三档门（L2 主链）

寻源解决之后、产能评估之前，插入质量检验任务（QA Lead），产出材料等级 out_material_grade（A / B / C 枚举）。接质量等级网关，三条分支：

  • Grade A：合格，直接进产能确认。
  • Grade B：部分合格，需 QA Lead 与供应链 Lead 联合豁免审批（task_gradeBWaiver），产出豁免决定 out_waiver_decision 和理由 out_rationale。批准则走材料限制文档任务（把限制传给下游组合调整），驳回则并入调整合并网关。
  • Grade C：不合格，等同寻源失败，直接并入调整合并网关（作为第三个触发源）。

质量检验任务上挂 48 小时中断型定时器边界事件（PT48H，cancelActivity=true）：超时则取消检验任务，转到加急质量决定任务（供应链 Lead），产出 out_expedited_decision（ACCEPT / REJECT / ESCALATE）加理由，再经加急评估网关分别汇回主链、进调整或升级。

成本方差门（gw_costVariance）：替代寻源导致成本方差超预算 15% 时，转 Finance Controller 复核；不超则采购团队自行放行。L3 的规则 21 进一步要求分档，超 25% 触发高管升级，门条件必须用数值比较（${out_cost_variance > 0.15}、${out_cost_variance > 0.25}），不能用布尔标志。

组合调整、并行审批与再验证防环（L1 到 L3 交汇）

产品组合调整由供应链 Director 提出（task_productMixAdjustment）。三个触发源（寻源失败、产能判定需调整、Grade C 拒收）经一个包容网关（inclusiveGateway gw_adjustmentMerge）汇聚后进入组合调整，这体现规则 8a 的多触发条件可任意叠加。

调整后先做产能预验证，通过后进入并行审批：并行分叉网关同时开供应链 Director 复核（产出 scApprovalResult）和销售 Director 渠道确认（产出 salesAccepted）两条独立分支，合并网关之后由审批决定网关用 ${scApprovalResult == true && salesAccepted == true} 决定：都通过则设再验证标志后回产能确认，任一驳回则升级。

再验证防环（规则 10）：task_setRevalidationFlag 设 isRevalidation=true 后回产能确认；产能判定网关用该标志区分首轮与再验证，再验证时若仍需调整则直接升级高管，不再回组合调整。

L3 追加有界循环（规则 18 的循环语义）：组合验证网关 gw_mixValidation 用计数器 mixRetryCount 约束重试，条件如 ${mixRetryCount < 3 && !mixValidationPassed} 回退重试、${mixRetryCount >= 3} 达上限升级。L3 还要求组合调整任务跨车道取数：至少消费来自 QA 车道（in_material_restriction）和采购车道（in_sourcing_result）的输入。最后的高管升级是最后手段，必须走一个单独的终止结尾事件（参考答案里是 endEvent_escalation），与正常 endEvent 分开。

用什么评测

打分链路：main.py 的 evaluate() 先确认四份必交文件都存在，缺任一即 return [0.0]。存在则把四份文件读到临时目录，调用 score_output_bundle(bpmn_path, structural_path, rules_path, results_path)。该包装器按 evaluate.py → evaluate_L2.py → evaluate_L3.py 顺序 import，再调用 evaluate_L3(args)，返回 report.get("weighted_score", ...) 作为 score。evaluate() 最终 return [float(result.get("score", 0.0))]。整个过程纯程序化，无 LLM，不重跑 Flowable，不重放场景。

分数是连续加权分，不是二值。task_card 的 evaluation 文字说"全部段通过才 1.0，否则 0.0"，但 score_output_bundle.py 实际返回 weighted_score，即六段按权重加权、段内按通过比例的连续分。overall_pass（六段全通过）会一并算出，但它不影响返回给 harness 的分数。

六段权重与段内得分算法（_compute_weighted_scores 与 _SECTION_WEIGHTS）：

段权重段内得分算法该段"通过"（计入 overall_pass）的条件
A 结构拓扑0.30通过的布尔检查数 ÷ 布尔检查总数全部布尔检查都通过
B 测试场景0.25pass_rate = 通过场景数 ÷ 总场景数total_scenarios==67 且 key 匹配 且 通过数 ≥ 61
C 合规覆盖0.15(结构 key 覆盖率 + 规则 key 覆盖率) ÷ 2两个覆盖率都为 100%
D 反作弊0.10checks 字典里为 True 的布尔数 ÷ 布尔总数ag_pass 指定的一组检查全为 True
E 数据流0.10E1 到 E7 里为 True 的布尔比例E1 到 E7 全通过
F 角色耦合0.10F1 到 F7 里为 True 的布尔比例F1 到 F7 全通过

B 段用于加权的是原始 pass_rate，与 meets_threshold 无关；哪怕 total 不是 67，加权仍按 pass_rate 给分，但该段不计入 overall_pass。E、F 两段调用的是 L2 版本函数，L3 未扩展。

怎么评测

B 测试场景（权重 0.25）

check_test_results 读 test_results.json：取 scenarios（或退而取 results）数组，逐条判 pass（或 passed/status）。段内得分 = 通过数 ÷ 总数。计入 overall_pass 需同时满足 total==67、key 匹配、通过数 ≥ 61（min_passed_scenarios）。评测不验证 actual_path 是否真实，只信 pass 布尔。

C 合规覆盖（权重 0.15）

check_compliance_L3：结构覆盖率 = structural_changes.json 里出现的 modification_1..18 key 数 ÷ 18；规则覆盖率 = business_rules_compliance.json 里出现的必需 rule key 数 ÷ 22（必需集是 rule_1..7、rule_8a、rule_9..22）。段内得分 = 两覆盖率均值。

C 段只查 key 是否存在，不查 JSON 内容与 BPMN 是否一致。交叉校验 check_30（rule_17 结构匹配）、check_32（成本阈值单调）、check_33（覆盖任务有 rationale 输出）会被计算并打印，但既不进 C 段得分也不进 overall_pass。task_prompt 宣称"评测会交叉校验文档与 XML"，实际打分不依赖这些校验结果。

D 反作弊（权重 0.10）

check_anti_gaming_L3 = L1（D1 到 D3）+ L2（D8 到 D10）+ L3（D11 到 D16），约 15 个布尔项，段内得分按 True 比例。逐项：

失分的典型形态

  • 直接 0 分四份必交文件缺任一，evaluate() 立即返回 0.0；或 BPMN 解析失败（XML 语法错）。
  • B 段大跌test_results.json 顶层数组不叫 scenarios、场景缺 pass 字段、total_scenarios 不是 67、或通过数 < 61：B 段 pass_rate 直接受损，且不计入 overall_pass。
  • A 段连锁改坏或删掉任一原始 ID，original_elements_preserved 失败，并让锚点式与属性式节点发现失效，一连串结构检查跟着 FAIL。
  • 发现失效新增节点用 serviceTask 或没写 assignee/candidateGroups/名字关键词，discover_L2_chain 认不出，对应结构、数据流、角色检查全掉。
  • D 段扣分网关条件硬编码、缺默认流、新任务没写足够长的 documentation、定时器不是 PT.. 或非中断型、存在死分支或到不了 endEvent 的分支、两组对照变量走同一条路径（d13）。
  • E 段扣分in_* 在拓扑前驱上找不到匹配 out_*；漏了原始 out_* 属性；质量/限制/成本三条数据链任一断裂。
  • C 段扣分两份 JSON 少写任一 modification_k 或 rule key（尤其漏 rule_8a 或误写成 rule_8），覆盖率不到 100%，C 段拿部分分且不计入 overall_pass。
  • 时序/循环定时器到加急决定之间插了中间用户任务使 BFS 距离 > 2（check_31 掉）；组合验证网关条件不含计数变量、或没有向升级的出口（check_27/28 掉）；组合调整只从单一车道取数（check_29 掉）。
  • 不直接失分但值得注意覆盖任务的 rationale 输出（check_33）、成本阈值单调（check_32）、rule_17 结构匹配（check_30）都只打印不计分；加分项 D17/D18/check_23 也不影响总分。把精力先放在真正加权的 A/B/C/D/E/F 判据上。
