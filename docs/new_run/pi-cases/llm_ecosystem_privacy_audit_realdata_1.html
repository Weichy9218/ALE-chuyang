题目本身

在无网络的 Linux VM 上，依据 OpenAI GPT Actions Usage Policy（含 Policy-to-Taxonomy 映射指南）对 2,253 个 GPT Action 做隐私合规审计。需产出两份文件：output/policy_violations.json（逐字段列出违规项及严重级 CRITICAL/HIGH）与 output/cross_domain_exposure_report.csv（对被至少 3 个不同 GPT 使用的每个后端域，给出跨域数据放大报告）。全部输入本地只读，仅允许用 Python 标准库（json/csv/re/collections）解析。

要求

policy_violations.json 须含 total_violations、severity_breakdown{CRITICAL,HIGH}、violations 列表；每条须带 severity/policy_clause/action_domain/api_name/data_field_name/data_type，缺 policy_clause 或 action_domain 的条目在评分前被丢弃。cross_domain_exposure_report.csv 表头固定为 domain,gpt_count,action_count,avg_datatypes_per_action,union_datatypes_count,amplification_factor,union_datatypes；仅收录被 ≥3 个不同 GPT 使用的域，amplification_factor 为字符串 f"{round(union_datatypes_count/avg_datatypes_per_action,3)}x"，union_datatypes 为分号分隔、字母序去重列表。键格式 "<domain>, <api_name>" 按首个 ', ' 切分（域名会带尾空格，需 strip），taxonomy.csv 为 UTF-8 BOM。

评测方法

scripts/score_outputs.py：overall_score = (sub1_score + sub2_score) / 2.0，两个子任务各自二值 0/1，故 0.5 恰表示“一过一挂”。sub1 score_policy_violations：violation key = (severity, action_domain, api_name, data_field_name, data_type)——注意 policy_clause 不在 key 内，仅需非空即可通过 _has_citations；通过条件 = recall_critical ≥ 0.85（CRITICAL_RECALL_THRESHOLD）且 precision ≥ 0.75（OVERALL_PRECISION_THRESHOLD），recall 只查 CRITICAL、无整体召回门槛。sub2 score_cross_domain：先硬门槛——参考中任一 domain 在提交里缺失即直接判负；否则对交集域比较 amplification_factor，|a-r|/|r| ≤ 0.05（AMP_RELATIVE_TOLERANCE）算命中，tolerance_ratio = within/evaluated 需 ≥ 0.95（AMP_COVERAGE_THRESHOLD）。除 amplification_factor 外，avg、union、分隔符格式、排序、多余行均不参与打分。

模型执行过程（逐帧）

OFF（38 步）与 ON（22 步）路径相似：先并行读四份输入，发现 key 含 ' , '（域名带尾空格）与部分 action 的值为空列表；随后写/内联脚本聚合。两者产出的 policy_violations.json 逐字节相同（均 144022 字节，total=544、CRITICAL=41、HIGH=503）。CSV 上 OFF 按域名字母序输出 131 行、剔除 6 个在 pp 中 0 动作的域（step[15] 'eligible 137 missing from pp 6'，step[35] 'report_rows 131'）；ON 输出 137 行、把这 6 个 0 动作域也以 '…,0,0.0,0,0x' 写入（step[19] 'report_rows 137 zero_action_rows 6'）。关键一致点：两者的 action_count 都按“该域下 pp 里的全部 key 数”计算，均未剔除值为 [] 的空 schema 动作。两版都做了输出自检（OFF step[37] 打印文件字节/计数，ON step[20-21] 校验非空表头与行数）。

哪里做错了

失分全在 sub2。用真实 scorer 复算：两个 run 都是 sub1=1.0（recall_critical=1.0、precision=0.9117647=496/544）、sub2=0.0（硬门槛通过、missing_count=0，但 within_tolerance=103 / evaluated_overlap=130，tolerance_ratio=0.792 < 0.95）。27 个域的 amplification 超差，根因完全相同：agent 把值为空列表 [] 的 action（收集 0 个数据字段）也计入 action_count，抬高分母、压低 avg_datatypes_per_action，从而放大 amplification=union/avg。参考只统计“至少有 1 个数据字段条目”的非空 action。实例：api.example.com 下 3 个 key 中 'api.example.com , PyPilot Shopping Trends API' 与 'api.example.com , 예시 API' 的值为 []，参考 act=1/amp=1.0x，agent act=3/amp=3.0x；pokeapi.co 参考 act=2/amp=2.0x vs agent act=5/amp=5.0x；gpt-wallet.link 参考 act=22/amp=1.089x vs agent act=30/amp=1.485x；gpts.webpilot.ai 参考 act=3/amp=1.125x vs agent act=4/amp=1.5x。所有 27 例 union_datatypes_count 均与参考一致，唯 action_count 被空动作污染。

怎样才能做对

计算 action_count 与 avg_datatypes_per_action 时，只计入该域下“非空”的 action（len(pp[key])>0），即真正收集了数据字段的动作。以此规则离线复算，130/130 行的 amplification_factor 与参考精确一致（现行“计全部 key”规则仅 102/130 精确一致）。这本质是对题面 “Actions … that appear in pp_action_data_entities.json” 的语义把握：字面可读作“文件里出现的所有 key”（agent 的读法，可辩护），但参考取“实际收集了数据字段的动作”——题面确有歧义，但数据里成片的空 [] 是明显信号，谨慎实现应排除空 schema 动作。sub1 已稳过（precision 0.912 远高于 0.75、41 个 CRITICAL 全中），无需改动；其 48 个 precision 失配仅因 data_field_name 取值差异（agent 用 title 如 'order volume'/'stop loss price'，参考用 data_name 如 'volume'/'stopLoss'），不改变判定。

harness（ON）的效应

ON 相对 OFF 唯一行为差异是把 6 个 0 动作域也写进 CSV（137 vs 131 行），policy_violations.json 逐字节相同，sub 分数完全一致（sub1 过、sub2 的 tolerance_ratio 均为 0.792）。sub2 硬门槛只查“参考域是否缺失”，多写的行既不加分也不减分，故分数 0.5→0.5 未变。ON 追加的镜像提示（M1 预算 / M2 文件存在非空 / M3 对照 input 内 staged reference 迭代重算 / M4 防重复）在此均冗余或不适用：OFF/ON 都已自查输出文件行数与非空；M3 根本不会触发——参考文件位于 base/reference（隐藏，reference_dir），不在 input，模型没有可对照重算的 self-check。真正的 bug 是对 action_count 的语义误读，任何“镜像式只复述任务状态”的提醒都无法纠正，因此 ON 无从修复也未改变分数。
