题目本身

让 agent 在 Linux 上做一次 TCGA-LUAD 的 KRAS 表达生存分析：从 GDC Data Portal 下载 LUAD 的临床数据与 STAR-count 表达矩阵，用 tpm_unstranded 指标取 KRAS(ENSG00000133703) 表达，对有多个原发肿瘤样本的 case 保留 submitter_id 字典序最小的样本去重，合并临床协变量后按队列中位数把病人分成 high/low（>=中位数为 high），再做 Kaplan-Meier、log-rank 和含 KRAS 组 / 年龄 / 分期的 Cox 比例风险模型。产出 cohort.csv、km_plot.png、cox_results.json、analysis.R 四个文件到 output/。

要求

必须在 output/ 下产出 4 个文件。cohort.csv 至少 400 行、含 10 个必需列(patient_id,sample_id,file_id,kras_expression_selected,kras_group,time_days,status,age_at_diagnosis_years,raw_stage,stage_group)、指定列不得为 NA、sample_id 取 TCGA 条码前 15 字符、kras_expression_selected 用 tpm_unstranded。cox_results.json 必须含四个顶层段 cohort_summary / log_rank / cox_model / ph_test；cohort_summary 含 n_patients,n_events,n_kras_high,n_kras_low,median_kras_expression；cox_model.coefficients 键为 kras_group_high / age_at_diagnosis_years / stage_group_advanced，每个含 hazard_ratio,p_value,ci_lower_95,ci_upper_95。关键点：output_requirements.txt 对 ph_test 只写了一句『ph_test: structure is flexible』（结构自由），task_spec.json 给出的提示是 '"ph_test": "cox.zph()"'。analysis.R 要体现 GDC 下载与生存分析工作流；禁止读取 evaluator 的 reference/ 目录（analysis.R 若触碰会被硬判 0）。

评测方法

评分器 scripts/score_outputs.py 是加权 rubric，并非精确复现参考答案——参考数据只当验证 oracle，统计量从『提交的』cohort.csv 现算后再与『提交的』cox_results.json 比对（即自洽性检查，这就是为什么 OFF 479 / ON 475 / 参考 486 的病人数差异、以及各自不同的 p 值都不扣分）。五段权重 SECTION_WEIGHTS={artifacts:0.20, cohort:0.25, derivations:0.25, statistics:0.20, reproducibility:0.10}。statistics 段内部 = 0.15*summary + 0.25*logrank + 0.50*cox + 0.10*float(ph_valid)。cohort / expression 用容差带（_band_score，patient_f1>=0.95 满分；表达量 _close_score atol=1e-4,rtol=1e-4）。真正致命的是末尾的关键项闸门：critical_checks 有 6 项(patient_set_similarity、expression_verification_coverage、expression_match_rate、summary_consistent、ph_test_valid、group_labels_consistent)，quality_gates_passed 要求各段过阈值且 all(critical_checks.values())；一旦不过就执行 `score = min(score, 0.84)` 把分数硬封到 0.84。ph_test 是否有效由 _validate_ph_test 决定：它只从 section['per_variable']（dict）、section['table']（list）、或（前两者都为空时）顶层『值为 dict 且变量名可识别』的键里取条目，要求 {kras_group_high, age_at_diagnosis_years, stage_group_advanced} 三者都出现且各有非负 statistic 与 [0,1] 的 p 值。

模型执行过程（逐帧）

两次 run 流程几乎相同：都先读 task_spec / task_description / output_requirements / runtime_notes / README 五个输入文件，确认 R 包(TCGAbiolinks/survival/survminer 等)齐全、GDC API 返回 200/OK，再用 TCGAbiolinks 的 GDCquery / GDCquery_clinic（585 行×98 列临床）下载并构建队列，各写一次 analysis.R（OFF 8502 字节@step18，ON 9005 字节@step22），跑 Rscript 产出四文件。两者都做了自检：OFF 在 step28 校验 cohort 列/行数/去重/中位数/标签（479 行、high240/low239、median 28.1055）、用 jq has() 检查 cohort_summary 五个键、file+identify 验 PNG、Rscript parse 校验 analysis.R；ON 在 step26 用 test -s 检查四文件非空、read.csv 校验行数/事件/分组（475 行、171 事件、high238/low237）、jq has() 检查键，step30 还尝试读 km_plot.png（模型不支持图像被略过）。差异只在收尾：OFF 在 step33 把 sample_id 截取从 15 改成 16 又重跑、step37-39 发现 gdc 缓存不一致于是删缓存重建，最终 TIMEOUT（但 eval 时盘上已存在的那份输出评为 1.0）；ON 32 步 completed。决定分数的是各自 analysis.R 里 ph_test 的序列化方式——OFF 写成顶层 {kras_group:{...}, age_at_diagnosis_years:{...}, stage_group:{...}, GLOBAL:{...}}，ON 写成 {method:'cox.zph', results:[{variable:'kras_group',...},...,{variable:'GLOBAL',...}]}。

哪里做错了

OFF 没做错任何事，满分 1.0（复现 score_submission：五段全 1.0、uncapped=1.0、六个 critical_checks 全 True、ph_variables=['GLOBAL','age_at_diagnosis_years','kras_group_high','stage_group_advanced']）。ON 的统计学同样正确——log_rank_consistency=1.0、cox_consistency=1.0、summary_consistent=True，其余五个 critical_checks 全 True，uncapped_score=0.98。唯一失分点是 ph_test 的 JSON 形状：ON 把 cox.zph() 结果序列化为 {method, results:[...]}，而 _validate_ph_test 只认 'per_variable'/'table' 两个键或顶层变量键字典；它根本不看 'results' 这个键，回退分支又要求顶层值本身是 dict，但 ON 顶层只有 method(字符串) 和 results(列表)、两者都不是 dict，于是 entries 为空、valid_variables 为空、ph_test_valid=False（复现 ph_variables=[]）。这让 all(critical_checks.values())=False，触发 `score = min(0.98, 0.84) = 0.84`，同时 statistics 段因 0.10*float(ph_valid) 归零从 1.0 降到 0.9。注意参考答案自己用的是第三种形状 per_variable——三种合法形状里偏偏没有 ON 用的 results 列表；这是一个隐藏的 schema 白名单，与 output_requirements 承诺的『structure is flexible』直接矛盾。

怎样才能做对

对 agent 而言修复极简单、但也纯属运气：把 ph_test 换成三种被接受形状中的任一种即可满分——(a) 顶层变量键字典 {kras_group_high:{test_statistic,p_value},...,GLOBAL:{...}}（OFF 的做法）、(b) {'per_variable': {...}}（参考答案的做法）、或 (c) {'table': [{'variable':'kras_group_high','test_statistic':..,'p_value':..},...]}。统计内容 ON 已算对，只是把列表放在了 'results' 键下而非 'table' 键下、且顶层混进了非 dict 的 method 字段。但 agent 无从得知该用哪种键：output_requirements 明写 ph_test『结构自由』、task_spec 提示用 cox.zph()，ON 正是照此实现并给了合理的 {method, results} 序列化。因此这不是模型能力或指令遵循的问题，而是评分器把『自由结构』偷偷限制成隐藏白名单造成的失分，无法靠更强模型或更好自检消除（reference/ 目录还被禁止读取，读了直接判 0，连对答案的机会都没有）。

harness（ON）的效应

ON（harness 开）相对 OFF 在行为上几乎无变化：两者都独立完成了下载、分析，并主动自检了四个交付文件是否存在/非空/列齐/键齐/PNG 有效——OFF 在无任何提示下已经做了（step28），说明 M2『交付物存在且非空』与 M4『别重复读/跑』这两条镜像提示在此处是冗余的。ON 反而更利落：32 步 completed（1307s），OFF 39 步 timeout（2409s）。分数从 1.0 掉到 0.84 与 harness 没有因果关系：镜像块只复述预算/交付物/验收/防抖，从不提及 ph_test 的键名或 schema；M3『按数值目标反复复算』也不触发，因为 ph_test 形状不是数值目标、且唯一的参考属 evaluator-only（agent 被禁止读取）。真正决定成败的 ph_test 序列化形状，是两次独立生成 analysis.R 时的采样差异——一次抽到白名单内形状、一次抽到白名单外形状。结论：这是隐藏 schema 上的采样方差，而非 harness 注入的错误。
