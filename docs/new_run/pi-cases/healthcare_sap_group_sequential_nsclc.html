题目本身

在 Linux VM 上、仅凭 protocol.json 为一项二臂 III 期晚期 NSCLC（帕博利珠单抗+化疗 vs 化疗）试验编写完整的成组序贯统计分析计划(SAP)交付集。需基于协议给定的 HR=0.73、单侧 α=0.025、power=0.8、目标事件数=240，计算 log-rank/Schoenfeld 样本量、三次 O'Brien-Fleming 效力边界(信息比 0.5/0.75/1.0)、look-1 的绑定 futility(CP<0.20，looks 2/3 记 NA)、门控 Hochberg 多重性、功效曲线，并产出 8 个规定文件。

要求

必须在 output/ 生成 8 个文件：SAP.md、analysis.R、sample_size.json、boundaries.csv、multiple_testing.json、power_curve.csv、power_curve.png、boundary_plot.png。硬门槛：8 个文件全部存在且非空，否则整体 0 分(hard_gate_failed)。关键约束：task_instructions.md 只描述『要算什么』(6 条计算要求)，完全没有给出任何 JSON 键名或 CSV 列名的 schema；参考答案 reference_values.json 与评分脚本在 reference 目录、solve 时不可见。

评测方法

见 scripts/score_outputs.py。6 分项加权求和：boundaries 0.25、sample_size 0.20、multiple_testing 0.20、documents 0.15、power_curve 0.10、plots 0.10；passed 需 score>=0.85。各项按参考『精确键名』核对：sample_size 读顶层键 per_arm_n(±3%→0.65)、events_required/total_n/adjusted_total_n(整数相等各 0.08)、inflation_factor(±0.01→0.11)；boundaries 按 look 索引，每 look 查 info_fraction(±0.001)、events_at_look(整数相等)、efficacy_z_boundary(±0.05)、futility_z_boundary(±0.05 或 NA)，共 12 子项 passed/total；multiple_testing 查顶层 secondary_endpoints[].{name,hochberg_rank,adjusted_alpha(round 4 位±0.0001)} 各 2 分 + 顶层 subgroup_bonferroni_alpha(±1e-5)；power_curve 要求 CSV 含列 hazard_ratio 与 power、>=5 行，检查 in_range/has_target(HR≈0.73 且 power≈0.80±0.08)/单调。致命设计：所有数值都用 `_to_float(row.get(key))`，键缺失→`_to_float(None)` 抛 TypeError，被分项级 except 捕获→整个分项清零(而非只扣该子项)。原始人工评分器 raw_submitter_evaluate.py 是二元 PASS/FAIL，用的正是同一批键名(per_arm_n / efficacy_z_boundary / futility_z_boundary / secondary_endpoints[].adjusted_alpha)——ALE 版把它改写成部分给分并新增了 info_fraction/events_at_look/total_n/adjusted_total_n/inflation_factor/subgroup_bonferroni_alpha/power_curve 列检查，键名仍不对 agent 公开。

哪里做错了

sample_size：两次都 0。均无顶层键 per_arm_n(grep -c=0)，用的是 randomized_per_arm/adjusted_total_sample_size_events 等；`per_arm_n` 缺失→异常→整分项清零。且模型自作主张——判定协议的 240 事件在 HR=0.73 下仅 68% 功效(自报 0.6836)，改按 Schoenfeld 重算 fixed 317、adjusted 325 事件、356 例(178/臂)，与参考的 240 事件/330 例/165 每臂不一致；即使键名正确，per_arm_n 178 vs 165 差 7.9%>3% 仍失分，只有 inflation_factor 1.0238 vs 1.017(差 0.0068<=0.01)会过。boundaries：两次都 0。列名用 information_fraction(非 info_fraction)→读 info_fraction 得 None→抛异常→整分项清零。讽刺的是 OFF 的 CSV 里明明有一列 protocol_planned_events=120/180/240(与参考 events_at_look 完全一致)、efficacy_z_boundary=2.863/2.337/2.024(look2/3 在 ±0.05 内)，只因列名不叫 events_at_look/info_fraction 而全被清零；若改成参考列名，boundaries 约 10/12≈0.83，仅丢 look-1 效力 z(2.863 vs 2.963 差 0.10>0.05，Lan-DeMets 谱 vs 经典 OF 之别)与 look-1 futility z(0.0158 vs 0.459)。multiple_testing：两次都 0，但数字全对——模型把三个 Hochberg 临界值 0.025/0.0125/0.008333 放进 secondary_family.endpoints(字符串列表)+ordered_p_value_rules，Bonferroni 0.00625 放进 subgroups.bonferroni_alpha_per_factor(OFF)/per_test_one_sided_alpha(ON)；评分器要顶层 secondary_endpoints[].{name,hochberg_rank,adjusted_alpha} 与顶层 subgroup_bonferroni_alpha，键名/结构全错，且缺 subgroup_bonferroni_alpha 触发异常清零；若按 schema 填可拿满 1.0。power_curve：OFF 0(无 power 列)、ON 1.0(有 power 列，HR=0.73 行 power=0.7971 落在 0.80±0.08、全程单调)。plots+documents：两次都 1.0(8 文件齐全、两张 PNG 有效、SAP 含 sample size/o'brien/hochberg/futility/overall survival 五词且>=500 字、analysis.R 含 gsDesign 与 protocol.json)——由精确等式 OFF 0.25=0.10+0.15、ON 0.35=0.10+0.10+0.15 反推可证。

怎样才能做对

1) 键名/列名对齐(纯 schema 问题，约可救回 0.47 分)：sample_size.json 顶层补 per_arm_n/events_required/total_n/adjusted_total_n/inflation_factor；boundaries.csv 列改名 info_fraction、events_at_look；multiple_testing.json 改成顶层 secondary_endpoints:[{name,hochberg_rank,adjusted_alpha}] 与顶层 subgroup_bonferroni_alpha；power_curve.csv 增设 power 列。仅此一步 multiple_testing 即 0→1.0(+0.20)、boundaries 0→约 0.83(+0.21)、power_curve(OFF) 0→1.0(+0.10)。2) 采纳协议给定的 240 事件而非重算 317/325(这样 per_arm_n=165/total_n=330/events=240/adjusted=336 与 boundaries 的 events_at_look=120/180/240 才对得上)——此为模型的实质分歧点：协议自相矛盾(240 事件与 80% 功效不兼容)、指令未消歧、答案键默默取 240，而模型选了功效优先。3) look-1 效力 z 需与参考一致的 OF 参数化得 2.963(模型 gsDesign 默认 Lan-DeMets 给 2.863，差 0.10)、look-1 futility z 需按参考 CP 约定得 0.459(模型得 0.0158)。注意：即便完全对齐 schema，用模型自己的数字上限也只到约 0.80，仍达不到 0.85——满分须同时(a)对齐 schema 且(b)采用参考的 240 事件设计；而(b)与(3)两处数值分歧本身部分源于协议/答案键的模糊，并非纯粹的模型能力缺陷。

harness（ON）的效应

ON 相对 OFF 分数 +0.10，但与镜像四提示(M1 预算/M2 校验文件非空/M3 对参考复算/M4 防抖)无任何因果关系。这 +0.10 纯属两次独立运行写 CSV 列名的随机差异：ON 恰好把功效曲线一列命名为 'power'，OFF 命名为 'fixed_design_power'，同一套计算、只因命中评分器硬编码的列名而 power_curve 0→1.0。M2/M4 在此冗余——两次都已自行 read 回全部输出、验证 PNG、重跑脚本确认复现(OFF 步 20-31，ON 步 18-46；ON 反而更爱折腾，47 步 7 次 edit)。M3(『对照参考复算直到达标』)在本题根本无法有效触发：reference_values.json 位于 reference 目录、solve 时不可见，没有任何可见输入能让 agent 发现评分器要的精确键名——这正是要害：当验收标准(精确键名/列名)对 agent 隐藏时，镜像式『复算直到达标』的提示无能为力。
