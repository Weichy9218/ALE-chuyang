题目本身

任务要求基于暂存资料包（Zscaler FY2025 的 10-K、Q2/Q3 财报与电话会等 offline 文件）撰写一份面向私募股权的 Zscaler 尽调筛选备忘录（screening memo）。须只用暂存资料、不得联网检索，按 memo_template.md 的结构成文，并给出明确的 Go / No-Go / Hold (Needs More Diligence) 建议。唯一交付物是 output/ 下的 screening_memo.md（有效 UTF-8 Markdown）。

要求

交付文件名必须恰好为 screening_memo.md，写在 remote_output_dir 下；有效 UTF-8 Markdown；须含六个规范标题（'# Zscaler Screening Memo'、'## I. Recommendation'、'## II. Investment Thesis'、'## III. Financial Summary'、'## IV. Risks'、'## V. Appendix — Business Overview'，contract 允许把模板占位 [Company] 视作 Zscaler、忽略标题内多余的 ** 加粗）；Recommendation 段须给出显式建议；总字数 ≥250；只用资料包、不得联网。

评测方法

main.py 的 evaluate() 先检查 output/reference/contract 三个文件存在（缺则 return [0.0]），再调用 scripts/score_screening_memo.py 的 score_screening_memo()。该评分器是 'LLM-judge edition'：先做三道基于规则的硬门槛——(1) _missing_headings 按序校验六个规范标题、(2) 字数 <MIN_WORD_COUNT=250、(3) _recommendation_is_explicit 匹配 go/no-go/hold 等关键词——任一不过直接返回 ScoreResult(score=0.0)。三门槛通过后用 OpenAI 客户端（MODEL='gpt-4o-mini', temperature=0）对 27 个分节问题 + 10 个 anchor 问题共 37 次 yes/no 判断（_batch_judge 用 ThreadPoolExecutor(max_workers=10)）打分：score = round(0.75*weighted_coverage + 0.25*anchor_score, 6)，weighted_coverage = 0.15*recommendation +0.25*investment_thesis +0.25*financial_summary +0.20*risks +0.15*appendix，pass_threshold 默认 0.7。决定性脆弱点：evaluate() 只把 session.read_file() 包在 try/except（'Failed to read task artifacts'）里，对 score_screening_memo() 本身没有任何异常保护——裁判 API 一旦抛错，异常直穿而出，任务被判 failed、score=null（而不是 0.0）。

模型执行过程（逐帧）

两个条件下 pi 的执行都很规范，与失败无关。OFF（40 步；read×20/bash×9/write×1）：[3] 先并读 task_brief、memo_template、source_manifest、README；[9]-[29] 分块精读 10-K 与 Q2/Q3 财报，用 rg 定位 Revenue/free cash flow/stock-based compensation/ARR/Red Canary/convertible notes 等要点；[33] 写出 screening_memo.md（write 返回 18584 bytes）；[35]-[39] 自检——file -bi 确认 charset=utf-8、rg 校验标题与关键数字、wc 得 83 行 2572 词。ON（34 步；read×17/bash×6/write×1）流程几乎相同，[30] 写出 16906 bytes、[32] 用 python3 verify 文件非空。两份产物都给出 'Hold / Needs More Diligence' 建议、六个规范标题齐全（含 '## V. Appendix — Business Overview'）、字数 2572/2356，均已越过全部硬门槛并进入 LLM 裁判阶段——正是在这一步 gpt-4o-mini 返回 503 使评测崩溃。

哪里做错了

根因在评测基础设施而非模型输出。run.json 记录 termination.phase='evaluation'、category='transport_error'、error.message="Error code: 503 - {'error': {'message': 'Service temporarily unavailable', 'type': 'api_error'}}"；两条运行的 eval_result.json 同样 eval_status='failed'、score=null，错误字符串逐字一致。该 503 来自评分器内 _llm_judge 对 gpt-4o-mini 的调用（已发出请求并收到 HTTP 503，说明 API key/base_url 都存在，不是 'OPENAI_API_KEY not set' 那类配置错误，而是裁判服务瞬时不可用）。ThreadPoolExecutor.map 会把首个异常重新抛出，而 evaluate() 未捕获 score_screening_memo()，异常直穿成整任务 failed/score=null。OFF 评测仅 12.77s、ON 仅 4.88s 即崩溃，与批量并发裁判中一发请求即 503 相符。模型输出本身合规：六标题齐全、2572/2356 词、显式 Hold，硬门槛全过，若裁判正常应能得到一个正分（凭覆盖度很可能高于 0.7 阈值）。

怎样才能做对

此失败不可由被评 agent 修复——产物已满足全部要求。需修的是评分/编排侧：(1) 在 _llm_judge/_batch_judge 中对 5xx/429 加入重试与指数退避（当前对 gpt-4o-mini 是单发无重试）；(2) 在 main.py 的 evaluate() 用 try/except 包住 score_screening_memo()，裁判不可用时回退（例如降级为仅按硬门槛计分，或返回可重跑标记）而非让异常抛成 null；(3) 让 harness 对 category='transport_error' 且 phase='evaluation' 的失败自动重跑评测。因 503 是 'temporarily unavailable' 的瞬时故障，单纯重跑评测极大概率成功并给出正常分数。

harness（ON）的效应

被评的 ON/OFF 差异（pi 启动时 M1–M4 镜像提示）在此完全无关：失败发生在评分器调用外部裁判 API 的评测阶段，ON 与 OFF 共用同一套评分代码，因而以完全相同的 503 / transport_error 崩溃（两份 eval_result.json 错误字符串逐字相同）。镜像提示在这里既非有益也非有害——产物根本没等到被打分。ON 的产物（2356 词、16906 bytes）与 OFF（2572 词、18584 bytes）同样通过全部硬门槛，唯一可见差别是无关紧要的备忘录日期（OFF 'July 15, 2026' vs ON 'September 11, 2025'）。
