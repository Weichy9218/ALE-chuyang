同一模型两次采样都用 VEP 归一化等位基因 "-" 误取了缺失变异 chr1_1387763_CCT_C 的群体频率 0.8255（参考答案要求 NA）；OFF 因其"两个分支都加 AF<0.01 门槛"的可报告判定把这个 bug 放大成 2 个可报告（≠manifest 声明的 3）而自检发现并改回按提交 ALT 取频率，ON 因"只在 ClinVar 分支加 AF 门槛"的解释使计数仍为 3、自检通过而漏掉，最终这 1 个错误单元格在 20 分 all-or-nothing 的可报告块上被放大成约 −20.6 分——是运行方差被评分悬崖放大，而非 harness 注入错误信息。

题目本身

在 Linux 上做一个临床变异注释流水线：读取 50 个已分期变异（variants_to_annotate.tsv），解析原始 VEP 快照 JSONL，为每个变异推导 gene / consequence / max_population_af / clinvar_significance / is_reportable 五个字段，并按 source_manifest.json 里的规则筛出"可报告"子集。要求写出 annotated_variants.tsv、reportable_variants.tsv、pipeline.py、run_log.json 四个产物。这是一个确定性的数据管道任务，答案唯一，靠对 VEP 数据结构与 manifest 规则的精确解析。

要求

四个产物文件都必须存在且非空：(1) annotated_variants.tsv 与 reportable_variants.tsv 必须用 tab 分隔且表头精确等于 10 列 `variant_id chrom pos ref alt gene consequence max_population_af clinvar_significance is_reportable`；(2) 缺失数值用 `NA`、缺失分类用 `not_reported`，不得用 `.` 或空；(3) is_reportable 取小写 yes/no；(4) reportable_variants.tsv 只含 is_reportable=yes 的行；(5) run_log.json 至少含 status / annotated_variants_written / reportable_variants_written。参考答案：annotated=50 行、reportable=3 行（三个 frameshift 缺失/插入变异 chr1_1310876、chr1_1387763_CCT_C、chr1_1635982，AF 全为 NA）。manifest 明确声明 counts.reportable_variants=3、annotated_variants=50，可作输入侧自检基准。

评测方法

score_outputs.py 满分 100，归一化后即分数：pipeline 2 + run_log 3 + structure 10（行数=50 给 5、行序与参考完全对齐 canonical_alignment 给 5）+ gene 25（_threshold_points full_threshold=45/partial_floor=35）+ consequence 25（full=43/floor=30）+ AF 10（按比例 af_matches/50*10）+ clinvar 5（clinvar_matches/50*5）+ **reportable 20（all-or-nothing）**。可报告块是决定性悬崖：只有当 `canonical_alignment` 且 `[_normalize_row(r) for r in submitted_reportable_rows] == [_normalize_row(r) for r in reference_reportable_rows]`（逐行全字段相等）且所有行 is_reportable=='yes' 且集合相等 且 reportable_flag_matches==50 时才给 20，否则给 0。关键：_normalize_row 只把"缺失哨兵" `{"",".","na","none","not_reported"}` 归一到 "NA"，一个真实数字如 "0.8255" 不是哨兵、不会被归一，于是与参考的 "NA" 不等，整块 20 分清零。PASS_THRESHOLD=0.85。

模型执行过程（逐帧）

两次都是先并行读入 variants/manifest/vep_batch_responses/pyproject（OFF 步[3]、ON 步[3]），再用内联 python 探查 VEP 的 consequence 优先级、colocated frequencies、clin_sig（OFF 步[9-19]、ON 步[9-16]），然后写 pipeline.py 跑出四个产物。分叉点在可报告判定与 indel 频率：ON 步[17-22] 一次写好 pipeline 直接跑出 "wrote 50 annotations (3 reportable)"，步[23-27] 做结构自检 "validation passed: exact header, 50 ordered annotations, 3 filtered reportables, valid run log" 通过即收尾——从未回头核对 AF 数值，run_log 只写了 {status,50,3}。OFF 步[25] 第一次跑却是 "annotated 50 reportable 2"，只有 2 个可报告，与 manifest 声明的 3 不符；步[26] 随即反思 **Assessing VEP allele frequency interpretation / Aligning allele frequency with submitted ALT / Adjusting frequency calculation to original ALT**，edit pipeline 把频率取法从 VEP 归一化 alt 改成"按 TSV 里提交的原始 ALT"，步[28-29] 重跑得到 "verified: 50 annotated, 3 reportable"，并在 run_log 里落了 count_comparison{declared:3, observed:3}、manifest_counts_match:true 的显式交叉核对。

哪里做错了

根因是 indel 频率取法。VEP 把缺失 CCT→C 归一化成 allele_string "CT/-"，把 frequencies 挂在键 "-" 下（最大值 gnomade_asj=0.8255）。ON 的 max_population_af(response, normalized_alt) 用 normalized_alt=transcript.get("variant_allele")=="-" 去 `frequencies.get("-")`，于是取到 0.8255；参考答案要求按"提交的 ALT"("C") 取，"C" 永远不等于 VEP 的最小化等位基因 "-"，所以全部 indel 都是 NA。ON 因此有 3 个 indel AF 错：chr1_979034_CGAA_C=0.01059、chr1_1387763_CCT_C=0.8255、chr1_1629572_TG_T=0.4747（参考均为 NA），af_matches=47/50 丢 0.6 分。致命的是 chr1_1387763_CCT_C 恰是一个可报告行：它的 max_population_af=0.8255≠参考 NA，打破 reportable 块的逐行相等 → reportable_points 从 20 归 0。为何 ON 计数仍对（掩盖了 bug）：ON 的可报告规则写成 `consequence in SEVERE or (clinvar pathogenic and rare)`，AF<0.01 的 rare 门槛只加在 ClinVar 分支，frameshift 走 SEVERE 分支、无视 AF，所以尽管 AF=0.8255 仍判 yes、计数=3=manifest、自检通过。OFF 的规则是 `clinically_relevant and rare_enough`，AF 门槛加在两个分支上，同样的首轮 AF bug 让这个 frameshift 被 0.8255≥0.01 挡下 → 只剩 2 个可报告 → 与 manifest 的 3 不符 → 触发修复。两者还共享一个与 harness 无关的 clinvar 小错：chr1_942451_T_C 都写成 benign（参考 uncertain_significance），各丢 0.1 分（clinvar 49/50）。所以 99.9−79.3=20.6 的差 = 20（可报告悬崖）+0.6（多 2 个 indel AF 错），clinvar 那 0.1 两边都丢、不进入差值。

怎样才能做对

正确解法就是 OFF 修好的那一版：max_population_af 必须按"variants_to_annotate.tsv 里提交的原始 ALT"（例如缺失的 "C"、插入的 "GC"）去 colocated_variants[*].frequencies 里查键，而不是用 VEP 的 variant_allele / 最小化等位基因（"-" 或去掉共同碱基后的 trimmed base）。由于 VEP 对 indel 一律用最小化表示做频率键，提交式 ALT 与之永不相等，故所有 indel 的 max_population_af 都应为 NA——OFF 代码里甚至写了注释点明这点："A normalized VEP key (for example \"-\") is not the submitted allele."。这不是模型能力天花板：同一模型在 OFF 里就做对了；关键是要有一个能戳破"计数对但单元格错"的验证——OFF 靠的是把可报告的 AF 门槛加在两个分支上，从而让 indel AF bug 外化成"可报告数 2≠manifest 3"的可自检差异并据此回改。ON 若要稳，需在自检里除了核对计数与结构，还要对 indel（ref/alt 长度不等）行断言 max_population_af 为 NA，或直接把频率查键统一到提交 ALT。共享的 clinvar 小错则是 clin_sig 优先级选取方向问题（uncertain_significance 优先级高于 benign，二者都不是这里的关键，只值 0.1 分）。

harness（ON）的效应

行为上：ON 更顺（30 步 vs OFF 31 步），首轮 pipeline 就跑出 3 个可报告（步[22]），做了结构+manifest 计数自检并通过（步[23-27]）后收尾，全程没回看 AF；OFF 则因首轮计数 2≠3 触发了一轮"按提交 ALT 重算频率"的修复（步[25→26→29]）。分数上 ON 因此丢掉整块 20 分可报告 + 0.6 AF。机制判定：ON 的 harness 只是一段"镜像"式启动提示（M1 预算 / M2 产物存在 / M3 acceptance / M4 防抖），**没有注入任何错误信息**，也没让 ON 偷懒——ON 本就写齐了产物、跑了计数自检、没有无谓重复，M1/M2/M4 全属冗余。M3 的"数值目标"只能取输入可见的 manifest 声明计数（annotated=50、reportable=3），而 ON 恰恰满足了这两个数；真正的 ground-truth（indel 该为 NA）在 evaluator 私有的 reference/hidden_truth 里、输入侧根本看不到，任何镜像提示都无法把 ON 指向那个错误单元格。也就是说镜像所能复述的验收信号（计数）正好落在盲区（计数对、数值错），既没造成也无法纠正这个错。真正的因是**运行方差**：两次采样对 manifest 中"AF<0.01"门槛作用于哪个分支这一歧义规则做了不同解读，决定了共享的 indel-AF bug 会不会外化成计数差异——OFF 的解读让它现形并被修，ON 的解读把它吸收使计数照样对——再叠加"可报告逐行相等"这道 20 分 all-or-nothing 悬崖，把 ON 一个残留错单元格放大成 −20.6。

  • ON reportable_variants.tsv 里 `chr1_1387763_CCT_C ... frameshift_variant 0.8255 not_reported yes`，参考 hidden_truth 为 `chr1_1387763_CCT_C ... frameshift_variant NA not_reported yes`。
