题目本身

在 Linux VM 上实现图书馆编目迁移工具 scripts/remediate_catalog.py，把厂商遗留 MARC 批次迁进 FOLIO Data Import。需先把 starter_project 复制到 output/submission，实现同一 CLI（--case-dir/--output-dir），对 64 条公开合成 MARC 记录做：控制号规范化（OCLC/LCCN/ISBN）、去重（保留最完整记录、压制较弱重复）、AACR2→RDA 改造（040$b eng、040$e rda、删 245$h、加 336/337/338）、按 authority_map.csv 做权威控制替换、依 folio_instances.csv 决定 update/create/suppress、按 949+location_map.csv 生成馆藏与馆藏件负载，产出 5 个成品文件。评测另在 2 个隐藏用例上重跑同一 CLI 做防硬编码检查。

要求

在 output/submission 下产出 6 个交付物：scripts/remediate_catalog.py 及 outputs/public_case/ 下的 remediated_records.xml、overlay_decisions.csv、folio_import_plan.json、qa_report.json、remediation_summary.md。CSV 列固定为 record_id,normalized_oclc,match_key,matched_instance_hrid,action,reason；folio_import_plan.json 顶层含 actionProfiles/folioRelease/jobProfileName/matchProfiles/records，每条记录含 record_id/action/match_key/matched_instance_hrid/source_record_id/instance/holdings/item/srs。规则全部来自 cataloging_policy.md（含 OCLC 规范化、去重存活排序、RDA 载体 336/337/338 取值、权威替换、949 映射）。约束：不得改 input/，只能写 output/。

评测方法

两级脚本。evaluate_submission.py 只是 launcher，调 evaluate.py 取 score(0-100) 后 normalized_score = max(0,min(1, score/100))。真正打分在 evaluate.py：① artifact 门槛——required_files 的 6 个文件 path.exists() 且 st_size>0 → score+=10，任一缺失则总分 0 且两个隐藏用例直接判 'artifact gate failed'；② 公开精确比对（仅门槛通过后 compare_outputs 对比 reference_outputs/public_case）：remediated_records.xml 经 ET.indent 规范化后字符串相等 = 25、overlay_decisions.csv 按 json.dumps(row,sort_keys) 排序后列表相等 = 15、folio_import_plan.json 全 dict 相等 = 25、qa_report.json 全 dict 相等 = 10、remediation_summary.md 文本相等 = 5；③ 隐藏用例——对 hidden_river_maple、hidden_harbor_cedar 各重跑 CLI，run_hidden 里 'if score != 80: return False'，即 5 个文件必须全中才 +5。合计 100，'passed = score >= 85.0'。决定性一行是 compare_outputs 的 'passed = loader(actual_dir/name) == loader(expected_dir/name)'——零容差精确等值，无部分分。

哪里做错了

重新跑真评测确认：score=20.0，artifact_checks 6 项全 pass(+10)，public_checks 里只有 qa_report.json passed:true(+10)，其余四项 passed:false；两个隐藏用例 message 均为 'failed hidden checks: remediated_records.xml, overlay_decisions.csv, folio_import_plan.json, remediation_summary.md'（0/10）。业务逻辑其实基本对——qa_report 9 项计数与参考完全一致(records_received64/active56/suppress8/update28/create28/rda56/authority112/holdings56/item56)，remediated_records.xml 3810 行仅差 112 行(97% 相同)，CSV 的 record_id/normalized_oclc/matched_instance_hrid/action 也都对。丢分全在可见材料未定义的序列化约定逐字节对不上：① overlay_decisions.csv 的 match_key 列模型写 `oclc:(OCoLC)800000001`/空/`oclc:(OCoLC)...`，参考要类型标签 `oclc`/`no_match`/`duplicate_oclc`；reason 模型写 「Matched existing FOLIO instance by OCLC.」「No OCLC, LCCN, or ISBN match; create a new FOLIO instance.」，参考是 「Matched existing FOLIO instance.」「No existing FOLIO match; create new instance, holdings, and item.」；suppress 行模型还带了 matched_instance_hrid，参考留空 → 64 行全不等，CSV 挂(15)。② folio_import_plan.json 的 jobProfileName 模型 「Legacy MARC Remediation Overlay」 vs 参考 「LIS Legacy MARC Remediation Overlay」；actionProfiles 模型 2 项 vs 参考 5 项(['Update instance','Create instance','Create/update holdings','Create item','Modify SRS MARC'])；matchProfiles 模型 「Normalized OCLC」 vs 参考 「MARC 035$a OCLC to Instance」 → 挂(25)（folioRelease 两边都是 'Sunflower R1 2025'、每条记录键也对，但顶层几个字符串就足以判负）。③ remediated_records.xml 的 001 模型保留 `ocn800000001`、参考剥成裸数字 `800000001`，003 模型改成 `LOCAL`、参考保 `OCoLC` → 112 行差、挂(25)。④ remediation_summary.md 模型写成分节的 'MARC Remediation Handoff' 长备忘录，参考是 9 行固定短文本(如 'FOLIO job profile: LIS Legacy MARC Remediation Overlay'、'Unresolved assumptions: none; ...') → 挂(5)。隐藏用例因同样这 4 个文件逐字对不上而全 fail。

怎样才能做对

要满分必须让每个产物与 evaluator-only 参考输出逐字节一致，而卡死分数的约定——match_key 词表(oclc/no_match/duplicate_oclc)、reason 原文、jobProfileName 的 'LIS ' 前缀、actionProfiles/matchProfiles 的确切命名与项数、summary 备忘录的确切版式与措辞——在 cataloging_policy.md、TASK_PROMPT.md、以及提供的 catalog_remediation_lib.py 里通通没有；lib 只有 normalize_oclc/read_csv/write_records 等通用解析封装，不含任何规范字符串或模板。这些是出题人任意设定、非行业标准，看不到参考就无法复现，故非模型能力可补。少数可勉强推断的点（policy 规则1 提到 OCLC 去 ocn 前缀、或可推及 001 剥前缀；003 保 OCoLC 是 MARC 惯例）即便修对，因 CSV/JSON/summary 仍逐字不符、分数依旧钉在 0.2。真正的修法在评测侧：把精确等值放宽为语义/结构等值，或把这些约定字符串写进 policy；agent 侧几乎无可行改法。

ON 与 OFF 行为几乎相同、分数都是 0.2，harness 无实际作用。M2(核对交付物存在且非空)与 M4(防重复读/重复失败命令)模型本就自发做了：OFF step37-38、ON step31/36 都自查了 5 个产物齐全，两者都重跑了 CLI，ON 还两次核对 folio_import_plan.json 哈希验证确定性。M3(按输入内可见 reference 反复自校至达标)在此根本不适用——参考输出是 evaluator-only、solve 时不可见，没有可收敛的目标，M3 的触发前提(输入内有可见 reference)不成立。ON 甚至多做了 online 载体核查与确定性哈希，仍停在 0.2，因失分维度是不可猜的约定字符串，与 '是否验证/是否重跑' 无关。故 mirror 提示在本任务完全冗余，对分数零影响。
