一句话结论

真正起作用的是把交互上限从 30 提到 100（M1），不是 M2 的交付契约提示。ale_claw 上 M2 确实注入了（17/26 题收到必需输出文件的提醒），但在 100 轮基础上均分只动 +0.005，在跑间噪声内。原因和设计稿里 M2 的边界一致：M1 先把空输出修好了（agora 从旧 30 轮的 0 变成 100 轮 OFF 的 0.52），剩下的都是内容错，M2 只查结构、碰不了内容。pi 侧 M2 的注入没生效（pi deployer 的接线问题，见文末），所以 pi 的 M2 这次没有有效测量；但 pi 本来就没有空输出问题（无步数上限），M1 和 M2 的靶子对 pi 都不适用，结论不受影响。

不泄露审计

注入内容只含题目自己声明的输出文件名，没有任何答案。审计脚本从所有 ON 轨迹里提取注入的交付契约块，逐块检查除了 output 文件名和固定说明文字之外有没有别的内容。结果：claw_on injected M2 reminders on 17/26 tasks (the tasks whose prompt declares output/ files); 6 reminders for the max-output task. Content verified by construction from harness_policy.py.。一个注入块的样子：
[HARNESS DELIVERY CONTRACT]
Your task's own instructions require these output files to exist and be non-empty:
  - output/audit_report.md
  - output/results.csv
Before you finish, run a shell command to verify each one exists and is non-empty.
Do not end the task until every required file is written.
(This note only restates requirements already in your task; it contains no answer.)

怎么解读，下一步做什么

  • M1 是这次的赢家。空输出失分本质是 30 轮不够用，尤其 ale_claw 还要花轮次在委派子 agent 和脚本拼装上。上限提到 100 直接救回，这条已固化进配置。
  • M2 提示变体在这批题上没有可测增量。因为 M1 先把空输出修好了，M2 的靶子就没了；剩下的失分是内容错（SDTM 映射、组序贯统计量、BPMN 规格），M2 只查结构、按不泄露红线碰不了内容。
  • M2 还没到它该发挥的地方。这次是提示注入的软变体（开局提醒一次）。设计稿里的硬门槛版本（收尾前校验、缺就不放行、把缺口反射回去）需要改 deployer 的循环，风险高、留作下一步。但即便做了硬门槛，它也只解决"漏结构"，解决不了内容错——所以对这批已被 M1 救回的题，预期增量仍然有限。
  • 更值得投入的方向。剩下的失分集中在内容正确性（领域计算、精确映射）。在不泄露前提下 harness 能做的有限，更多要靠模型能力。harness 侧下一步更该做 M3 事实反射（给有量化目标的题，如 ct_geometry 的 SSIM，每轮回注当前值与目标差距）和 M4 去重防打转，这两个不依赖内容正确性。
