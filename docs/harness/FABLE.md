# FABLE — Prep 与 Verifier 的定位、通信方式与痛点

本文常驻保存这两个辅助 agent 的核心 insight，随证据更新改写，不做增量日志。版本演化在
[EVOLUTION.md](EVOLUTION.md)，当期设计在 [PREP.md](PREP.md) 与 [VERIFIER.md](VERIFIER.md)，
逐轮实验证据在 [results/](results/README.md)。当前协议：`task-prep-v21`、
`public-verifier-v17`（本仓库）；pgl 正在运行的六题两臂实验用 v20/v16，两组读数不混。

## 总纲：转化链

分数是 writer 行为的函数。Prep 和 Verifier 不产生分数，只能改变 writer 在提交前的行为，
所以评价它们的唯一尺度是一条转化链：

```text
产生信号 -> 到达 writer -> writer 采纳 -> 分项变化
```

历次实验的教训一致：瓶颈从不在测量或研究的质量，而在链条的后三环。

- 到达环：反馈只在 DONE 后推送时，52 个 verifier run 产生 0 次修复；344 条冻结 check 有
  156 条死在自设的来源门上，根本没有运行。
- 采纳环：v18 六题里 prep 交付的 artifact 在 writer 轨迹里零调用——**内联报告保证 exposure，
  不保证执行**；SEC 单题 +0.26 经轨迹核对与 prep 无关。
- 副作用环：清单点名的维度会把 writer 的努力从未点名的维度抽走（Agora 单题 -0.34：引文被
  压缩到能保证子串精确匹配的最短片段，牺牲了 scorer 未公开的长度与关键词条件）。

## Prep：输入侧 agent

**定位**：在 writer 开始前补齐输入。输入是公开题面、`input/`、`software/`、沙箱运行时和
web；输出按保真度排序是三种载体：

1. **沙箱状态**（装好的环境、跑通的服务）——零损耗，writer 无需信任任何文字。
2. **可运行的自检脚本**（`self_check`）——合同知识的程序化载体，writer 拉取式消费，随时
   可跑、零权威。
3. **散文**（清单、findings）——最有损的载体，存在于 `task_prep/PREP_REPORT.md`，writer
   被 digest 点名后自己读（v21 起不再内联首轮 prompt；digest 只带运行时状态、self_check
   命令、条目数和"先读报告文件"）。

**消费方式**：能下沉到状态的下沉到状态，能程序化的程序化，散文只承载前两者装不下的部分。
这个排序不是风格偏好：v18 实测中第 3 类的采纳率是零，第 1 类（BPMN 判定 Docker 嵌套不可用）
是该轮唯一确定改变 writer 行为方式的交付。文件式消费换掉了内联的两个结构病（12k 注意力
预算、尾部截断），代价是新失败面"writer 不读文件"，用 transcript 里的 read 调用率直接量。

**红线**：运行期不碰候选 `output/`（彼时不存在，交付的检查则应引用它）；不选最终取值；
只做机械校验（语义 gate 必然退化为格式检验）；fail-open；不缓存（状态是真实的，缓存报告
会撒谎）。

**最重要的单条 insight**：清单是对题面的部分阅读，而 writer 会照着清单优化。清单越具体、
约束力越强，未点名维度被牺牲的风险越大；把清单程序化成 self_check 会同时放大采纳率和这个
风险。对策是结构性的：条目措辞为最低义务而非优化目标、清单和脚本都声明"不覆盖什么"、
权威顺序把题面永远置于 prep 之上。这个对策是否够用，是 prep 侧下一个要测的问题。

## Verifier：输出侧 agent

**定位**：writer 提交前唯一的独立测量者。输入只有公开任务表面（绝不含 Prep、writer 历史、
隐藏 reference、evaluator）；输出是 solve 前冻结的测试包，和对 output 只读快照的四类测量
报告（hard_mismatches / review_items / execution_errors / coverage_gaps）。

**消费方式，两条通道**：

- **拉取（主通道）**：`verify` 工具，writer 在 DONE 前主动对草稿运行冻结包，测量在预算内
  到达，修复由 writer 自己决定和执行。
- **推送（兜底）**：DONE 后的有限复核轮，只在存在可复核差异时触发。

拉取通道存在的理由就是转化链：同一份测量，DONE 前到达可以转化为修复，DONE 后到达只能
转化为验尸。

**权威设计**：测量、权威、复核三维分离。权威只决定一条差异算不算硬要求，不决定检查跑不跑
——来源已定位、checker 可复现的检查一律运行，歧义与部分覆盖以 advisory 身份出现并附审计
说明。quote 是事实、locator 只是坐标，坐标错误机械修正，不让格式问题冒充语义问题。

**红线**：标准在 writer 开始前冻结，每次执行复验全部 hash；隔离执行（Landlock/seccomp、
只读快照、双次运行）；报告测量不做诊断、不给 repair hint；writer 可用公开反证 dispute 任何
一条；结构 pass 不等于任务正确，未覆盖面永远声明。

## 两者的关系：一处真实的定位重复

- 独立并发，互不读取：prep 对题意或实现的错误不能同时污染求解和验收。
- 同一公开表面的两次独立阅读是可用的信号源：机械对账（按引用的公开文件求双向差集）把
  "两个 agent 重复读题"的成本变成"分歧即警告"的收益，且不授予任何一方新权限。

但重复是真实的，不该粉饰：**self_check 和 `verify` 都是"writer 提交前对草稿跑的机械
检查"**，都从公开题面派生。v21/v17 起分工按对象切开：

| | prep 的 self_check | verifier 的 `verify` |
|---|---|---|
| 对象 | 结构覆盖："缺不缺"——存在性、字段、拼写、行数、编码、跨文件一致 | 判定测量："对不对"——expected、重算、任务软件 |
| 权威 | 无，writer 可无视 | 分级（hard / advisory），hard 要修或 dispute |
| 成本 | 一次性生成，运行不限次、零 LLM | 构建要两个 agent，运行限次 |
| 独立性 | 与 writer 同源，不要求独立 | 独立冻结、审计、hash 固定 |

self_check 不硬编码期望取值、不给对错结论；prep 提示 writer 自检（digest 点名命令）是
这个设计的本意，它不僭越 verifier，因为它没有任何判定权。残余重复只剩"同一条结构义务
两边都可能查"，这恰是机械对账要暴露的分歧面，不是要消除的浪费。

在 prep_verifier 臂里 writer 仍会同时收到清单、self_check、verify 报告、对账注四路"你的
output 要满足什么"，注意力稀释和口径冲突都无法先验排除。当前的处理不是设计出一个融合
方案，而是**先分开量**：pgl 六题只跑 prep 和 verifier 两个单臂，两条通道各自独立测出
调用率和转化率，再决定合并形态。在拿到这组读数之前谈融合是凭空设计。

## 系统结构

```text
                    ┌─ Prep ──────────────┐──> 沙箱状态 / 报告文件+digest / self_check ──> Writer ─┐
公开题面+input+software┤                    │        （机械合同对账 ⇢ Writer）                      │ output/
                    └─ Builder ─> 定位/修复 ┴─> 预检 ─> 审计 ─> frozen suite ──────────────────────┤
                       （与 prep 并发）    （prep 后、prep staging 前）│                           │
                                    （solve 中）Writer ───────────────┴─ verify ─> 快照+隔离执行 ─> 四类报告
                                    （DONE 后）快照 ─> 完整冻结包 ─> 复核/修复 ─> 重跑
                                                       ↓
                                      output/ ─> hidden reference staging ─> 任务原 evaluator
```

## 一个跨两侧的失败签名：删减到通过

Agora 的引文压缩和 BPMN 的 delete-to-pass 是同一件事：面对一条机械检查，**内容越少越容易
通过**，而隐藏 rubric 恰恰奖励被删掉的部分。它在 prep 侧被 self_check 放大（脚本比文字
更有约束力，writer 会跑到全绿为止），在 verifier 侧被 `verify` 放大（限次但有权威）。

对策不是再加提醒，而是给它一个读数：每次快照都记录 per-file 的字节数和行数
（`snapshot_manifest`），分析侧把连续快照做差，得出 output 在信号到达后是增长、缩水还是
丢文件（`output_shrank`、`output_drift_bytes`、`output_dropped_files`）。一个读数同时覆盖
self_check、`verify` 和复核轮三个信号源，纯 harness 统计，不改任何权威。

需要说清楚一处已经存在的保护，避免重复造：总判定 `_overall` 只聚合 blocking 检查，
ambiguous / 蕴含不足 / 部分覆盖 / simulation 在冻结时 blocking 就是 false，它们的差异不会
让 Overall 变红。所以风险不是"有个全绿聚合目标可刷"，而是**逐条 advisory 的注意力消耗和
逐条 Goodhart**。这也是为什么对策是读数而不是新 gate。

## 当前痛点（按优先级）

1. **采纳环仍未被证明打通。** v18 六题的诊断把零调用劈成两半：Variant/BPMN/Digital 的
   artifact 引用被 12,000 字符截断从尾部切掉了（报告都顶到 ~11,900 字符），writer 根本没
   看见；SEC 的引用活着却仍然零调用，那是交接语一个字不提它。v20 的两个修复各治一半
   （Self-check 节前置、handoff 点名命令），读数在 pgl 六题回来前不知道。v21 更进一步把
   报告改成纯文件消费，截断类失败整体消失，但引入"writer 不读文件"的新失败面。这仍是
   最大的未验证假设。
2. **清单定向优化。** Agora 给了第一份实测证据；self_check 可能放大它。对策（最低义务措辞、
   边界声明）已落进代码文案，加上删减读数，效果未测。
3. **约束力最强的信号，验证环节最弱。** verifier 的每个 checker 冻结前要过 fixture 预检
   加 Auditor 审计；self_check 原本只有 prompt 里一句"在合成小样上测试"。现在补了最小
   预检：staging 后用空草稿跑一次，崩溃、超时、无输出就降级进 dropped 并保留文字清单。
   这只保证脚本不是坏的，不保证它判得对。
4. **k=1 方差远大于效应。** 六题配对 sd 约 0.2，任何单轮分数都测不出 0.02 量级的效应。
   所以协议迭代只认机制读数（每题确定可数），分数只在机制门通过后用配对多轮验证；base 不
   重跑，用历史多轮均值。
5. **ambiguous advisory 的噪声风险。** 放开来源门把 42% 的沉默检查变成 advisory 信号，
   代价是 writer 注意力；differ 率和采纳率决定这步是收益还是打扰。
6. **清单条数与成本仍无预算护栏。** 报告端的预算问题 v21 已经消除（不内联、不做注意力
   预算、截断只剩安全上限且对读者可见），但清单 24 条上限在 v18 有 4 题打满，成本方差
   一个数量级（35k-359k token）且与收益无关联；prep 会话目前只有步数和墙钟上限，没有
   token 上限。
7. **快照只活在容器里。** round-0 和每次 verify 的快照随容器销毁，"修复前后官方分对照"
   这条转化链末环的直接测量目前拿不到。本轮先落 manifest（尺寸与文件级差异），完整内容
   持久化留待下一轮，它是"信号到达后分数升还是降"唯一的硬前置。
8. **语义对齐做不到。** 合同对账只到文件粒度；两份阅读对同一句话的不同理解仍无人裁决，
   这是机械手段的边界，不是待修的 bug。

## 实验纪律

- 不重跑 base；treatment 臂对历史多轮均值配对。
- 每个协议改动先过机制读数，再谈分数；单轮六题只判机制，26 题只在机制门通过后。
- 归因必须过轨迹核对：分差在采用链（transcript 里的真实调用）成立之前不属于任何干预
  （v18 的 SEC +0.26 教训）。
