# 下一步：给 pi 搭一层不泄露答案的 harness

本文只讲下一步做什么、为什么、怎么落。目标是在 pi 外面搭一层 harness，在不告诉模型任何任务答案的前提下，用它提升 Qwen3.5-397B 在 ALE 上的成绩，并逐步走向让模型自己看轨迹、自己修 harness。结论先放前面：先补一批由真实失败模式驱动的、只给事实和预算的程序性规则，挂到 `pi-agent.md` 第 6 节那几个钩子上；跑通并验证提分后，再把写规则这件事交给 390B 模型自己做。

## 1. 目标的精确表述

理想的下一步是这样一个闭环：harness 能看到模型跑任务的轨迹，用 390B 模型自己分析这些轨迹，找出失败模式，然后重构 harness（包括 prompt、tools、hook），让模型下一轮跑得更好。整个过程 harness 不泄露任何任务答案，它看的是模型自己的行为，改的是模型的执行环境和引导，不是替模型算出结果。

这里有两层。近期一层是人先写这批 harness 规则，验证它们能提分。远期一层是把写规则的工作交给 390B，让它读自己的失败轨迹、总结、改 harness，形成模型和 harness 的共同进化。近期这层是远期那层的前提，因为只有先确认哪些规则真能提分、以及提分不是靠泄露答案，才谈得上让模型自动去生成这类规则。

## 2. 从 MetaX 借什么，修正什么

这个方向的方法论参照是 `self_harness_agent`（MetaX 项目，文档在 `/home/dataset-local/wcy/self_harness_agent/docs/`）。它研究的是 harness 作为调节器，能不能把模型的自我校正能力引出来、再训练进权重，最终让模型自己给自己写 harness。ALE 是比它原来的 sokoban 载体更难、模型更强的场景，正好用来承接这个远景。

三样东西直接借。

第一，镜子非地图。MetaX 的核心约束是 harness 只反射关于模型自己的状态和历史的事实，比如你在原地转圈、还剩几步、上次试 X 得到 Y，绝不给任务解，比如最优动作、答案、搜索出的路径。给答案等于作弊，等于决策离开了模型的 token 流。这条约束原样搬到 ALE。

第二，leak_audit。MetaX 有一个审计扫描所有注入文本里有没有最优最佳推荐这类词，把泄露答案的轨迹标红判定不可训练。这套机制也搬过来，作为红线的自动检查，下面第 3 节展开。

第三，on-policy 判据。MetaX 区分 h2 作弊档和 h3 镜子档：h2 直接给最优动作，strip 掉提示模型就不会了，不可内化；h3 只触发模型本就能产生的自省，扰动小，可内化。ALE 上同理，我们加的规则要是模型自己能消化的小扰动，不是灌给它一个它产不出的精巧解。

一样东西要修正。MetaX 把这类介入统一叫元认知，分成 A 建模联想、B 监控校正、C 预算觉察三类 primitive。对 ALE 这个语境，元认知这个抽象层太虚，不好落地也不够准。更实用的说法是一批具体的程序性规则，每条规则是一个可判定的条件加一个动作：改文件前如果没读过这个文件，就先读再改；回答或动手前先查已有信息和过往经验，不从零开始；快到上下文上限时先提示还剩多少、该收敛了。这些不是抽象的觉察，是明确的操作纪律，条件能判定、效果能验证。下面第 4 节就是把这批规则列清楚。用规则库这个说法替代元认知这个说法，是这份方案和 MetaX 表述上的主要区别。

## 3. 一条红线：不泄露答案

红线是 harness 给的所有信息，必须是关于模型自己行为和处境的事实，或关于环境和预算的事实，不能是任务答案的任何部分。

在 ALE 语境里，可以给的和不能给的要分清。

可以给：你这个 edit 的目标文件本轮还没被读过；你连续三步在改同一行；你已经跑了 80 步、上下文用了 80%；你脚本刚算出的这个指标是 1.17、任务要求的阈值是 0.05；容器里默认 python3 是 3.14 没有科学计算包、系统 python3 是 3.10 有。这些都是模型自己能观察到或本就该知道的事实，harness 只是把它拎到眼前。

不能给：这道题的正确算法是什么；MCCFR 不收敛是因为你该把迭代次数加到多少、遍历方式改成什么；这个数值的正确答案是多少。这些是任务解，一给就越线。

区别的判据是 strip 测试：把这条注入删掉，如果模型仍能靠自己产出正确行为，只是慢一点，这条注入是镜子，合规；如果删掉后模型就产不出正确行为了，说明正确行为本来就来自这条注入而非模型，这条是地图，越线。第 4 节每条规则都要过这个测试，leak_audit 做自动兜底。

## 4. 规则库：每条规则挂哪、治什么

下面六条规则各自对应一个在 ALE 轨迹里真实看到的失败或低效，各自挂到 pi 的一个钩子上（钩子清单见 `pi-agent.md` 第 6 节），各自只给事实不给解。前三条是你提的三个例子，后三条是从 Ising 和 CFR 两条轨迹里读出来的。

### 4.1 改文件前先读文件

触发条件：模型要 edit 或 write 一个文件，而这个文件本会话还没被 read 过。

harness 动作：在 beforeToolCall 里拦下这次调用，返回一条事实，你要改的文件本轮还没读过，先读再改。不告诉它文件里是什么，只提示它自己去读。

挂点：beforeToolCall。

治的问题：盲改文件导致的覆盖和格式破坏。这是编码 agent 的通病，改一个自己没看过的配置或数据文件，容易改错结构。

strip 测试：过。删掉这条，模型仍能自己想到先读，只是有时会忘。这条只是把纪律前置。

### 4.2 动手前先查已有信息和经验

触发条件：模型开始写解题代码前，没有先 ls 或 read 任务目录、没有先查环境里已有的数据和脚本；或跨任务地看，它在重复解一个同类任务已经解决过的子问题。

harness 动作：轮内层面，在 system prompt 里加一条通用准则，动手前先查清楚任务目录里有什么、环境里装了什么，不从零假设。跨任务层面，用一个 extension 注册一个 notes 工具或经验检索工具，让模型把每次踩过的坑写进一个持久 notes，下次同类情况先查 notes。注意 notes 里只存模型自己总结的过程经验，比如某类环境该用哪个解释器，不存任何任务的答案。

挂点：system prompt 加 extension。

治的问题：Ising 任务花八步试解释器，CFR 任务重复摸索环境。同类环境坑在不同任务里被反复踩。

strip 测试：过。notes 存的是过程经验不是答案，删掉后模型仍能自己重新试出来，只是慢。这里要小心的是 notes 内容的审计，leak_audit 要扫 notes 防止某个任务的具体解被写进去带到别的任务。

### 4.3 预算觉察，压缩前提示

触发条件：步数或 token 或上下文占用越过一个阈值，比如上下文用到 70%、步数到预算的 80%。

harness 动作：在 afterToolCall 或轮末，把当前用量反射给模型，你已经用了 N 步、上下文占了 X%、快到压缩点了，注意收敛。pi 有 compaction 但触发时不提示模型，模型不知道自己快被压缩，也就不会主动收尾。

挂点：afterToolCall 反射用量，shouldStopAfterTurn 做硬止损。

治的问题：CFR 的 528 万 token 和 135 步失控。模型没有预算感，会一直觉得再修一下就行。

strip 测试：过。用量是模型自身资源的事实，给它只是让它自己权衡节奏，不替它决定停不停。硬止损那部分是控制不是内容，属于 harness 该管的预算护栏，不涉及答案。

### 4.4 终止判据校正

触发条件：模型准备判定任务完成，而任务有可检验的客观完成条件（数值达标、测试通过、契约满足），且当前不满足。

harness 动作：在 shouldStopAfterTurn 里接一个轻量客观检查，只反射条件满足与否。比如你报的可利用度是 1.17，任务要求 0.05，当前不达标。不满足就不允许停，把这个事实推回去逼它继续。不告诉它怎么达标。

挂点：shouldStopAfterTurn 加 afterToolCall。

治的问题：CFR 的核心失败。模型明知可利用度不达标，却因为文件写出来了就收工。这是零分档里最大的一类，直接打在它上面最可能提分。

strip 测试：过。达标与否是模型自己算出的指标和任务公开阈值的对比，都是事实。怎么把可利用度压到 0.05 才是解，harness 不给。

### 4.5 环境事实前置

触发条件：任务开始时。

harness 动作：把对整类任务都成立的稳定环境事实，在 system prompt 或任务启动时注入。比如容器里默认 python3 是 3.14 无科学计算包、系统 /usr/bin/python3 是 3.10 有 numpy scipy。ALE 的任务卡本身带 software 字段和 runtime 入口，harness 可以结构化地把这些喂给模型。

挂点：system prompt 或任务 setup。

治的问题：Ising 花八步试解释器。这类环境事实对所有 Python 计算任务成立，却要每个任务各自试，试不出来就超时。

strip 测试：过。这是环境事实不是任务解，删掉后模型仍能自己试出来。这条纯粹省重复试探的步数。

### 4.6 失败循环打断

触发条件：连续 N 步没有实质进展，比如同一条命令反复报同一个错、同一行代码反复改、状态指标不动。

harness 动作：在 beforeToolCall 或轮末反射这个事实，你在这一处已经绕了 N 步，同一个错误重复出现，换个思路。不替它换思路。

挂点：beforeToolCall 加轮末信号累积（用 extension 订阅事件维护进展计数）。

治的问题：CFR 在一个 shape bug 上绕了十步。模型陷在局部循环里不自知。

strip 测试：过。绕了几步、错误是否重复，是模型自己行为的事实。换什么思路由模型自己想。

### 4.7 汇总

| 规则 | 挂点 | 治的失败 | 给的是 |
|---|---|---|---|
| 4.1 改前先读 | beforeToolCall | 盲改覆盖 | 文件未读的事实 |
| 4.2 先查再动手 | system prompt + extension | 重复摸索、重解子问题 | 查什么的提示 + 自存经验 |
| 4.3 预算觉察 | afterToolCall + shouldStopAfterTurn | token 和步数失控 | 用量事实 + 硬止损 |
| 4.4 终止判据校正 | shouldStopAfterTurn + afterToolCall | 跑完零分、自我合理化 | 达标与否的事实 |
| 4.5 环境事实前置 | system prompt / setup | 重复试环境、超时 | 稳定环境事实 |
| 4.6 失败循环打断 | beforeToolCall + 事件订阅 | 局部 debug 死循环 | 无进展的事实 |

这六条覆盖了 ALE 当前两大失败来源。4.3 和 4.4 直接打超时和跑完零分，是最可能提分的。4.1、4.5、4.6 提高单任务的解题效率。4.2 兼顾单任务和跨任务的经验积累。每条都过了 strip 测试，leak_audit 做自动兜底。

## 5. 让 390B 自己看轨迹、自己改 harness

第 4 节的规则是人写的。你的远景是把写规则这件事也交给 390B 模型，让它读自己的失败轨迹、总结失败模式、改 harness，形成模型和 harness 的共同进化。这对应 MetaX 的三阶段，但要说清楚异同。

MetaX 的三阶段是：S1 用外部强模型按全局视角写镜子式 harness；S2 把 S1 的轨迹训练进弱模型权重，验收是丢掉 harness 后能力不退化且学会自触发；S3 模型自己写自己的 harness。你的设定有一点不同：跑任务的和分析轨迹改 harness 的是同一个 390B 模型，不是一个更强的外部模型。这更接近 S3 的自写形态，只是先不训练权重，用 in-context 的方式让模型分析和改。

落成一个闭环，每一轮是这样：

第一步，采轨迹。用当前 harness 跑一批 ALE 任务，收集 trajectory.json 和 run.json。

第二步，390B 分析失败。把失败任务的轨迹喂给 390B，让它回答三个问题：这个任务卡在哪一步、卡点是什么类型的失败、有没有一个只反射事实不给答案的介入能让模型自己绕过去。关键约束和 MetaX 一样，390B 的价值是诊断失败模式，不是给更聪明的解。它输出的是新规则或规则修订，不是任务答案。

第三步，规则过审。新规则先过 leak_audit，扫有没有把任务解写进注入文本。再过 strip 测试的人工或自动判定，确认删掉规则后模型仍能自己产出正确行为。过审的规则才进 harness。

第四步，重跑验证。用带新规则的 harness 重跑，看提分、看 leak 是否为零、看提分是不是靠泄露。

第五步，收敛判断。如果新规则稳定提分且不泄露，留下；进入下一轮。

远期如果要往训练走，才引入 MetaX 的 S2，把带镜子的轨迹训练进 390B 权重，让它去掉 harness 也能自己触发这些纪律。但训练是后面的事，当前先把 in-context 的采轨迹、分析、改规则、验证这个闭环跑通。

这里有一个 MetaX 明确提出的开放问题，搬到这里同样存在：390B 设计的触发规则本身，何时介入、介入什么，是不是一种隐性的策略注入。比如它总结出在可利用度不达标时打断，这个规则的时机选择里已经含了它对任务的理解。这个边界要在实践里盯着，判据仍是 strip 测试，注入的是事实还是解。

## 6. 可执行路线

按先易后难、每步可验证排。

第一步，读全量结果定优先级。99 个任务已跑完，分布和失败归因见 `ALE_qwen_run.md`。真实尝试 96 个平均分 0.288，失败主要是超时（19）和跑完零分（约 32）。这两类决定先补 4.3 和 4.4。这一步还暴露两个运行层前提：一是网关配额，末段 13 个任务曾被 apihy 402 废掉、集体拿假零分（已重跑，10 个拿回真实分）；二是机器资源，有 3 个任务要求 16 CPU、60 GB，本机分不出对应 cgroup 配额而跑不起来。所以搭 harness 前要先把运行做稳：监控网关错误、支持断点续跑、跑前确认配额和宿主机容量都够撑完整批，否则提分实验会被这类假零分污染。

第二步，先做 4.3 的预算护栏和 4.4 的终止判据校正。这两条挂在 shouldStopAfterTurn 和 afterToolCall 上，改动小，且直接打超时和跑完零分两大失败来源。先在几个已知失败任务上验证，比如 CFR，看能不能把它从 135 步止损、或逼它继续压可利用度。

第三步，补 4.1、4.5、4.6 这三条效率规则，挂 beforeToolCall 和 system prompt。用一小批任务做 A/B，带规则和不带规则各跑一遍，比平均分和平均步数。

第四步，做 4.2 的经验积累，用 extension 加 notes 工具。这条最复杂，因为跨任务的 notes 要防泄露，leak_audit 要能扫 notes 内容。

第五步，规则都验证有效后，做第 5 节的闭环，把分析轨迹和改规则交给 390B 试一轮，看它自己总结的规则能不能提分。

第六步，如果 in-context 闭环成立且要固化，才引入 MetaX 的 S2 训练。这一步 gated 在前面都验证通过之后。

## 7. 怎么衡量

每一步都要能证明提分是真的，且不是靠泄露。三个指标一起看。

平均分提升。带 harness 对不带 harness，同一批任务的平均分要显著涨。分开看超时数和跑完零分数有没有降。

leak 为零。leak_audit 扫所有注入文本和 notes，泄露答案的轨迹数必须是零。这是红线，不为零就不算数。

提分不靠泄露。对提分的任务做 strip 检查，把镜子注入删掉重跑，如果模型仍能做对只是慢，说明能力是模型的，harness 只是加速；如果删掉就做不对，说明分是 harness 喂出来的，越线了，这种提分不要。

一个贯穿的原则：harness 的功能是给事实、给结构、给预算，不是给答案。ALE 的评分看模型自己算对没有，harness 替模型做得越多，越测不出模型真实能力，也越训不出能独立解题的模型。pi 的薄正好守这条原则，我们要补的是护栏和事实反射，逐步补，每补一条都过 strip 测试和 leak_audit。
