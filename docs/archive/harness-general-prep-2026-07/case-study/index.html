ALE 逐题轨迹分析

从 pi 和 gpt_claw 的运行轨迹里挑有代表性的题，按领域分组，逐题讲清题目条件、给了什么、要求、如何评测，再看两套 harness 各自怎么做、为什么是这个分，最后给这一组题的 harness 优化方向。回到 结果总表。
这批运行时 gpt_claw 的交互轮数被限制在 30 轮，事后看太低也不公平：它的多数空输出失分直接来自这个上限，何况它还要花轮次在委派子 agent 和脚本拼装上。已把上限改到 100。之后的 ALE 任务模型走 boyue 网关（apirx.boyuerichdata.com）。本页分析基于 30 轮上限的运行结果。

跨领域的三条 harness 结论

  • 30 轮上限太低。gpt_claw 的空输出失分（agora、legal_ma、pe_screening）几乎都来自这个上限，何况它还要花轮次在委派子 agent 和脚本拼装上。已改到 100。批量题（sec_10k）上 pi 无上限就比封 30 轮的 gpt_claw 高 0.09。
  • 不泄露前提下最有价值的干预是交付契约校验。很多题有纯结构性的硬门槛：必需文件、必需标题、必需结论、必需字段。harness 可以在 agent 收尾前核对交付物是否满足这些结构契约，把缺口作为客观事实反射回去，不碰答案。这能救回空输出和漏结构的失分。
  • 报错数不预测成败。healthcare_variant 上 gpt_claw 报错 14 次仍拿满分，pi 报错少反而因规则偏差扣分。harness 不要用报错次数做干预信号，要看最终产出对不对。
