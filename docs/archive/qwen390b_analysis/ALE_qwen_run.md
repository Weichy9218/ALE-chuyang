# ALE 上用 Qwen3.5-397B 跑 pi-agent 的结果分析

本文报告在 tyyun_4 上用 pi-agent 跑 ALE（agents-last-exam）的结果。模型是 Qwen3.5-397B-A17B，经 apihy 网关调用。先讲清楚 ALE 是什么样的任务，再重点分析结果和结论。全量 99 个 CLI 任务已跑完，但要先说一个影响读数的事实：跑到末段时 apihy 的 qwen key 触发了 402 配额限制，废掉了 13 个任务，这批模型一个 token 都没跑。配额恢复后这 13 个全部重跑，其中 10 个拿到了真实分数（社会科学的疫苗复现、交通的车辆路径问题重跑后都拿了满分）。剩下 3 个要求 16 CPU、60 GB 内存，本机分不出这么大的 cgroup 配额，无法运行，从统计里排除。下面的分数按 96 个真实尝试来算。

## 1. ALE 是什么

ALE 是一个 agent 基准，全称 agents-last-exam。它不考单轮问答，考的是一个 agent 在一个真实容器里，从一句任务描述出发，读文件、写代码、跑命令、产出交付物的完整能力。

每个任务的形态是固定的。系统起一个 `agentslastexam/ale-ubuntu22-docker` 容器，容器里预置了任务的输入数据、依赖环境、一份任务说明。agent 拿到说明后在容器内自主操作，最后把结果写到指定路径。任务结束后有一个评分脚本检查产出，给一个 0 到 1 的分数。

三个特征决定了 ALE 难。

第一，任务是长程的。不是一步能答完的问题，是要写几百行代码、跑几十分钟、反复调试才能完成的工程任务。本次跑的一个 CFR 博弈任务，agent 走了 135 步、烧了 528 万 token。

第二，评分看数值不看格式。产出一个格式正确的文件不给分，产出的数值达到容差才给分。有硬门槛的任务里，某个前置检验不过直接零分，后面做得再多也没用。

第三，覆盖面宽。本次的 99 个 CLI 任务横跨约十一个领域：计算数学、健康医疗、生命科学、商业金融、工程、法律、教育信息、物理科学、交通安全、社会科学、心理神经。领域内又细分到量子物理仿真、基因组变异检测、期权定价、机器人 URDF 建模、临床试验统计等具体专业方向。一个任务往往要求 agent 具备该领域的专业知识加上把它落成可运行代码的能力。

本次跑的是 ALE 里的 CLI 子集，即纯命令行、不需要图形界面操作的任务，共 99 个（`ale_cli.txt` 与 `docker_support.txt` 的交集）。ALE 完整集还包含需要 GUI 操作的任务，本次没跑。

## 2. 运行配置

experiment `local_docker_pi_qwen35_cli`，99 个 CLI 任务，concurrency=4，每任务 wall_time 7200 秒，cleanup_mode=delete。每个任务起一个独立容器，pi 在容器内跑，用容器自带的 node 和 python。LLM 走 apihy 网关（`https://zgc.apihy.com/v1`），模型 qwen3.5-397b-a17b，reasoning 关闭。

pi 的接入方式是新写的一个 ALE harness（注册名 `pi`），细节见 `pi-agent.md`。运行输出在 `agents-last-exam/.logs/ale/local_docker_pi_qwen35_cli/pi/qwen3-5-397b-a17b/<task>/v0/<ts>/`，每个任务目录有 run.json、trajectory.json、transcript.jsonl。

## 3. 总体结果

先把 99 个任务分成两堆。

第一堆是被网关 402 废掉、后来重跑的 13 个任务。原始运行里它们的 run.json total_input_tokens 全是 0、stopReason 是 error、errorMessage 是 402，都在末段同一批（03:14 前后，physical_sciences、transport_safety、social_sciences、psychology_neuro 几个领域），起容器后一调 LLM 就收到 402、3 步内退出。配额恢复后全部重跑：10 个跑出真实分数并入下面的统计，3 个（免疫组分打分、有限角 CT 重建、mose2 能带吸收）因为要求 16 CPU、60 GB、本机无法分配对应的 cgroup CPU 配额而起不来，排除。这是两条运维教训：跑全量前要确认网关配额和机器资源都够撑完整批，并给运行加断点续跑和错误监控。

第二堆是 96 个真实尝试，模型实际跑了、消耗了 token。状态分布：

| 状态 | 数量 | 含义 |
|---|---|---|
| completed | 75 | 进程正常跑完并交付 |
| timeout | 19 | 跑满 7200 秒被杀 |
| failed | 2 | 跑了一半进程报错退出，无分数 |

在 94 个拿到分数的真实尝试上（completed 加有分的 timeout），平均分是 0.288。分数分布：

| 分档 | 数量 | 含义 |
|---|---|---|
| score=1.0 | 10 | 完全做对 |
| 0.5 ≤ score < 1 | 18 | 大体做对 |
| 0 < score < 0.5 | 16 | 部分做对 |
| score=0 | 50 | 跑完但没做对，或超时无产出 |

一个参照系：同一套 ALE、OpenHands harness、Qwen3.5-9B 的全量结果平均分约 0.06。换成 397B 大模型加 pi harness 后平均分约 0.29，是前者的四到五倍。这个差主要来自模型规模，不能全记到 harness 头上，但说明 pi 这套接入没有拖后腿。这个倍数只作粗略参照，两次的任务集不完全对齐。

满分的 10 个任务覆盖了计算数学（量子 Ising 仿真）、商业金融（美式期权 LS 定价、AB 测试分析、内部员工 agent）、生命科学（colistin 抗性基因识别）、系统运维（日志权限守卫）、交通（车辆路径问题）、社会科学（疫苗复现）。这说明模型在纯计算、纯统计、纯脚本类任务上具备一次做对的能力。

## 4. 分领域结果

按真实尝试统计各领域平均分（排除 3 个本机跑不了的任务）。重跑后物理科学有 10 个、交通安全 3 个样本；社会科学、心理神经仍各只有 1 个，样本太少，读数仅供参考，下表以样本数不少于 2 的领域为主。

| 领域 | 平均分 | 真实尝试数 |
|---|---|---|
| transport_safety | 0.589 | 3 |
| legal | 0.576 | 2 |
| business_finance | 0.538 | 10 |
| computing_math | 0.345 | 18 |
| life_sciences | 0.296 | 18 |
| health_medicine | 0.217 | 20 |
| education_info | 0.196 | 3 |
| engineering | 0.127 | 7 |
| physical_sciences | 0.042 | 10 |

商业金融和法律分高，因为这类任务多是结构化数据处理、报表重构、合规分类，软件栈标准、评分点明确。工程和物理科学分最低，因为它们涉及机器人控制、电网可靠性、建筑 MPC 控制、能带计算、声子谱这类需要专用仿真器和领域求解器的问题，模型既难一次写对，环境依赖也重。健康医疗任务数最多（20 个）但分不高（0.217），因为里面有大量需要跑完整生信流水线或医学影像处理的重任务，容易超时。

## 5. 失败构成

把失败拆开看，比只看平均分更能定位瓶颈。真实尝试里三类失败。

第一类，超时。19 个 timeout，占失败大头。这些任务跑满 7200 秒被杀，多数是重计算（医学影像解码、基因组变异检测、城市交通仿真标定）。pi 的主循环没有步数上限也没有 token 预算，只要模型一直发工具调用就一直转，长任务容易滚到墙钟上限。19 个超时里只有 1 个（branch_bound_atsp，0.8125）拿到了部分分，其余 18 个是 0 分无产出。

第二类，跑完但零分。50 个零分里去掉上面 18 个超时零分，还有约 32 个是进程正常结束、产出了格式正确的文件、但数值没达标。典型是下面第 7 节的 CFR 任务：agent 明知可利用度不达标，仍因为文件写出来了就判定完成。评分看数值，格式对数值错等于零分。这是真实尝试里最大的一类可改进失败。

第三类，进程报错。2 个 failed（有 token 消耗的那种），跑到一半代码或环境硬错误退出。

另外要和上面第 3 节呼应：还有 3 个任务因本机资源不足（需 16 CPU、60 GB）无法运行，那不算能力失败，是机器容量问题。

一个被数据否定的担心是缺工具。有人担心 pi 缺搜索或联网工具会拖分。实测里真实零分任务中只有极少数的描述含联网或下载关键词。多数 ALE CLI 任务的数据已在容器本地，bash 加 curl 足够。所以能力瓶颈不是工具，是两件事：任务本身太难模型算错，和长任务超时。

## 6. 成功轨迹：量子 Ising 链后测量态

### 6.1 任务

`computing_math/ising_post_measurement_1`。给一条临界的一维量子 Ising 链加一条 ancilla 链，N=10，耦合参数 u=0.1。要求算四样东西存成 numpy 文件：临界基态、后测量概率、一号格点约化密度矩阵、单体关联函数。基态要用虚时演化求，dt=0.0002，K=50000 步。评分是数值容差检验：基态与精确对角化结果的保真度要达标，概率要归一，密度矩阵要厄米且迹为一。纯计算任务，数据在本地，软件栈是 Python、NumPy、SciPy。

### 6.2 agent 怎么解的

pi 走了 46 步，得分 1.0，输入 24 万 token，输出 1 万 token。分四段。

读规格（步 3 到 9）：一次读多个文件，拿到 N、u、dt、K，确认依赖 numpy==2.2.6、scipy==1.15.3，ls 输入目录。没有浪费步数。

写脚本（步 10 到 13）：建 output 目录，一次写出 12591 字节的 solve.py，涵盖虚时演化、逐测量结果算后测量态、约化密度矩阵、关联函数。

环境摸索（步 14 到 32）：这是真正的卡点。第一次运行报 no module named scipy。接下来八步都在找对的解释器：pip install 报缓存不可写、import 仍失败、打印 sys.path 发现默认 python3 是 3.14 版、试各种 pip 都不行，最后步 30 到 32 确认默认 python3 指向 cua-server 的 3.14 虚拟环境没装科学包，而 /usr/bin/python3 是 3.10 且包齐全，改用后跑通。

验证（步 34 到 46）：agent 没算完就交，而是另写一段精确对角化代码，算出基态保真度 0.99999990，态不保真度约 1e-7，远低于 1e-4 容差；再检查密度矩阵厄米、迹为一、本征值合法；检查关联函数落在 [-1,1]；最后 ls 确认四个文件都在。

### 6.3 这个成功说明什么

模型的物理和数值能力足够，一次写对了完整解法，还自己造了独立验证器。真正花步数的是环境摸索，八步试错才定位到解释器问题。

这里有一个可被 harness 消化的点。容器里默认 python3 是 3.14 无科学包、系统 python3 是 3.10 有包，这个事实对所有 Python 计算任务都成立。成功任务花八步试出来，别的任务可能试不出来就超时。harness 在任务开始时把这条环境事实直接告诉模型，或提供配好依赖的运行入口，这八步就能省掉。这是给环境事实不是给答案。

## 7. 失败轨迹：CFR 博弈均衡求解

### 7.1 任务

`computing_math/cfr_game_theory_equilibrium`。实现三层递进的两人零和博弈均衡求解器，合并成一个 results.json。Tier 1 是矩阵博弈，求均衡值和混合策略；Tier 2 是 Kuhn poker，用 CFR 迭代报可利用度和平均策略；Tier 3 是 4-rank Leduc poker，用 MCCFR 报可利用度和完整平均策略表。评分有硬门槛：results.json 缺失、JSON 解析失败、或 Tier 1 的公开检验不过，任一触发直接零分。三层各有可利用度目标，Tier 3 目标 0.05。难点在 CFR 和 MCCFR 要真收敛到低可利用度，不只是把代码写出来。

### 7.2 agent 怎么解的

pi 走了 135 步，得分 0.0，输入 528 万 token，输出 10 万 token。这是所有任务里 token 消耗最高的一个。工具调用构成是 bash 44 次、write 8 次、edit 8 次、read 7 次，报错结果 14 次。

前段（步 9 到 40）是环境准备和三层求解器初版。中段是长时间 debug，反复运行 solver、看输出、发现不对、edit 修改、再运行。一个典型循环在步 113 到 122：agent 发现 regret_matching 在所有 regret 为零时返回固定的两元素数组 [0.5, 0.5]，而实际策略维度可能是 3，导致形状不匹配。它加调试打印定位、改对函数、删掉打印、再运行。单这一个 shape bug 就绕了差不多十步。后段（步 124 到 135）solver 终于跑通，产出格式正确、含三层字段的 results.json。但 agent 在步 125 的思考里自己写道 Tier 3 可利用度是 1.17，远高于 0.05 的目标。它在步 127、129、131 反复确认输出结构正确、可利用度偏高，然后在步 135 判定完成。

### 7.3 卡点在哪，为什么零分

卡点不是不会写，是写出来的 MCCFR 没收敛。Tier 3 可利用度 1.17 对目标 0.05 差二十多倍，意味着求出的策略远不是均衡。这通常是迭代次数不够，或采样、平均策略累积、遍历方式有实现问题。

更值得注意的是收尾判断。agent 明确知道可利用度不达标，却因为输出格式正确、结构完整就认定完成。这是一次自我合理化，把我产出了一个文件当成我解决了问题。

从这条轨迹读出三个问题。第一，模型能实现算法框架，但让迭代类算法真正收敛到指标，超出它一次成型的能力，它也没靠自己把可利用度压下去。第二，没有有效止损，135 步、528 万 token 里很大一部分花在一个 shape bug 的反复试探上，上下文越滚越长，token 就是这么堆出来的。第三，终止判据错位，agent 用文件写出来了当完成信号，而真实完成信号是可利用度达标，模型手里有这个数、也知道不达标，但没有机制强制它继续迭代。

### 7.4 为什么能刷到 135 步

这直接对应 pi 的架构。pi 的主循环没有步数上限也没有 token 预算，靠模型自己不再发工具调用来停。模型只要一直觉得还能再修一下，循环就一直转。cfr 里模型陷在 debug 循环始终认为下一步能修好，于是转到 135 步才因自认完成而停。这一点详见 `pi-agent.md`。

## 8. 关键结论

第一，模型规模到 397B 后，pi 这套薄 harness 在 ALE CLI 子集上、96 个真实尝试里能到平均分 0.288，是 9B 加 OpenHands 的四到五倍。接入本身没问题。

第二，瓶颈不是缺工具，是任务难度加长任务失控。缺搜索工具的担心数据不支持。真正拖分的是超时（19 个）和跑完但没做对（约 32 个）。

第三，两类最直接可改的失败有共同根源，都是 pi 没有护栏。超时源于主循环无预算，任务能无限刷步数。跑完零分源于终止判据交给模型，模型会用文件写出来了自我合理化。这两类失败不是模型不会做，是外壳没有在正确的时候拦住它。

第四，模型的正面能力是真实的。Ising 任务一次写对完整物理解法还自造验证器，说明它有自我校验的行为倾向，只是不稳定、不是每个任务都触发。

第五，两条运维教训。一是网关配额，末段 13 个任务被 apihy 402 废掉、集体拿假零分，跑全量前要确认配额能撑完整批，跑中要监控 402 并支持断点续跑；这 13 个已重跑，10 个拿回真实分数。二是机器资源，有 3 个任务要求 16 CPU、60 GB，本机无法分配对应 cgroup 配额而跑不起来，跑全量前要核对最大单任务的资源需求和宿主机容量。

前四条合起来指向下一步：不改模型，先在 pi 外面补一层只给事实和预算、不给答案的护栏，把超时和跑完零分这两类失败接住。具体方案见 `next_step.md`。
